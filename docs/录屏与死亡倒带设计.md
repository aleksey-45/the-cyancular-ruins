# 录屏与死亡倒带设计

> 状态：**F5 录屏已升级（2026-11-12：原生 1:1 抓帧 + H.264/AAC MP4 + 音频 + 死亡重开不打断），死亡倒带沿用原型**。现行规格见 **§0.1**；与源码冲突时以源码为准，`core/present/record/recorder.gd` 是单一真相源。§1/§4/§6 里 2026-11-06 的 960×720@60/q0.80/主视口 26 ms 等数字是旧原型快照，已被 §0.1 取代。
> 已落地：exe 同目录 `record/`（已 gitignore）、`Recorder` autoload、AVI MJPEG 临时封装 + ffmpeg H.264/AAC 后编码、内存死亡带、VHS 回放叠加层。
> 侦察与实测的原始记录在会话临时目录（不入库），本文只摘结论与可复核口径。

## 0.1 现行 F5 录屏规格（2026-11-12 升级，以此为准）

> 实测方式：一次性非 headless 探针（不入库，按仓规不为观感/成本项写产品守卫）；下面数字是本轮探针的实测结论，可复跑口径见 §0.1 各行的命令/参数。

| 项 | 规格 |
|---|---|
| 抓帧 | **直读主视口**：`get_viewport().get_texture().get_image()`，原生 1920×1440、1:1、无缩放/无重采样。**不再用 SubViewport 抓 1:1**——桥要额外渲染一张 1920 视口，实测整帧 26.8 ms / 37 fps；直读读回仅 9.6~11.4 ms，且所见即所得（含 HUD/后处理）。SubViewport 只保留给死亡带（960×720 LINEAR，旧观感不变）；录制期间死亡带复用同一张整帧在 worker 里 resize，不额外读回。 |
| 帧率 | 目标 **30 fps**，用 `Time.get_ticks_usec()` 做槽位时钟：每次 `_process` 算目标槽位 `floor(elapsed*30)`，抓到一帧后按「目标槽位 − 已写槽位」把同一 JPEG blob 重复写入 AVI。视频时长恒等于真实录制时长（掉帧 / 死亡重开都不漂）；录制时钟与 `_run_t`/`_reset_run` 解耦。 |
| 编码 | worker 线程 JPEG **q0.95** → MJPEG AVI 临时文件；停止后 **worker 线程**跑 ffmpeg（`OS.execute` 不在主线程）合成：`-c:v libx264 -preset medium -crf 22 -pix_fmt yuv420p -color_range tv -c:a aac -b:a 192k -movflags +faststart -shortest`。CRF 默认 **22**（视觉无损档，取 OBS 官方 x264 录制档 16~23 的中段），可用环境变量 `CYR_REC_CRF` 覆盖（14~32；16=最高质量、体积约 4 倍，24+ 更小）。 |
| 体积/码率 | 1440p30、含「死亡→REWIND→重开」段的实测样片：**298 帧 / 9.933 s / 2.87 MB = 16.5 MB/min（2.28 Mbps）**；同管线旧默认 CRF16 实测约 **70 MB/min**（≈4 倍）。CRF 矩阵（同一 7.03 s 样片重编码，保守口径）：16→60.6、20→31.8、22→20.2、24→13.6 MB/min。按 16.5 MB/min 估算 3 分钟约 **50 MB**（CRF16 约 210 MB）。 |
| 音频 | 录制时给 Master bus 挂 `AudioEffectCapture`（buffer 1.5 s，先 clear），每次 `_process` 排空 `get_buffer()`，按 `AudioServer.get_mix_rate()` 转 s16 立体声写 `clip.wav`（自拼 44 字节 WAV 头、close 回填长度）；停止收尾摘掉 effect（不录时 Master bus 无副作用）。转码成功删 AVI + WAV。**非静音验证**：探针起录即播 440 Hz 固定音 + `Sfx.play("explosion"/"hurt"/"kill")`，成片 `volumedetect mean_volume = -19.0 dB / max 0.0 dB`（回退 WAV 同法 `mean_volume = -25.1 dB`）。 |
| 输出 | 成功：`record/rec_<stamp>/clip.mp4`（控制台打印实际路径，AVI/WAV 成功即删）；无 ffmpeg / 转码失败：保留 `clip.avi` + `clip.wav` 并打印原因。ffmpeg 探测只在启动时做一次（PATH，可用环境变量 `CYR_REC_FFMPEG` 覆盖/`0` 禁用），不引入硬依赖。 |
| 死亡重开不打断 | `start_rewind()` 不再停录；`_process` 的录制 tick 在 `_replaying` 早退之前（回放画面也录进去）；`restart_single()` 原地复位不影响录制；F5 在回放中也能停录。 |
| 质量（同机位、静帧） | MP4 抽帧 vs 游戏内 PNG（默认 CRF22）：**PSNR 42.2 dB / SSIM 0.998**；CRF16 时为 42.5 dB（差 0.3 dB，肉眼不可辨）；旧 960×720 q0.80 管线模拟：PSNR 35.4 dB（差 6.8 dB）。ffprobe（CRF22 样片）：`h264 High / 1920×1440 / yuv420p / 30 fps / 298 帧 / 9.933 s / 2.28 Mbps` + `aac LC / 48000 Hz / 立体声 / 9.962 s`。 |
| 音画同步 | 录制时间戳全部取自 `Time.get_ticks_usec()`；探针在已知录制时间注入 1 kHz 短音，成片音轨检测到的起点与视频时间轴偏差 **-4 ms / +3 ms**（两处，n=2）；音频/视频流时长 7.018/7.033 s，帧数 = 时长×30（211 帧）无漂移。 |
| 方向/颜色 | 直读 `get_image()` **不需要 `flip_y()`**：1920×1440 PNG 与 MP4 抽帧方向一致，HUD（时钟/击杀数/武器栏）位置正常；判定方法 = 统计右上/右下 200 行内 `● REC` 的 danger-red 像素（`UiFactory.C_DANGER`≈(0.9,0.4,0.4)），实得**上区 604 / 下区 0**，且人工打开 PNG 确认 HUD 全部在正常位置、玩家正立。 |
| 抓帧成本（本机，120 帧/档） | SubViewport+Sprite 桥 readback mean/p99：1920×1440 9.7/12.1 ms、1600×1200 7.6/10.0、1440×1080 5.4/7.2、1280×960 4.9/7.4、960×720 2.8/4.5；主视口直读 9.8/12.5 ms。桥在 1920 档整帧 P95/P99 有 25~26 ms 尖峰；1:1 时桥无收益。整段真实录制（含倒地→倒带→重开）：**游戏帧率 mean 54.3 fps、帧 p99 24.0 ms；视频 244 帧 / 8.13 s = 30 fps**。 |
| 守卫 | 观感/成本/音画同步项**零自动守卫**（只能人眼 + 一次性探针实测）；纯逻辑（死亡带曲线/帧数）仍由 `tests/smoke/record_rewind_smoke.gd` 守。 |

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| F5 录屏 | **1920×1440 原生 1:1（直读主视口）@ 30 fps**，worker JPEG q0.95 → 停止后 worker 线程 ffmpeg 转 **H.264 + AAC MP4**（无 ffmpeg 回退 AVI+WAV），同步录 Master bus 音频。现行完整规格见 **§0.1**。 |
| 为什么不直接录 1920×1440 | 旧结论已推翻：主视口 `get_image()` 实测 **9.6~11.4 ms/帧**（2026-11-12 复测），可支撑 30 fps 录制；真正不可用的是「SubViewport 1:1 抓帧」桥（额外渲染一张 1920 视口，整帧 26.8 ms / 37 fps）。现行方案 = 直读 root 视口（§0.1）。 |
| 死亡倒带 | **纯内存环形缓冲，不生成任何文件**（按 2026-11-06 的要求；也避免"写盘 + 失败删除"的 4 类残留）。与 F5 共用采集机制，只是第二个 sink；默认 640×480，读回按面积估算约 3.4 ms/次。 |
| 原点 | 一局的地图出生点（地图 `# player`，`MazeGenerator.load_spawns()["player"]`）。带子从加载完成、玩家可见的第一帧开始录，死亡瞬间冻结。 |
| 加速曲线 | **按显示帧的几何级数**：`step_i = step_0 · r^i`，`step_0 = 1/60`（起步 1× 实时），`r = 1.04`。前面加 0.5 s 死亡慢放（0.5×→1×）。D = 10/30/60/120/300 s 时演出总长 **2.07/2.53/2.82/3.12/3.50 s**；死亡到可操作 **2.50/2.96/3.25/3.55/3.93 s**。演出总长只随 `log D` 增长。 |
| 帧率 | **回放显示 60 fps ≠ 采集全程 60 fps**。F5 录制要 60 Hz；死亡带默认 30 Hz（慢放段 30 fps 源 + VHS 噪声可接受），预算允许再升 60 Hz。远处按 `Δt(u) = max(1/60, speed(u)/60)` 逐级抽稀；300 s 一局只要约 **192 帧**。 |
| 存哪 | 死亡带 640×480 JPEG，约 13~33 KB/帧，一局 **192~320 帧 ≈ 2.5~10.5 MB**，内存上限 24 MB；无文件、无删除逻辑。F5 落盘：录制中 MJPEG AVI（q0.95，1920×1440 约 110 KB/帧 ≈ 3.3 MB/s）+ WAV，停止后 worker 转 H.264 MP4（crf 22，实测约 **0.28 MB/s = 16.5 MB/min**），成功后 AVI/WAV 删除、最终只留 `clip.mp4`。 |
| 滤镜 | VHS 磁带组（逐行抖动 / 跟踪带 / head-switch / 色差 / chroma bleed / 扫描线 / 噪点 / dropout / 桶形 / 暗角）+ 速度驱动（帧混合、横向拖影）+ 底片化（复用后处理 `rewind_film` 公式）+ 冷青 tint + `REWIND`/`◁◁`/时间码/倍率 UI + 白闪-黑场转场 + 磁带 whirr 音。 |
| 关键前提 | **当前发行 exe 的模板有 JPG**（实测；与仓库 `cyancular_build_profile.gdbuild` 的 `module_jpg_enabled:false` 不一致，见 §4）。若按仓库 profile 重编模板，JPG 与 MJPEG AVI 会一起消失，需走 960×720 PNG 退路。 |

## 1. 录屏通道（F5 普通录屏）

### 1.1 抓什么：960×720 专用抓帧视口

> ⚠ 2026-11-12：本节方案已被 **§0.1** 取代——录制改为直读 root 视口（1920×1440 原生 1:1），SubViewport 只保留给死亡带。下面 960×720 的数字是旧原型快照。

**结论先行：不能抓 1920×1440 主视口再缩。** 实测主视口 `get_viewport().get_texture().get_image()`（1920×1440）单次 **26.11 ms**，连续录制时主线程中位 **40~43 ms**，单帧就超过 60 fps 的 16.7 ms 预算；抓帧成本随像素面积线性（960×720 = 7.69 ms、1920×1440 = 26.96 ms、2208×1728 = 37.69 ms）。Phase 2 的端到端实测里，"主视口抓 + shrink + 2 worker JPG" 只有 **23.96 fps**，"1920 + 8 worker" 只有 **26.66 fps**。

可行路径（**唯一实测达到 60 fps 的组合**）：

1. 新建一个不可见的 **`CaptureViewport`（SubViewport，960×720，`render_target_update_mode = ALWAYS`）**；
2. 里面放一张全屏 `TextureRect`，`texture = get_viewport().get_texture()`（root viewport 的 `ViewportTexture`），`stretch_mode = STRETCH_SCALE`——用 GPU 做 2× 降采样，拿到的是**最终合成画面（含 PostProcess 与 HUD）**；
3. 录屏服务在 `RenderingServer.frame_post_draw` 之后（或 `_process` 里）读 `CaptureViewport.get_texture().get_image()`（960×720），只付 960×720 的读回成本；
4. 死亡带可以复用同一张 960 图，在 worker 里再缩到 640×480（或直接再建一只 640×480 的抓帧视口，按 §1.5 的预算取舍）。

为什么不是别的源：

- **root viewport 1920×1440**：画面最准，但读回 26 ms，不成立。
- **`WorldViewport` 2208×1728**：读回 37.69 ms，而且它是透明底的世界渲染缓冲，**没有** PostProcess 合成的天空/光照/鱼眼/中心裁切，也没有 HUD 与发光通道；回放时要么缺一半观感，要么得重放整套昼夜参数（第二个真相源）。
- `window/stretch/mode="viewport"` ⇒ 窗口尺寸档位怎么切（`core/config/settings.gd` 的 `apply_display()`），root 纹理恒为 1920×1440，`CaptureViewport` 也固定 960×720，与窗口无关（实测窗口 1280×960 时抓帧仍是 1920×1440）。

**抓帧桥已验证（2026-11-06，真实 Level0）**：`TextureRect` 会因自身最小尺寸 = 贴图尺寸（1920×1440）把视口撑大、结果只裁到左上角；改成 **`Sprite2D` + `scale = (960,720)/root_size`** 后内容正确（与 root 降到 960 的逐像素采样差 mean ≈ **0.03–0.08 / 255**，仅差 1 帧延迟）。读回实测 **3.7~4.1 ms/次**，不是 Phase 2 探针场景里的 7.69 ms。实现见 `core/present/record/recorder.gd::_ensure_capture()`。

- **抓帧时机**：`get_image()` 是 GPU→CPU 同步读回，拿到的是最近一帧。放在渲染帧末（`RenderingServer.frame_post_draw` 信号里）或 `_process` 中抓上一帧都可以；仓内截图范式都先 `await` 2~4 帧再抓（`tests/harness/menu_autotest.gd`、`tools/_shot_scene.gd`）。
- **headless / Web 早退**：headless 的 root 视口纹理是空壳，`get_image()` 会打引擎 ERROR（污染 `grep -ci error` 判红）；Web 没有可写的 exe 伴随目录。两处都必须 `DisplayServer.get_name() == "headless"` / `OS.has_feature("web")` 早退。

### 1.2 编码与线程模型（实测）

实测环境：Windows，Godot 4.7.1（发行裁剪模板），20 逻辑核；样本是 64×64 伪随机噪声平铺（**编码耗时/体积的保守上界**），n=12 取中位。

| 分辨率 | 编码 | 单帧字节（噪声上界） | 单线程中位 | 8 并发等效吞吐 |
|---|---|---:|---:|---:|
| 1920×1440 | PNG | 372 KB | 123.6 ms | 43.1 fps |
| 1920×1440 | JPG q0.80 | 1.81 MB | **56.3 ms** | **115.0 fps** |
| 1920×1440 | WebP q0.75 | 3.18 MB | 520.0 ms | 9.8 fps |
| 960×720 | PNG | 171 KB | 36.4 ms | 169.4 fps |
| 960×720 | JPG q0.80 | 453 KB | **14.8 ms** | **391.6 fps** |
| 960×720 | WebP q0.75 | 796 KB | 132.6 ms | 10.5 fps |

其它实测：`Image.duplicate()`（1920 RGBA8）0.13 ms；`shrink_x2()` 2.97 ms；`resize(960×720, BILINEAR)` 13.5 ms（太贵，别放主线程）；写盘 10 MB ≈ 10~24 ms（400~950 MiB/s，page cache 口径）。

Phase 2 真窗口端到端（300 帧，`Engine.max_fps = 60`，vsync off；探针场景 150 个移动色块，**GPU 负载远轻于真实游戏**）：

| 配置 | 实际 FPS | 帧时间 p50 / p99 | 主线程中位 | 丢弃帧 |
|---|---:|---|---:|---:|
| 不录（baseline） | 60.00 | 16.66 / 17.28 ms | — | — |
| 主视口抓 1920 + shrink + 2 worker JPG | 23.96 | 44.26 / 49.06 ms | 43.50 ms | 0 |
| 主视口抓 1920 + 8 worker JPG | 26.66 | 40.94 / 43.85 ms | 40.14 ms | 0 |
| **960×720 抓帧视口 + 2 worker JPG** | **60.01** | **16.67 / 17.02 ms** | **7.96 ms**（max 15.48） | **0** |

结论：

- **默认：960×720 抓帧 + JPEG q0.80 + 2 个编码 worker**。编码只在 worker 线程做（`WorkerThreadPool.add_task`），主线程绝不 `wait_for_task_completion`，每帧轮询 `is_task_completed`。
- **队列上限 4~6**；满时丢**最老**的待编码帧（最近段更重要），同时记录时间戳，回放/封装按时间戳走。
- **主线程预算**：实测中位 7.96 ms、峰值 15.48 ms（探针场景）。真实游戏的物理/渲染/脚本开销会叠加上来，**能否在真实对局里稳 60 fps 尚未验证**（见 §4.1 与 §5）。
- **1920×1440 输出本机不可行**：主视口抓帧 26~43 ms，编码器再快也救不回来。若产品必须 1920 输出，需要另找异步读回或"960 抓帧 + 编码后放大"（均未验证）。
- **WebP 不可行**：960×720 单线程已 132.6 ms，8 并发约 10 fps，差 60 fps 六倍以上；只适合做缩略图/静态截图。
- **若 JPG 不可用**（按仓库 profile 重编模板）：唯一 60 fps 退路是 **960×720 PNG**（36.4 ms，8 并发 169 fps），但抓帧 + PNG 端到端未实测；或接受 30 fps。

### 1.3 封装与落盘

- **推荐单文件容器 `.cyrrec`**：`magic + JSON 头（宽/高/fps/编码/起点时间/帧数）+ 逐帧 [u32 长度][JPEG 字节]`。不依赖外部库，可断点恢复，实现约 100 行。
- 若需要"双击就能播"：写一个最小 **AVI (RIFF/MJPEG) muxer**，每个 `00dc` chunk 放一帧 JPEG，约 100~150 行。**前提是 JPG 在**（当前模板可行；jpg-off 模板上 `MovieWriterMJPEG` 与 `save_jpg` 一起消失）。
- 不推荐「每帧一个 JPG 文件」：目录污染、易丢帧；60 次/秒 create+close 在 Windows 上会被杀毒软件拖住。
- **目录**（三态，和仓内 `server/server_main.gd` 的 `local_ip.txt` 同款思路）：
  - 导出包：`OS.get_executable_path().get_base_dir().path_join("record")`；
  - 编辑器：`ProjectSettings.globalize_path("res://").path_join("record")`（即仓库根）；
  - 失败回退 `user://record`，并在日志/UI 里打印最终落点。
  - `DirAccess.make_dir_recursive_absolute()` 与 `Image.save_*` 的 `Error` 都要判；文件名手拼 `YYYYMMDD_HHMMSS`（**不要**用 `Time.get_datetime_string_from_system()` 的冒号，Windows 非法；也**不要**用 `RegEx`）。
- 本仓实际状态：仓库根（= 当前 exe 目录）已建 `record/`，并已加进 `.gitignore`。
- **体积估算**：960×720 JPEG 真实像素画风实测 **30~74 KB/帧** ⇒ 60 fps 约 **1.8~4.4 MB/s**，1 分钟 **108~266 MB**。若嫌大，降到 q0.70~0.75 或 30 fps；这是产品取舍，不是技术限制。
- **音频（可选，第二期）**：`AudioEffectRecord` 挂在 Master bus 上，结束后 `get_recording()` 拿 `AudioStreamWAV`，另存 `.wav` 再与视频封装；也可先不做音频。

### 1.4 F5 键位与开关

- **实现方式：`Level0._unhandled_input()` 里原码判定，转发给 WorldViewport 之前拦截**：

  ```gdscript
  var k := event as InputEventKey
  if k != null and k.pressed and not k.echo and k.physical_keycode == KEY_F5:
      _recorder.toggle()            # 开始/停止
      get_viewport().set_input_as_handled()
      return
  $WorldViewport.push_input(event)
  ```

  理由：F5 全仓空闲；不改 `project.godot`、不进 `Settings.REMAPPABLE_ACTIONS`；`Settings.reset_bindings()` 会 `InputMap.load_from_project_settings()` 清掉运行期加的动作，所以"只在运行期 `InputMap.add_action`"不可靠。
- **本期不做可重绑**。将来要做，必须同时改 `project.godot [input]`、`Settings.REMAPPABLE_ACTIONS`、`scenes/settings_menu.gd` 的 `ACTION_NAMES`，并升 `BINDINGS_VERSION`（还有一份键位契约冒烟会红）。
- **启动时默认不录**（F5 是开关）；录制中右上角显示 `● REC`（1 Hz 闪）；离开关卡/切场景自动收尾 `flush()+close()`。
- 命令行自动化开关（如 `-- --rec-autotest`）必须从 `OS.get_cmdline_user_args()` 读，写在 `--` 之后。

### 1.5 60 fps 主线程预算与降级阶梯

60 fps 帧预算 16.67 ms。实测（探针场景）：960×720 抓帧视口 `get_image()` 7.69 ms，`shrink_x2` 2.73 ms（如需要），"抓帧 → 入队"主线程总中位 7.96 ms、峰值 15.48 ms。编码全部在 worker（960 JPG 约 6.1~6.4 ms/帧）。

| 触发条件（滚动中位/每秒结算） | 动作 |
|---|---|
| 主线程中位 > 10 ms 或 p99 > 16.7 ms 连续 60 帧 | L1：死亡带若已开 60 Hz → 降回 **30 Hz**（默认就是 30 Hz）；F5 仍是 60 Hz（用户明确要 60） |
| 死亡带仍超预算 | L2：死亡带 640×480 → **480×360**（读回成本按面积约减 44%） |
| F5 录制期间掉帧 | L3：F5 抓帧 960×720 → **800×600 或 720×540**，或录制帧率 60 → 30 |
| 编码队列深度 ≥ 4 持续 1 s | L4：q0.80 → q0.70；仍积压则分辨率降档 |
| 主线程仍 > 10 ms p95 | L5：关闭死亡带（只保留 F5）；死亡时走「假倒带」兜底（§2.6） |
| 单帧读回 > 16 ms（偶发） | 丢该帧，不立刻降级；连续 3 次才降 |

> **真实游戏未验证**：探针场景的 GPU 负载远轻于游戏，7.96 ms 是"只抓帧"的成本；真实对局的物理/渲染/脚本开销叠加后是否仍稳 60 fps，必须在真实关卡里实测（见 §5 第 1 步）。这也是本方案唯一还没有实测闭环的硬风险。

### 1.6 音画同步与时间戳

- 每个 `CaptureFrame` 带**局内时间**（录制服务自己 `_t += delta`，单位秒），不是文件序号。掉帧时时间戳照样往前走，回放/封装按时间戳对齐，不会因为丢帧导致"时间变慢"。
- 死亡带按 `t_run` 排序并冻结；F5 封装在文件头写 fps 与起点时间，容器内每帧可带 u32 时间戳（毫秒）。
- 音频若做（第二期）：`AudioEffectRecord` 录 Master bus，结束后拿 `AudioStreamWAV`；视频/音频各写各的，封装时按起点时间对齐。音频采样率与视频帧率无关，不要用帧序号推算音频偏移。

## 2. 死亡倒带

### 2.1 语义与原点

- **倒带 = 视频回放，不是状态回滚**：播放录下来的画面，不改游戏世界状态；播完再调现有的 `Level0.restart_single()`。不要复用 `WorldRewind`（20 Hz 状态快照，会真的改位置/HP/子弹/砖）。
- **原点 = 一局的地图出生点**（主策划案 §2.2「失败后将倒回该张地图开始时」）。权威来源 = `MazeGenerator.load_spawns()["player"]`；播放结束时不要自己算，直接调 `restart_single()` 让它自己取值（单一来源）。
- **一局边界**：从 `Level0` 加载完成、玩家可见的第一帧（`LoadingScreen.hide_loading()` 之后）开始录；死亡瞬间冻结；`restart_single()` 之后清空并重新钉原点帧。不要从 `_ready` 第一行开录，否则带子开头是加载遮罩/黑屏。
- **不生成文件**（按 2026-11-06 要求）：死亡带 **纯内存**，不落盘、不写临时文件、不需要"播完删除"。F5 普通录屏才写 `record/`（exe 同目录，且只在那一个目录内）。两者共用采集源，但 sink 不同。

### 2.2 缓冲：内存环形缓冲（RingSink）

> 2026-11-06 追加约束：**倒带不生成任何文件**。不写 `record/`、不写临时文件、不需要"播完删除"；唯一会写盘的是玩家主动按 F5 的普通录屏。

- **内容**：**640×480** JPEG blob + 游戏时间戳（`age`，距死亡/距开局的秒数，由录制服务自己 `_t += delta` 累加，不要拿 `WorldRewind._t`、`engine.get_frames_drawn()` 或 `day_hour` 当索引）。
- **为什么是 640×480**：抓帧读回成本随像素面积线性（960×720 = 7.69 ms 实测）；640×480 约 3.4 ms、480×360 约 1.9 ms（按面积推算，未直接实测）。死亡带是"被 VHS 滤镜盖住的回放画面"，640×480 上采样到 1920×1440 完全够；若真实游戏里 3.4 ms 吃紧，再降 480×360。F5 录制仍用 960×720（用户要的录屏观感）。
- **采样规则**：不存全帧。设 `u` = 该帧距离死亡的秒数，`speed(u)` = 回放到该处时的倍率（见 §2.3 式 3）：

  ```
  Δt(u) = max(1/60, speed(u)/60)         # 单位：游戏秒；speed(u) = 1 + 60·(r−1)·max(0, u − D_A)
  ```

  即最近段按 60 Hz 上限（实际采集档 = F5 时 60 Hz / 只有死亡带时默认 30 Hz），越远越稀。按 `r = 1.04`、含 0.5 s 慢放前缀的连续采样，帧数：

  | D（一局秒数） | 10 | 30 | 60 | 120 | 180 | 300 |
  |---|---:|---:|---:|---:|---:|---:|
  | 入库帧数（含钉住的原点帧） | 104 | 133 | 151 | 168 | 179 | 192 |

  工程上也可以直接用「静态档位」近似：0→0.38 s @60 Hz、0.38→0.79 s @60、0.79→1.62 s @30、1.62→3.29 s @15、3.29→6.62 s @7.5、之后每档再减半（每档约 25 帧上限、427 s 内共约 273 帧）。静态档位比连续规则多约 30~40% 帧数，但实现更简单。
- **上限与淘汰**：`RING_MAX_FRAMES = 320`、`RING_MAX_BYTES = 24 MB`；超限时从**最老**的一端再抽稀一半（保留钉住的原点帧与最近死亡帧）。
- **帧纹理**：回放时 worker 预解码 2~3 帧，主线程用 4~6 张 `ImageTexture` 循环 `update()`；不要每帧新建纹理。
- **清空时机**：`restart_single()` 开头、`Level0._exit_tree()`、回主菜单/切场景；死亡带与 F5 的 FileSink 各自独立清。
- **体积**（640×480 JPEG，按 960×720 实测 30~74 KB/帧 × 面积比 0.44 ≈ **13~33 KB/帧**）：192 帧 ≈ **2.5~6.3 MB**；320 帧上限 ≈ **4.2~10.5 MB**。纯内存完全可接受，且没有写盘抖动、SSD 寿命与孤儿文件问题。

### 2.3 加速曲线（核心）

记显示帧率 `f_d = 60`，第 `i` 个显示帧吃掉**游戏时间** `step_i`：

```
step_i = step_0 · r^i,     step_0 = 1/60, r = 1.04
D = Σ step_i = step_0 · (r^N − 1)/(r − 1)          …(1)
T = N / 60                                          …(2)
```

关键性质：倒带已倒回的秒数 `u` 满足 `speed(u) = 1 + (r−1)·u/step_0`，即**倍率线性于"已倒回的游戏秒数"**；这也让抽稀规则可以写成闭式（§2.2）。

**推荐变体**：0.10 s 死亡定格 → 0.50 s 慢放（0.5×→1× 线性，吃掉 `D_A = 0.375` 游戏秒）→ 几何加速段覆盖 `D − D_A` → 0.10 s 原点定格 → 转场。

| D（s） | 几何段帧数 | 演出总长（含定格/慢放） | 死亡→可操作（含 0.43 s 转场） | 结束倍率 |
|---:|---:|---:|---:|---:|
| 10 | 82 | 2.07 s | **2.50 s** | 24.0× |
| 30 | 110 | 2.53 s | **2.96 s** | 71.9× |
| 60 | 127 | 2.82 s | **3.25 s** | 140.0× |
| 120 | 145 | 3.12 s | **3.55 s** | 283.7× |
| 300 | 168 | 3.50 s | **3.93 s** | 699.1× |

- **精确落点**：`N = ceil(ln(1 + D·(r−1)/step_0)/ln r)`；若要求最后一帧精确落在原点，固定 `N` 反解 `r`：解单调方程 `(r^N − 1)/(r − 1) = D/step_0`（二分 60 次），每局死亡时算一次。
- **3.5 s 上限**：`r = 1.04` 恰好用满 3.5 s 的临界 `D ≈ 303 s`（约 5 分钟）；`D > 303 s` 时反解 `r` 自动上调（最多约 1.048），演出总长钉在 3.5 s。若觉得偏长，可改 `r = 1.05`（300 s 局 → 3.03 s）或缩短慢放/转场。
- **为什么不选别的**：恒速跨局不稳定（10 s 局 2.9×，300 s 局 85×）；幂函数 ease-in 起步速度趋 0，会"卡住"；双指数先猛后缓，和"起步看得清、结尾不拖"相反；分段常速只是几何级数的离散近似，边界有可见跳变。
- **退化**：`D < 2.5 s`（刚出生就死）不播倒带，用 0.35 s「假倒带」（当前帧 + 最强 VHS/底片/噪声，无帧推进）→ 白闪 → 重开；带子不足 8 帧同样走假倒带。

伪代码（缩短版；完整调度见 `.tmp/rec/rewind-design.md`）：

```gdscript
const STEP0 := 1.0 / 60.0
const R_BASE := 1.04
const T_HIT := 0.10
const T_A := 0.5
const V_A0 := 0.5
const D_A := T_A * (V_A0 + 1.0) * 0.5      # 0.375
const T_C := 0.10
const T_SHOW_MAX := 3.5

func begin_tape(run_seconds: float) -> void:
    D = run_seconds
    if D < 2.5: _play_fake(0.35); return
    var body := D - D_A
    var n := ceili(log(1.0 + body * (R_BASE - 1.0) / STEP0) / log(R_BASE))
    n = mini(n, int((T_SHOW_MAX - T_HIT - T_A - T_C) * 60.0))   # 168
    r = _solve_r(body, n)          # 二分：u(n) = body 精确
    tape = ring.freeze()           # 按 age 升序，最后一帧 = 钉住的原点帧
    _cursor = 0

# 每显示帧（_elapsed 从死亡瞬间起算）
func _process(delta: float) -> void:
    _elapsed += delta
    if _elapsed < T_HIT: _show(tape[0]); return
    var tau := _elapsed - T_HIT
    var u: float
    if tau < T_A:
        var a := tau / T_A
        u = T_A * (V_A0 * a + 0.5 * (1.0 - V_A0) * a * a)
        speed = lerpf(V_A0, 1.0, a)
    elif tau < T_A + n / 60.0:
        var nf := (tau - T_A) * 60.0
        u = D_A + STEP0 * (pow(r, nf) - 1.0) / (r - 1.0)
        speed = pow(r, nf)
    else:
        _hold_origin(); return
    while _cursor + 1 < tape.size() and tape[_cursor + 1].age <= u:
        _cursor += 1
    _show_blend_or_frame(tape, _cursor, u, speed)
```

### 2.4 帧率：回放显示 60 fps，采集分层

- **回放显示 60 fps**：每个显示帧至少有一张采集帧可显示即可。倍率 `v` 时一个显示帧推进 `v/60` 游戏秒，因此采集帧间隔满足 `Δt ≤ v/60` 就不会看到重复帧顿挫——这就是 §2.2 的抽稀公式。
- **F5 录制 60 Hz；死亡带默认 30 Hz**：慢放段 0.5× 用最近 0.375 游戏秒的帧；30 Hz 源在 0.5× 播放时每张显示 2 帧、运动观感是 30 fps，叠 VHS 噪声后基本可接受，作为默认档。若真实游戏有预算余量，再升到 60 Hz（慢放更顺）。
- **数据量结论**：300 s 一局约 192 帧（连续规则）/约 273 帧（静态档位），而不是"全程 60 fps 存 18000 帧"。**帧率要求的关键不是 60 fps 存储，而是 60 fps 回放显示 + 按倍率抽稀（最近段最密）+ F5 的 60 Hz 采集。**

### 2.5 滤镜与视觉效果

美术方向：青灰砖 + 亮青天空（`PostProcess` 的 `SKY_DAY = #a5d5e6`），像素风；倒带只在这个色域里做旧，**不要**高饱和赛博风。所有噪声/扫描线按采集帧像素网格对齐。

**强度统一由 `x = clamp(log2(v)/log2(512), 0, 1)` 驱动**（v = 当前倍率；v=1 时 x=0，v≥512 时 x=1）：

| v（×） | blur_px（横向拖影） | chroma_px | 扫描线 | 噪点 | tracking | 暗角 | 底片 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 0.0 | 1.0 | 0.10 | 0.020 | 0.25 | 0.30 | 0.45 |
| 4 | 1.4 | 2.6 | 0.15 | 0.042 | 0.42 | 0.37 | 0.56 |
| 16 | 2.8 | 4.1 | 0.20 | 0.064 | 0.58 | 0.43 | 0.67 |
| 64 | 4.2 | 5.7 | 0.25 | 0.087 | 0.75 | 0.50 | 0.78 |
| 256 | 5.6 | 7.2 | 0.30 | 0.109 | 0.92 | 0.57 | 0.89 |
| 512+ | 6.0 | 8.0 | 0.32 | 0.120 | 1.00 | 0.60 | 0.95 |

逐项：

- **VHS/磁带**：桶形畸变（复用 `post_process.gdshader` 的 `r' = r(1+k r²)` 公式，回放用 k≈0.28）；垂直滚动 roll（`fract(uv.y + roll)`，低频 + 每 0.3 s 一次尖峰）；逐行抖动（每行 hash 横移 1.2 px）；跟踪带（一条随时间下移的带，带内横抖 ×40 px、色差 ×2、提亮、加噪）；head-switch 底带（画面底部 3% 剧烈抖动/亮线）；RGB 色差（`chroma_px`，换算口径同 `loan_aberration`：`off_px / tape_px.x`）；chroma bleed（R/B 水平 5-tap 模糊、亮度保持锐利）；扫描线（3 px 周期，像素对齐）；噪点（hash，冷暖平衡，不加彩噪）；dropout 白线（每行 hash 命中，混向冷白 `vec3(0.92,0.97,1.0)`）；暗角（半径口径同 `post_process.gdshader` 的 `dist/0.75`）。
- **速度驱动**：相邻采集帧混合（权重 `w = (u−a0)/(a1−a0)`，只在 `gap ≤ 2·speed/60` 时启用，天然产生方向正确的运动模糊；高速段禁用，避免糊成灰块）；横向 `blur_px = clamp(0.7·log2(v), 0, 6)`（只做 3-tap，不做全屏高斯，mobile 渲染器上太贵）；高速段整体提亮 `glow_boost`。
- **色彩**：底片化复用 `rewind_film` 的公式（`inv = 1−c`；`film = mix(inv, gray(inv), 0.25)`），慢放段从 0 ramp 到 0.45；`desat ≈ 0.35`；冷青乘性 tint `vec3(0.88,0.95,1.02)`（三通道都 ≤1.05，避免砖"发光"）；抬黑位 `col = 0.12 + 0.88·col`，模拟磁带底噪；末段 `flash` 到 0.9。
- **UI**：`◁◁`（复用 `TimeSymbolHud` 的符号/配色，PixelFont 64 px，亮度 0.75+0.25·sin(9t)）；`REWIND` 字样（40 px、冷白、8 px 深色描边、随速度 ±1 px 抖动）；时间码 `mm:ss.d / mm:ss.d`（左下）；倍率读数 `×17.2`（右下）；底部 6 px 进度条；`● REC` 常显（前几次死亡）或只在回放期显示 `◁◁ PLAY`。
- **转场**：原点定格 0.10 s 内白闪升到 0.9 → 白场 0.10 s → 黑场 0.18 s，黑场中 `restart_single.call_deferred()` → 0.25 s 淡入，恢复 HUD/音频。
- **音频**：死亡瞬间低频轰鸣 + Music duck；慢放段磁带 whirr 渐入（`pitch 0.6→0.9`）；加速段 whirr 音高随 `x` 升；原点定格"咔哒"；白闪全静音 0.05 s；重开 Music 淡回。磁带声建议用专用常驻 `AudioStreamPlayer` 循环播放（`Sfx` 是程序化生成短样本，零素材），并设 `PROCESS_MODE_ALWAYS`。

**着色器骨架（新建 `core/present/rewind_tape.gdshader`，不要改 `post_process.gdshader`）**：挂在一个全屏 `ColorRect` 上（回放层），两张 `ImageTexture` 分别绑当前帧/下一帧：

```glsl
shader_type canvas_item;
uniform sampler2D tape_tex : filter_linear, repeat_disable;
uniform sampler2D tape_next_tex : filter_linear, repeat_disable;
uniform vec2 tape_px = vec2(960.0, 720.0);
uniform float progress : hint_range(0.0, 1.0) = 0.0;
uniform float speed = 1.0;
uniform float speed_norm : hint_range(0.0, 1.0) = 0.0;
uniform float frame_seed = 0.0;
uniform float blend : hint_range(0.0, 1.0) = 0.0;
uniform float tape_time = 0.0;
uniform float film : hint_range(0.0, 1.0) = 0.0;
uniform float desat : hint_range(0.0, 1.0) = 0.35;
uniform float chroma_px = 2.0;
uniform float chroma_bleed : hint_range(0.0, 1.0) = 0.35;
uniform float scan_alpha : hint_range(0.0, 1.0) = 0.18;
uniform float noise_amt : hint_range(0.0, 1.0) = 0.06;
uniform float dropout : hint_range(0.0, 1.0) = 0.15;
uniform float tracking : hint_range(0.0, 1.0) = 0.40;
uniform float tracking_height : hint_range(0.01, 0.4) = 0.10;
uniform float roll = 0.0;
uniform float wobble_px : hint_range(0.0, 6.0) = 1.2;
uniform float head_switch_h : hint_range(0.0, 0.15) = 0.03;
uniform float barrel : hint_range(0.0, 0.5) = 0.28;
uniform float vignette : hint_range(0.0, 1.0) = 0.45;
uniform float flash : hint_range(0.0, 1.0) = 0.0;
uniform vec3 tape_tint : source_color = vec3(0.88, 0.95, 1.02);
uniform float contrast_lift : hint_range(0.0, 0.5) = 0.12;
uniform float glow_boost : hint_range(0.0, 0.5) = 0.0;

float hash21(vec2 p) { return fract(sin(dot(p, vec2(127.1, 311.7))) * 43758.5453); }
float luma(vec3 c) { return dot(c, vec3(0.299, 0.587, 0.114)); }

vec2 barrel_uv(vec2 uv, float k) {
    vec2 c = uv - 0.5; float r = length(c);
    return c * ((r * (1.0 + k * r * r)) / max(r, 1e-4)) + 0.5;
}

vec3 sample_frame(vec2 uv) {
    vec3 a = texture(tape_tex, clamp(uv, vec2(0.0), vec2(1.0))).rgb;
    if (blend <= 0.001) return a;
    vec3 b = texture(tape_next_tex, clamp(uv, vec2(0.0), vec2(1.0))).rgb;
    return mix(a, b, blend);
}

void fragment() {
    vec2 uv = barrel_uv(UV, barrel);
    uv = vec2(uv.x, fract(uv.y + roll));
    float line = floor(uv.y * tape_px.y);
    float wob = (hash21(vec2(line * 0.07, frame_seed)) - 0.5) * wobble_px / tape_px.x;
    float band_y = fract(tape_time * 0.09 + 0.31);
    float band = tracking * smoothstep(tracking_height, 0.0, abs(fract(uv.y - band_y + 0.5) - 0.5));
    wob += band * (hash21(vec2(line, frame_seed + 3.0)) - 0.35) * 40.0 / tape_px.x;
    vec2 suv = uv + vec2(wob, 0.0);
    float cx = chroma_px / tape_px.x;
    vec3 cen = sample_frame(suv);
    float cr = sample_frame(suv + vec2(cx, 0.0)).r;
    float cb = sample_frame(suv - vec2(cx, 0.0)).b;
    vec3 col = vec3(luma(cen)) + (sample_frame(suv + vec2(cx * 2.0, 0.0))
            + sample_frame(suv - vec2(cx * 2.0, 0.0)) - vec3(2.0 * luma(cen))) * chroma_bleed;
    col.r = mix(col.r, cr, 0.5);
    col.b = mix(col.b, cb, 0.5);
    if (mod(line, 3.0) < 1.0) col *= 1.0 - scan_alpha;
    float n = hash21(floor(uv * tape_px) + vec2(frame_seed * 7.13, frame_seed * 3.7));
    col += (n - 0.5) * noise_amt;
    col = mix(col, vec3(0.92, 0.97, 1.0),
            step(1.0 - dropout * 0.02, hash21(vec2(line * 0.13, frame_seed))) * 0.85);
    vec3 inv = vec3(1.0) - col;
    col = mix(col, mix(inv, vec3(luma(inv)), 0.25), film);
    col = mix(col, vec3(luma(col)), desat);
    col *= tape_tint;
    col = col * (1.0 - contrast_lift) + contrast_lift;
    col += vec3(0.05, 0.075, 0.10) * glow_boost;
    float vr = clamp(distance(UV, vec2(0.5)) / 0.75, 0.0, 1.0);
    col *= mix(1.0, 1.0 - vignette, vr * vr);
    col = mix(col, vec3(0.97, 0.99, 1.0), flash);
    COLOR = vec4(clamp(col, vec3(0.0), vec3(1.0)), 1.0);
}
```

> 完整骨架（含 head-switch、跟踪带噪声、逐项说明）在 `.tmp/rec/rewind-design.md` §3.4；本文节选已覆盖主结构。滤镜强度由 GDScript 按上表算好再推 uniform，保证画面/声音/读数同步。

### 2.6 UX 时间线

以死亡瞬间为 0：

| 区间 | 内容 |
|---|---|
| 0–0.10 s | 死亡定格：画面停住 + 红闪（复用 `PostProcess.flash_hit()`）+ Music duck + 输入锁定 |
| 0.10–0.60 s | 慢放段 0.5×→1×；底片 0→0.45；VHS 渐入；`◁◁` + `REWIND` 出现；时间码 = D |
| 0.60–T1 | 几何加速段；强度按 §2.5 表走；时间码跑到 0 |
| T1–T1+0.10 s | 原点定格：显示钉住的原点帧，VHS 最强，白线扫过，磁带停转 thunk；`flash` 升到 0.9 |
| 之后 0.10 s | 白场保持 |
| 之后 0.18 s | 黑场；黑场中调 `restart_single.call_deferred()` |
| 之后 0.25 s | 从黑淡入；HUD/音频恢复；清空带子并重新钉原点帧 |

- **跳过**：演出前 0.30 s 不可跳（防误触），之后 `R`/`Space`/左键任一按下即进入转场；跳过仍然调用 `restart_single`、仍然清带子。
- **暂停/切场景**：回放期间建议 `get_tree().paused = true` 冻结世界，叠加层与音频节点设 `PROCESS_MODE_ALWAYS`；`Esc` 是否允许开暂停菜单由产品定（若允许，暂停时冻结演出计时）。`_exit_tree()` 里必须恢复 `paused`、`Sfx.pitch_mult`、Music 音量并清纹理。
- **不追帧**：演出按真实 `delta` 走；掉帧就慢一点，保证最后一帧落点准确。

### 2.8 风险清单（照直觉接会静默错）

1. **`combat.went_down` 会在"状态回溯穿过倒地帧"时也发**（`combat_component.gd:97` 的 `set_downed_by_rewind(true)` 也会 emit）。直接接它会在正常按 Shift 回溯时误播死亡倒带。用轮询 `is_downed()` 上升沿，或加 `hp <= 0 and not is_rewinding()` 判据。
2. **`restart_single()` 不清 `WorldRewind` 磁带**：重开后立刻按 Shift 会倒回上一世（既有 bug，新功能会放大）。建议单独一支修，不要混进录屏改动。
3. **录制起点不能早于加载完成**：否则带子开头是加载遮罩/黑屏。起于 `hide_loading()` 之后、玩家可见第一帧。
4. **不能缓存节点/视口引用**：`safe_change_scene` 先 `add_child(next)` 再 `remove_child(old)`，旧世界由 reaper 逐帧 `free()`；缓冲只存 `Image`/`PackedByteArray`，用时现场取 `$WorldViewport`。
5. **不要用 `Engine.time_scale`**（仓库硬规则）：回放用独立时间轴 + `get_tree().paused`。
6. **headless 抓帧会打引擎 ERROR**：服务在 headless 下必须早退，避免污染 CI 的 `grep -ci error`。
7. **`record/` 落盘要判 `Error` + 回退 + 打印最终路径**；文件名手拼，不要冒号、不要 `RegEx`（导出包裁剪）。
8. **模板/CR 口径要统一**：当前发行模板有 JPG，仓库 profile 写着关 JPG；两者必须二选一（见 §4），否则实现完成、发布重编模板时录屏静默失效。
9. **HUD 进画面**：默认抓最终画面，HUD/击杀特效/加载遮罩都会被录进去；死亡后的去饱和灰屏也在里面（剪辑点必须卡在死亡帧）。可接受就先做；要"干净画面"再上 WorldViewport + 重跑后处理（成本高，见 §4）。

## 3. 与普通录屏共用通道

```
CaptureSource（唯一抓帧点，60 Hz 上限，960×720 抓帧视口 → Image；死亡带再缩 640×480）
   │  CaptureFrame { t_run, image }      # t_run = 局内秒，自己累加
   ▼
Encoder（worker，JPEG q0.80；也可 PNG 退路）
   │  EncodedFrame { t_run, blob }
   ├────────► FileSink   （F5：落盘 record/<时间戳>/，仅在录制中收帧）
   └────────► RingSink   （死亡带：按 Δt(u) 抽稀，纯内存，含钉住原点帧）
```

- `CaptureSource` **只抓一次**；两个 sink 按需各自 resize/encode（同时开 F5 时可以复用同一份半分辨率 blob，避免二次编码）。
- sink 不反向控制采集；RingSink 的抽稀发生在内部，F5 的 FileSink 仍拿全率。
- 回放只依赖 `RingSink.freeze() -> Array[{age, blob}]`，不关心帧来自哪；**回放期间暂停采集**（否则下一次死亡会录到上一次的倒带）。

## 4. 实测依据与待拍板

### 4.1 已实测（本机，Godot 4.7.1 发行裁剪模板）

- 编码/并行/写盘：见 §1.2。
- **发行模板能力**：当前 `The Cyancular Ruins.exe` 用的安装模板（44,273,152 B，SHA256 `8BE181C2…`）与仓库外自编译产物逐字节相同；实测**有 JPG、有 RegEx、`MovieWriterMJPEG` 在**；仓库 `cyancular_build_profile.gdbuild` 里写的 `module_jpg_enabled:false` / `module_regex_enabled:false` **不是**当前 exe 的构建依据。
- **MovieWriter 运行时开关不可行**：`Engine` 只暴露只读的 `get_write_movie_path()`，没有 `set_write_movie_path()` / `is_movie_maker_enabled()`；`MovieWriterPNGWAV/MJPEG` 不可由脚本实例化。`--write-movie` 只能在启动时用（CLI），不能接 F5 开关。⇒ F5 必须自研抓帧/编码/封装。
- **Phase 2 真窗口实测（已补）**：
  - 主视口 1920×1440 `get_image()` = **26.11 ms**（连续录制时主线程 40~43 ms）⇒ **抓 1920 再缩的方案不成立**。
  - 抓帧成本随面积线性：960×720 = **7.69 ms**、1920×1440 = 26.96 ms、2208×1728 = 37.69 ms。
  - **960×720 抓帧视口 + 2 worker JPG → 60.01 fps、p99 17.02 ms、0 掉帧、主线程中位 7.96 ms**（探针场景，GPU 负载轻）。
  - 真实像素画风截图缩到 960×720：JPG q0.80 = **30~74 KB/帧**（Phase 1 噪声样张的 453 KB 是 6~10 倍悲观上界）；60 fps 码率 1.8~4.4 MB/s。
- **Phase 2 仍未验证**：① 真实游戏里多渲染一份 960×720 抓帧视口的 GPU 代价、以及 7.96 ms 主线程与游戏逻辑叠加后能否稳 60 fps（探针未启动真实对局）；② "SubViewport 采样 root `ViewportTexture`"这条桥的可行性/延迟；③ 1920 输出的其他抓帧路径（异步读回、960 放大）未验证。

### 4.2 待拍板（本轮不替产品定）

1. **模板/CR 口径**：保留当前模板（JPG 可用，录屏方案按 §1.2 默认）还是按仓库 profile 重编（失去 JPG ⇒ 960×720 PNG@60 或 30 fps 退路）？建议把 profile 的 `module_jpg_enabled` 改成 `true` 并记录，避免"编辑器全绿、发布版录屏静默失效"。
2. **F5 录屏分辨率/帧率**：实测本机 1920×1440 输出不可行（主视口读回 26 ms），默认 **960×720@60**；是否接受？若产品坚持 1920，需要先解决抓帧路径（异步读回/960 抓帧后放大，均未验证），可能只能 30 fps。
3. **音频**：第一期是否要录音频（`AudioEffectRecord` + WAV 封装）？
4. **倒带演出时长**：默认最长 3.93 s（死亡→可操作）；是否接受？可切紧凑档（300 s 局 3.27 s）。

6. **HUD 进画面**：默认进（所见即所得）；是否要后期做"干净世界帧"路线？
7. **是否顺手修 `restart_single` 不清回溯磁带**（既有 bug，会与新功能语义撞车）？
8. **`● REC` 常显**：只在回放期显示，还是前几次死亡常显（强化"游戏在录"的元叙事）？
9. **Platform**：Web 构建直接关闭录屏；PvP 不接死亡倒带（服务器权威复活，语义不同）。

## 5. 验收与后续实现顺序（建议）

1. **先在真实对局里验证抓帧桥与帧时间**（Phase 2 只测了探针场景）：① 在游戏内建 960×720 抓帧视口，用 `TextureRect` 采样 root `ViewportTexture`，确认抓到的是含 HUD/后处理的最终画面、最多晚 1 帧；② 开/关录制各跑同一段关卡，记录 FPS、帧时间 p99、主线程入队耗时；③ 若稳不住 60 fps，按 §1.5 降档（死亡带先降 480×360/30Hz，F5 降 800×600 或 30 fps）。**这条不通过就不实现。**
2. **纯逻辑先行**：把曲线、抽稀、环形淘汰、时间轴拆成不依赖 Node/GPU 的 `RefCounted`（如 `core/present/record/rewind_tape.gd`），用 `tests/smoke/*.gd`（`-s`、不实例化 autoload）断言：帧数上限、淘汰顺序、`D→N→r` 复算、末帧落点、清空后状态。按仓库纪律写 `EXPECTED_CHECKS` 条数闸。
3. **实现采集/编码/封装**：先在编辑器里跑（落 `record/`），再用发行 exe 冒烟（确认 JPG/路径/权限）。
4. **最后接倒带演出**：叠加层 + shader + 闸门 + `restart_single` 时序；只在单机生效。
5. **人眼验收项**（headless 够不到）：慢放段可读性、加速段是否糊成一片、末帧是否精确回到出生点、暂停/切场景不残留、连续死亡不套娃。

### 6.2 实测结果（真实 Level0，真窗口，RTX 3060 Laptop / 20 逻辑核）

> ⚠ 本节 2026-11-06 快照已被 §0.1 取代；下面是 2026-11-12 升级后的实测。

- **抓帧**：直读 root 视口 1920×1440（1:1，无桥、无缩放），单次读回 mean 9.8 / p99 12.5 ms。
- **F5 录屏（含倒地→倒带→重开，CRF16=升级前默认）**：整段 8.15 s，`is_recording()` 全检查点为 true；输出 `record/rec_<时间戳>/clip.mp4`（AVI/WAV 成功后删除）；`ffprobe`：`h264 High / 1920×1440 / yuv420p / 30 fps / 244 帧 / 8.133 s / 15.2 Mbps` + `aac LC / 48000 Hz / 立体声 / 8.128 s / 141 kbps`；整段游戏帧率 mean 54.3 fps、帧 p99 24.0 ms。抽帧 vs 游戏内 PNG：PSNR 43.3 dB / MAE 1.15/255（旧 960×720 q0.80 管线模拟 PSNR 35.4 dB）。体积对比见 §0.1「体积/码率」。
- **音频非静音**：探针起录即播 440 Hz 固定音 + Sfx explosion/hurt/kill；成片 `volumedetect mean_volume = -19.0 dB / max_volume = 0.0 dB`、`astats RMS = -19.0 dB`（AAC 码率 141 kbps，不是静音流的 ~5 kbps）。
- **回退路径**：模拟 ffmpeg 不存在（`Recorder._ffmpeg = ""`）录 1.2 s ⇒ 保留 `clip.avi`（mjpeg 1920×1440/30fps/36 帧）+ `clip.wav`（pcm_s16le 48k 立体声，`volumedetect -25.1 dB`）、无 mp4、进程不崩。
- **死亡带空载**：只开 30 Hz / 640×480 内存带、不录 F5，实测 **60.00 fps**。
- **倒带**：用真实输入路径模拟倒地后按 R → `Recorder._input` 拦截 → 回放启动；演出结束自动 `restart_single()`，结果 `paused=false`、玩家复活、位置回到出生点；录制跨回放/重开不中断。
- **独立验收（Lead 另写探针复测，默认 CRF22）**：同一流程录 9.96 s，单 mp4 **2.87 MB（16.5 MB/min）**；`ffprobe` 298 帧 / 9.933 s / 30 fps / 2.28 Mbps + `aac 48 kHz 立体声 / 9.962 s`；暂停冻结帧（直接截屏 PNG）vs mp4 同帧 **PSNR 42.2 dB / SSIM 0.998**；两处 1 kHz 蜂鸣在成片音轨的起点偏差 **-14 ms / +1 ms**；抽看 6 帧确认画面覆盖「开打 → 死亡白闪 → REWIND 回放 → 重开后玩法」无断档。同一验收流程在 CRF16 下为 8.2 MB / 7.03 s（≈70 MB/min），画质仅高 0.3 dB。 |
