# 联机测试 Bot 设计规格

> 状态:待用户评审(2026-11-01 修订版)。目标:为联机模式提供一个真实的自动玩家(Bot),主要用于**测试**而非陪玩;同时考虑所有敌人与队友,采用优雅、可解释、可扩展的决策结构。本规格只定义设计与接口,不包含实施计划。
>
> **修订记录:** 2026-11-01 依仓库已落地变更同步:3v3 → 对抗模式(2~10 人、补贴规则)、出生/复活点改为地图数据按阵营半区、自动上台阶、环面相机连续空间跟随、客户端组合件重构(ReplicaSet / InputUplink / ReconnectDriver 等)、对抗模式无 AI 补位。

## 1. 目标与定位

- **首期目标 = 测试优先**:Bot 替代真人多开,自动把一段真实联机对局“玩起来”,持续制造移动、交火、死亡 / 复活等事件,用于暴露联机问题。
- **Bot 是操作员,不是裁判**:Bot 负责把真实玩家行为做出来;对局是否通过由独立的测试裁判依据客户端与服务端证据判定。
- **不作为陪玩优先**:首期的验收不以“像不像人”“好不好玩”为准;拟人化难度配置放在后期。
- **不以新增冒烟数量为交付物**:优先证明 Bot 能完成真实对局并给出可复现、可解释的行为证据;少量承重守卫保留,但不把守卫数量当成果。

### 成功判据(首期)

1. 一个或多个真实客户端 Bot 能通过正常联机链路(大厅 → 匹配 → worker 对局)进入对局。
2. Bot 通过**客户端输入注入**参与对局:移动、跳跃、攀爬、瞄准、开火、换弹、切换 / 拾取武器。
3. Bot 感知受限:只使用“主画面 + 小地图 + 记忆”可获得的信息,决策层不直接持有远端节点 / 原始快照 / 服务器真值。
4. Bot 同时考虑所有可感知的敌人与队友(敌我识别、威胁、支援、站位),而非追最近单一目标。
5. 行为可解释:能记录“看到了谁、为什么选这个行动、为什么放弃上一个行动”,且能区分 Bot 自身失败(寻路 / 操作)与联机异常。
6. 故障可复现:支持自由对局 + 定向场景任务 + 跨端证据,能稳定触发指定行为并报告是否真正触发。

## 2. 范围与边界

### 当前联机模式事实(2026-11-01)

模式 id 仍是 `pvp` / `royale` / `team`;显示名为 **1v1 / 大乱斗 / 对抗**。权威定义在 `core/mp/mode_defs.gd`,数值规则在 `core/mp/team_rules.gd`。

| 模式 | 人数 | 开局条件 | 关键差异 |
|---|---|---|---|
| 1v1(`pvp`) | 2 | 两人就绪 | 固定单副本,回合制击杀目标 5 / 赢 2 局 |
| 对抗(`team`) | 总 2~10,每队 1~5 | 两队各 ≥1 人 | 有比分 / 血量 / 伤害补贴;换边;队友子弹穿透、爆炸对队友满效;有助攻与队伤惩罚 |
| 大乱斗(`royale`) | 2~16(含 AI 补位) | 房主开始 | 归因制计分;无回合;**唯一仍有服务端 AI 补位**的模式 |

- **对抗模式无 AI 补位、无降级**;服务端 AI 补位(`AiInputSource` + `AiNavigator`)只在大乱斗经 `royale_start_ai` 启用。
- 对抗不因人数变化重算目标与补贴(开局快照);掉线判据是整队走光才终局。

### 首期建设范围

- 三种模式统一建模。1v1 只是人数较少的情形,不复写另一套决策。
- 决策体系:效用评分 + 分层行为树 + 独立动作执行器。
- 真实客户端接入主链路。现有服务端补位 Bot **不用于端到端验证**,但共享可复用的几何与关系规则。
- 可复用现有真链路观察者形态:`tests/harness/team_match_watcher.gd`(挂 root、跨换场存活、每物理帧写脚本手柄)+ `tests/harness/team_bot_input.gd`(哑手柄,真实 `PlayerInput` 子类)。首期按同样形状演进,而不是另起一套。

### 明确不做(首期)

- 不做通用行为树编辑器或可视化工具。
- 不做学习 / 调参系统。
- 不做拟人化陪玩难度配置(反应延迟、失误率等)作为首期主目标。
- 不读取全局真值喂给 Bot 决策;白盒 / 故障注入场景与正常游玩能力分开,不混算。
- 不为每个行为树节点各配一支冒烟测试。

## 3. 核心架构

**数据流(单向):**

```
客户端呈现状态 → 感知过滤(主画面 + 小地图) → 观察记忆
→ 局势评估(敌我 / 威胁 / 支援 / 风险) → 行为树(优先级组织)
→ 动作执行器(组合移动 / 瞄准 / 武器) → 正常玩家输入
```

**关键约束:** 决策层**不持有**远端玩家节点、原始快照、服务器对象;只消费经过过滤的**观察记录(Observation)**。否则即使实现了视野过滤,某个行为随手读角色坐标就会让限制形同虚设。

客户端侧可用入口(2026-11-01 结构):

- 远端角色 = `PlayerReplica` 副本,由 `scenes/mp_client/replica_set.gd` 懒建 / 消费世界快照 / 维护头顶标签。
- 输入上行 = `core/net/input_uplink.gd`(seq / 30Hz 流水线 / 发包 / ack / netstat),由 `PvpMatchClient` 驱动。
- 本地玩家输入源 = `PlayerInput` 子类(Local / Packet / AI 三种 `Kind`);注入脚本手柄的既有范本是 `tests/harness/team_bot_input.gd`。

### 3.1 观察的三个来源

| 来源 | 允许知道什么 | 主要用途 |
|---|---|---|
| 主画面 | 画面实际呈现的位置、动作,及设置允许显示的信息 | 瞄准、交战、判断眼前威胁 |
| 小地图(雷达) | 雷达范围内点位与颜色所表达的**关系**(敌我、相对方位、侧翼) | 接敌、支援、发现侧翼、选择移动方向 |
| 历史记忆 | 过去观察、观察时间、估计不确定性 | 搜索失联目标、短时预测 |

**约束:**
- 小地图看到一个点,不等于知道该角色血量、武器、换弹状态、精确动作。
- 雷达信息的位置带尺度误差(按雷达显示尺度表达),不把底层世界坐标当无限精度信息。
- 速度只能由**连续观察估计**,不能从原始快照顺手取。
- 若雷达颜色不足以区分同队个体,追踪关联允许不确定,不能凭底层 role 自动获得稳定身份。
- 关闭小地图或关闭敌方点位设置后,Bot 不能继续偷用雷达信息。
- 无窗口测试运行使用明确的视口与设置配置,不以 headless 名义扩大视野。

### 3.2 观察记录字段

- 身份(可确定时)或临时追踪编号;
- 信息来源:主画面 / 雷达 / 记忆;
- 敌我关系(必须来自 `match_sync` 的 `teams` / 模式,不从 role 号推导);
- 观察位置、观察时间、位置不确定性;
- 由观察估计的速度与可信度;
- 确实观察到的动作 / 装备等可选字段(可选字段没有观察到必须为“未知”,不能用默认值冒充已知)。

### 3.3 共享可见性规则层(不复制粘贴)

不能让 Bot 去读小地图的 `ColorRect`,也不应在 AI 里另抄一份半径常量。提取一个**薄规则层**,UI 与 Bot 共用同一份规则:

- **摄像机规则**:依据实际世界视口、摄像机变换(缩放 / 偏移 / 死区)与环面副本判断是否入画;不使用操作系统窗口物理像素。
- **雷达规则**:统一半径、开关、环面距离、点位显示资格。
- **关系规则**:依据实际模式与队伍表判定敌我;不从 role 编号猜测。
- **信息规则**:规定各来源能暴露哪些字段。

当前事实(仅作写规则的输入,不改 UI 行为):

- 主摄像机 `cam_zoom` / `cam_y_bias` / `cam_lookahead_x` / `cam_deadzone` 决定实际视野;相机自 2026-11 起在**连续(未取模)空间**做死区与指数平滑跟随,真实传送(复活 / 回退 / 换边)按 `SNAP_DIST` 重锚。见 `core/present/camera_2d.gd`。
- 小地图是玩家为中心圆形雷达,半径 50 格,敌人点按环面最短距离筛选、不查墙体遮挡;3v3 点位来自客户端副本并带队色。见 `ui/hud/minimap.gd`、`scenes/team_game.gd`。设置键 `pvp_show_minimap` / `pvp_minimap_show_enemy`。
- 墙体遮挡只参与**射击通路**与**移动可达性**判断,不剥夺“画面内感知”。三者须分开:

| 概念 | 定义 | 用途 |
|---|---|---|
| 感知范围 | 角色是否出现在当前视口 / 雷达(含环面副本) | 知道哪些敌友的位置与动作 |
| 射击通路 | 按具体武器判断墙体 / 地形是否阻挡攻击 | 决定能不能打、用什么武器打 |
| 移动可达性 | 能否通过行走 / 跳跃 / 攀爬等到达 | 决定追击、支援与转移路线 |

### 3.4 移动能力(2026-11-01 新能力)

- 自动上台阶:`core/sim/step_jump.gd` 的 `StepJump` 已把 ≤1 格(4 个 16px 子格)台阶处理成“矮台阶直接迈上 / 中台阶自动起跳 / 高于 1 格不跳”,且**客户端预测与服务器重放同一份判据**。
- 含义:Bot 的移动决策不必再为矮台阶单独判断,但**高于 1 格的障碍仍需自主跳跃 / 攀爬 / 绕行**;跳跃初速若需匹配台阶高度,用 `jump_velocity_for_height`(与两端同一重力常量)。
- 出生 / 复活点自 2026-11 起由地图数据决定(`.cyrm` 的 `# respawn 1|2`,按阵营半区:侧 1 左半 / 侧 2 右半),对抗每局按 `_side_swap_round` 换边;大乱斗从两侧并集取。Bot 的“我在哪一侧、队友在哪一侧”应来自实际出生点与队伍表,不假设固定方位。

## 4. 决策结构

不是把所有东西塞进一棵巨树,而是**小主树 + 职责明确的子行为 + 统一执行器**。

### 4.1 主行为树(按优先级)

1. **不可行动**:开局倒计时 / 倒地 / 结算 → 清空输入、等待。
2. **紧急风险** → 紧急规避、离开危险位置。
3. **当前动作脱困**:卡住、路径失效重规划、目标失效退出。
4. **执行当前战术**:交战 / 支援 / 转移 / 撤离 / 换弹 / 拾取(由候选行动评分产出)。
5. **搜索接敌**:前往最后观察位置或雷达接触区域进一步观察。

### 4.2 战术评估器(效用评分,综合所有敌友)

候选行动按**收益 − 成本**评分:

| 候选 | 主要收益 | 主要成本 |
|---|---|---|
| 攻击敌人 X | 有效攻击机会 | 暴露风险、接敌成本 |
| 支援队友 Y | 缓解队友压力、有利交战 | 赶路成本 |
| 转移到位置 P | 改善射程 / 视线 / 掩体 | 沿途威胁 |
| 撤离 / 换弹 | 降低死亡风险 | 放弃攻击的代价 |
| 拾取武器 W | 改善装备 | 绕路、暴露成本 |

**目标选择与站位选择相互校验**:不能“评分觉得这个敌人最好打,执行才发现没有可达的射击位置”。

### 4.3 满足“同时考虑所有敌人与队友”

每次战术决策先构造统一的**局势摘要**,再由评估器综合:

- 每位可感知敌人的相对位置、速度、视线、可达成本,对自己与对队友的威胁。
- 队友位置、移动趋势、交战区域;能否形成支援而不扎堆;是否堵路 / 堵射击线。
- 当前模式下的规则:对抗模式队友子弹穿透、爆炸对队友满效、队伤计入惩罚;大乱斗归因制、无队友;1v1 单对手。
- 对抗补贴只影响“打多久 / 谁血厚”,不改变决策结构:少人方更该避免被集火、拉长交换。
- 全局威胁分布、可通行路线、掩体、撤离方向、可拾取武器;自身弹药 / 换弹 / 姿态 / 脱困能力。

**关键差异:** 攻击目标可以只有一个,但移动与风险判断必须考虑所有相关角色。

### 4.4 稳定性规则(防抽搐)

- 新方案必须**明显优于**旧方案才切换(滞回)。
- 行动有最短承诺时间;紧急风险可打断。
- 路径失败、目标失效、连续无进展 → 明确退出当前行为,不能无限 `RUNNING`。
- 移动 / 瞄准 / 武器操作由**唯一执行器**协调,不让多个行为同时争抢跳跃 / 冲刺 / 切枪输入。

### 4.5 子行为执行与取消契约

每个子行为明确:

- 进入条件、持续运行条件;
- 成功条件;
- 失败 / 无进展条件(触发退出);
- 被打断时必须释放的输入。

例“到达射击位置”:

- 路线不可达 → 返回并**暂时降低**该候选位置优先级;
- 地形变化 → 路线失效,重规划;
- 到达且具备攻击条件 → 成功;
- 出现紧急风险 → 取消,让位规避。

## 5. 测试定位与证据

### Bot 失败 vs 联机异常必须分开报告

- 寻路失败、操作失败 → Bot 自身问题。
- 客户端与服务端出现分歧、协议异常、连接异常 → 联机问题。
- 不能把寻路失败误判成联机 bug。
- 注意 `AiInputSource` 的既有教训:输入手柄若只实现无参钩子、漏了带参钩子,本地能动、服务器侧却从不跳 / 从不火,且 C2 每帧回滚;Bot 手柄必须实现**全部**读口(`team_bot_input.gd` 文件头记录了这一点)。

### 场景任务只限定目的,不给答案

- 例“完成一次跨接缝交战”可交给 Bot;把隐藏敌人实时位置塞给它则不行。
- 专门的故障注入 / 白盒场景独立标记,不与正常游玩能力混算。
- 场景未真正触发 → 报告“未覆盖 / 执行失败”,不能报通过。

### 诊断须能回答

> 它看到了谁?为什么选这个行动?为什么放弃上一个行动?卡在导航、操作,还是客户端与服务端出现分歧?

### 复现与确定性

- 固定随机种子用于控制决策随机性,但**不宣称网络对局因此完全确定性复现**。
- 自由对局用于找未知问题;定向任务用于稳定触发指定行为。

## 6. 分阶段建设顺序

| 阶段 | 主要工作 | 实际交付证据 |
|---|---|---|
| 1 | 真实客户端接入 + 输入注入;摄像机 / 雷达过滤;敌我关系;观察记忆 | 能看清 Bot 知道了什么;窗口外雷达内只获得雷达信息 |
| 2 | 导航与动作执行器:平台通路、跳跃、攀爬、跨接缝、卡住恢复;利用现有自动上台阶 | 多个客户端持续接敌,而非各自在出生点晃动 |
| 3 | 战术评分与行为树:多敌威胁、队友支援、目标与站位联合选择;对抗补贴与换边不改变结构 | 团队局与大乱斗形成持续、可解释的交战 |
| 4 | 武器与资源决策:按实际武器能力攻击、换弹、切换、拾取 | 不同武器产生不同操作,而非通用按住开火 |
| 5 | 场景编排与故障证据:自由对局 + 定向任务 + 跨端记录 | 说清场景是否触发、哪里异常;能复现问题 |

**首期从阶段 1 打通,再逐阶段交付。** 初步实施计划见 [`docs/superpowers/plans/2026-11-01-bot-preliminary.md`](../plans/2026-11-01-bot-preliminary.md)。

## 6.5 低耦合实施设计(2026-11-01)

### 依赖方向(单向,禁止回指)

```
bot_input(哑手柄)  ←  bot_watcher(唯一适配器)  →  bot_observation(纯规则)
                                                    →  bot_brain(纯决策)
```

- `bot_brain` / `bot_observation` 是 **RefCounted 纯逻辑**,不 `extends Node`、不 import 任何会话态类(`PvpSession` / `NetBus` / `MatchHost`),只吃基础类型(`Vector2` / `Dictionary` / `Array` / `float`)。
- 需要产品常量(摄像机缩放、雷达半径、队伍表、地图尺寸)时,由 **watcher 取一次作为参数传进来**,纯逻辑侧不自己读全局。
- 环面几何只复用 `core/sim/grid_pathfinder.gd` 的纯静态函数(那是几何单一来源),**不复制环面数学**,也不引 MapFormat / MazeGenerator 的会话态。
- 三个模块之间只靠**固定形状的字典**通信:
  - `Observation`:`{role, source, relation, pos, time, uncertainty, seen_action, ...}`
  - `Intent`:`{axis, jump, aim, fire, reload, switch_to, pickup, reason}`
  - 形状写进各文件头;改字段必须同批改消费方与冒烟。
- 唯一允许碰运行时对象的是 `bot_watcher`:读摄像机、本地玩家、副本、`match_sync` 队伍表,然后只把**过滤后的观察**交给 brain。

### 文件布局(首期)

| 文件 | 性质 | 是否碰产品对象 |
|---|---|---|
| `tests/harness/bot/bot_observation.gd` | 纯逻辑 | 否 |
| `tests/harness/bot/bot_brain.gd` | 纯逻辑 | 否 |
| `tests/harness/bot/bot_input.gd` | `PlayerInput` 子类(哑手柄) | 否(只实现契约) |
| `tests/harness/bot/bot_watcher.gd` | Node 适配器 | 是(唯一耦合点) |
