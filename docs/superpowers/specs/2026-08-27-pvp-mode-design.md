# CyR PvP 模式设计

日期：2026-08-27
状态：已确认（等待用户审阅）

## 0. 摘要

给「The Cyancular Ruins」加一个 **1v1 联网对战模式**。**专用服务器权威**（朋友的一台 Windows 机器，headless 跑），房间注册表支持并发对局；客户端本地模拟自己（C2）保证零延迟手感，服务器裁决一切。环面用 canonical 真值 + 各端归最近副本渲染。子弹用确定性本地模拟。对局为回合制：每局先到 10 击杀赢、三局两胜、死亡复活、局间换边。

仓库**不分裂**：共享改动做成行为不变的重构先落主线，PvP 作为包裹层新增，服务端代码放 `server/` 目录。

## 1. 目标与范围

**目标**：2 人在线 1v1 对战 demo，通过主机的朋友服务器联机，输入房间号即可加入。

**范围内**：
- 1v1 对局（服务器权威）
- 主菜单 + 匹配（建房 / 输入房间号）
- 房间注册表（一个服务器进程并发多局，上限 2~4）
- 回合制对局（每局 10 击杀、三局两胜）
- 全 5 把武器自由切换、死亡复活、击杀记分、局间换边

**范围外**（明确不做）：
- 敌人 / AI
- 观战 / 语音 / 重连 / 断线重连恢复对局
- 公网打洞（跨 NAT 直连）——本方案是"服务器在公网"模型，客户端直连服务器，无需打洞
- 反作弊、大厅 UI 以外的管理
- 房间聊天、观战席位

## 2. 关键决策

| 决策 | 选择 |
|---|---|
| PvP 形态 | 联网对战 1v1 |
| 权威模型 | **专用服务器权威**；客户端本地模拟自己（C2） |
| 服务器部署 | 朋友 Windows 机器，headless 运行；房间注册表并发（上限 2~4 局/进程） |
| 仓库策略 | 不分裂；行为不变重构先落主线；PvP 为包裹层；服务端在 `server/` |
| 环面 | canonical 真值 + 各端归最近副本渲染 + 最短路径插值；**协议只传 canonical** |
| 子弹 | 确定性本地模拟（服务器生成时掷定随机量随包发出），服务器裁决命中 |
| 对局 | 每局先到 10 击杀赢，三局两胜；死亡复活；局间换边 + 重置 |
| 武器 | 全 5 把自由切换（键 1-5） |
| 传输 | ENet（`ENetMultiplayerPeer`）+ MultiplayerAPI + RPC；手动快照包 + reliable 事件 |
| 房间号 | 服务器签发；服务器地址做成可配置默认值 |
| 测试 | 输入抽象保 `player_contract_smoke` 绿；`-s` 双进程 loopback 冒烟 |

## 3. 进程与场景结构

### 3.1 进程角色

| 进程 | 职责 | 运行方式 |
|---|---|---|
| 服务器 | 权威模拟所有房间的对局：世界/物理、两个玩家、子弹、伤害/击杀/记分/回合、地图选择 | `server_main.tscn`，`--headless` 运行 |
| 客户端 P1 | 本地模拟自己（C2）+ 渲染世界 + 远端 P2 副本 + 输入上报 + 校正 | `pvp_game.tscn` |
| 客户端 P2 | 同上（对称，无主机/客户端差异） | `pvp_game.tscn` |

**关键点**：两个客户端完全对称——没有"房主优势"、没有"主机退出=对局结束"。

### 3.2 场景流程

```
main_menu.tscn（新增，改为默认场景）
 ├─ 单人 → 直接加载 level0.tscn（现状原样，逻辑不动）
 └─ 多人 → matchmaking.tscn（新增）
       ├─ 建房：连服务器 → 请求建房 → 拿到房间号展示 → 等待对手
       └─ 输入房间号：连服务器 → 加入该房间
       └─ 双方就绪 → 服务器开始对局 → 客户端加载 pvp_game.tscn
```

- **服务器地址**：配置成默认值（朋友服务器），建房/加入时不必每次输 IP；房间号是唯一的加入凭据。
- **单人模式完全不变**：`level0.tscn`、`player.gd` 等单人代码路径不改行为。

### 3.3 客户端场景 pvp_game.tscn（包裹层）

```
pvp_game.tscn（新增，根脚本 `pvp_client.gd`）
 ├─ Level0（实例化 Level0.tscn，world-only 模式）
 │     └─ WorldViewport / WallLayer / WaterLayer / Camera2D …（渲染世界）
 ├─ 本地玩家（Player.tscn，进 WorldViewport；camera 重指向它）
 ├─ 远端副本（PlayerReplica.tscn，进 WorldViewport；视觉节点，不做物理）
 ├─ NetworkManager（新增）：连接 / RPC / 编解码 / 快照缓冲
 └─ MatchHUD（新增）：回合分数 / 倒计时 / 击杀播报
```

- **Level0 只加 `static var pvp_mode`**：`_ready()` 里世界照建（地图/碰撞/水/后处理），pvp 模式跳过"刷敌人 + 单玩家放置"。单人路径逐字节不变。`pvp_game` 先设静态标志再 `add_child(Level0)`（在 Level0._ready 前生效）。
- **远端副本 = 纯视觉节点**：复用 Player 的 SpriteFrames/动画，由快照驱动 pose/facing/position；不做 CharacterBody2D 物理（避免 set position 与物理引擎打架）。

### 3.4 服务器场景（新增服务端代码）

```
server_main.tscn / server_main.gd（新增，headless 入口）
 └─ RoomManager（server/room_manager.gd）
      └─ Match（每个房间一个，server/match_host.gd）
           ├─ WorldBuilder 建世界（地图/碰撞/水——复用，不渲染）
           ├─ Player ×2（Player.tscn 模拟，NetworkInputSource 注入输入）
           ├─ 子弹模拟 + 裁决
           └─ 回合状态机 / 记分 / 复活 / 换边
```

- 服务器**不渲染**：无 SubViewport/相机/HUD/副本节点。
- 并发上限 2~4 局/进程：每局是一个独立世界模拟（满地图 8000×4800 + 全碰撞 + 2 玩家 + 子弹），CPU 有限。
- 地图由服务器选定，发送文件名给客户端（客户端必须含同名 `.cyrm`）。

## 4. 网络协议

### 4.1 三套包

| 包 | 方向 | 频率/模式 | 内容 |
|---|---|---|---|
| 输入包 | 客户端→服务器 | 60Hz / **reliable** | 每 tick 按键状态 + just_pressed/just_released 边沿（跳跃缓冲/可变高度依赖）+ 切枪 + 瞄准世界坐标 |
| 快照包 | 服务器→客户端 | 20~30Hz / unreliable | 每玩家 pos/vel/facing/pose/weapon/hp/waterproof/downed（**canonical 坐标**） |
| 事件包 | 服务器→客户端 | reliable | hit / 击退 / kill / respawn / tile_destroyed / round_state / room 事件 |

- 输入包 reliable：60Hz × ~20B = ~1.2KB/s/玩家，LAN/服务器模型下开销可忽略，保证边沿不丢。服务器缓冲按 tick 有序消费，缺包时沿用上一 tick 输入。
- 快照包：客户端用它做**远端插值**（最短路径）和**自己校正**（与本地预测差异超阈值时修正）。

### 4.2 子弹：确定性本地模拟

- 服务器在生成子弹时**掷定所有随机量**（s686 散射角等），随生成包发出。
- 生成包：bullet id / weapon / 出生位置 / 每弹丸初速度 / 引信等。
- 两端（服务器 + 两个客户端）用确定性弹道（重力/阻力/反弹衰减 0.6/引信）**各自本地模拟**，不逐 tick 同步位置。
- 命中由**服务器裁决**，发 hit/事件包。
- 已知边界：拆墙事件延迟到达时，两端子弹轨迹会短暂分歧——可接受。

### 4.3 环面规则（核心纪律）

1. **协议只传 canonical `[0, MAP)` 坐标**，绝不在发送端锚定副本（否则两端对不上、出现凭空跳变）。
2. **模拟用 canonical 真值**（服务器 + 客户端本地玩家都跑 `wrap_to_range`）。
3. **渲染各端归最近副本**：自己 = 中间副本；对手/子弹 = `anchor_to_nearest(自己, canonical)`。
4. **插值走最短路径**：`新渲染位置 = 上一渲染位置 + toroidal_delta_px(上一渲染位置, 目标副本位置)`，绝不用 canonical 值 naive lerp（否则跨接缝整屏滑动）。
5. **校正/击退事件同样用最短路径增量**应用，不直接 set position。

**不影响的**：物理计算——碰撞解析是副本无关的（9 副本铺贴地形逐像素相同）；锚定是渲染层变换，应用在 `move_and_slide` 之后，不回喂物理。

### 4.4 输入源抽象

- `player.gd` 里直接读 `Input.get_axis/is_action_pressed/…` 的地方改为读注入的 **InputSource**。
  - `LocalInputSource` = 现状（委托真实 Input + 鼠标瞄准）。
  - `NetworkInputSource` = 消费收到的输入包（**唯一消费方：服务器上的两个玩家**）。
- `weapon_base` 的瞄准（`_aim_world_dir` 读根窗口鼠标）走 **aim provider**：本地鼠标 / 网络注入的瞄准坐标。
- 客户端自己（C2）照常读本地 Input，远端副本不读输入。所以这个抽象只在服务器侧生效，重构面很小。
- **行为不变**，`player_contract_smoke.gd` 保绿。

### 4.5 击杀归因

- 子弹携带**射手引用**（重构：bullet 知道谁打的）。
- 服务器裁决：A 的子弹导致 B 死亡 → A +1 击杀分。
- 边角规则：**溺水/自己爆炸致死不计分**（只有对方伤害致死才算对方击杀）。

## 5. 对局规则

### 5.1 回合状态机（服务器驱动，广播 round_state）

```
LOBBY（等 2 人就绪）→ COUNTDOWN → PLAYING
  → 击杀记分（每击杀 +1，播报）
  → 某方到 10 → ROUND_OVER（记分 + 换边）
  → 下一局 COUNTDOWN / 或 MATCH_OVER（某方先赢 2 局）
  → 结算 → 双方回菜单
```

### 5.2 复活

- 死亡 → 短延迟 → 在己方出生点复活：重置血量/防水/位置/武器到初始，继续刷击杀。
- 不做单人"按 R 重载场景"路径。

### 5.3 出生点与换边

- 地图解析支持 `# player`（P1）与新增 `# player2`（P2）。
- `factory_1V1(260827).cyrm` 已有 `# player 17 65`，补一个 `# player2` 出生点。
- 第 1 局随机定边，之后每局换边。

### 5.4 武器

- 双方全 5 把（手枪/步枪/m82a1/s686/榴弹）自由切换（键 1-5）。
- 切枪作为输入包的一部分上报。平衡性后续再调。

## 6. 数据流（典型时序）

1. 客户端每 physics tick：本地模拟自己（player.gd 现状代码）→ 打包输入发服务器。
2. 服务器每 tick：消费双方输入包 → 模拟双方玩家 + 子弹 → 裁决命中/击杀/拆墙 → 广播快照 + 事件。
3. 客户端收快照：对手副本**最短路径插值**渲染；自己与快照差异超阈值 → 校正（位置/血量/防水/倒地状态）。
4. 客户端收事件：即时应用伤害白闪/击退/击杀播报/回合状态，不等快照。

## 7. 共享重构清单（先落主线，行为不变，冒烟兜底）

按依赖顺序：

1. `player.gd` 输入源抽象（InputSource；Local 委托真实 Input）
2. `weapon_base.gd` 瞄准 provider（local mouse / network aim）
3. 子弹射手引用（kill attribution）
4. `maze_generator.gd` `parse_spawn_metadata` 加 `# player2`
5. Level0 抽 `WorldBuilder`（世界构建可复用：地图/瓦片/碰撞/水/后处理；单人行为不变）
6. `Level0.pvp_mode` 静态标志（pvp 跳过敌人/单玩家放置）
7. `MazeGenerator` 钉住地图入口（服务器定图，客户端加载同名文件）
8. transport 抽象（peer 创建/连接/收发收口；ENet 实现，预留 WebRTC/Steam 切换）

**承诺**：每一步都是行为不变的纯重构，`enemy_logic_smoke.gd` / `player_contract_smoke.gd` 保持绿，单机玩起来和今天一样。

## 8. 测试

- 输入抽象落地后：`player_contract_smoke.gd` 保绿（契约不变）。
- 新增 `-s` **loopback 冒烟**：`server_main` 脚本进程 + 2 个客户端脚本进程同机对 `127.0.0.1`，测输入重放 / 快照 / 事件 / 记分 / 回合推进。测试由用户自己跑（项目惯例）。

## 9. 风险与边界

| 风险/边界 | 说明 |
|---|---|
| 延迟假设 | 目标局域网/服务器同机房；互联网高延迟需在 C2 基础上增强预测（C2 已是最便宜形式，两端同码） |
| 地图尺寸 | 必须保证 `MAP/2 > 视野半宽`，否则环面副本翻转会落入视野、出现"凭空瞬移"（当前 8000×4800 满足；未来小图注意） |
| 拆墙延迟 | 子弹本地模拟在拆墙事件到达前可能短暂分歧——可接受 |
| 无时限 | 10 击杀制已自收敛；可选加时/时限为未来项 |
| 断线 | 服务器检测到对端退出 → 通知另一客户端 → 回菜单。不做断线恢复 |
| 并发上限 | 每房间是一个完整世界模拟；进程内上限 2~4 局 |
| 反作弊 | 服务器权威已天然兜底；demo 不做额外防护 |

## 10. 后端化预留（未来项，不在本次实现）

- 网络层收口成 **transport 抽象**，`ENetMultiplayerPeer` 只是实现之一。
- 将来若要"公网房间号 + 免配置服务器地址"，可从 Nakama（房间+信号+托管）或 GodotSteam（Steam 大厅 + Datagram Relay）二选一，只换 transport 实现，协议/环面/回合状态机不动。
- 服务器权威上云（权威搬到 Nakama/自建服务器）已是本设计形态，无需额外演进。

## 11. 实现顺序（供 writing-plans 细化）

- **阶段 0**：共享重构 1-8 全部落主线，两个冒烟保绿。
- **阶段 1**：客户端主菜单 + matchmaking（建房/输房间号 UI + 连接状态）。
- **阶段 2**：transport + 协议编解码 + `server_main`/RoomManager/单房间 Match 跑通——服务器与客户端能连、玩家能移动。
- **阶段 3**：快照/副本插值/自己校正 + MatchHUD。
- **阶段 4**：回合状态机/记分/复活/换边/武器切换。
- **阶段 5**：打磨 + loopback 冒烟 + **并发多房间验证** + 部署说明（服务器 headless 启动脚本、开端口）。
