# 关卡编辑器重写 + `.cyrm` v4 格式设计

日期:2026-09-19
状态:设计已定稿,待实现
范围:**仅网页编辑器**(`level_editor/`)。游戏侧改动只出交接文档,不在本次实现内。

---

## 0. 一句话

把编辑器从「单层 125×75 的 64px 格 + 2×2 形状掩码」重写成「**四图层**、每格细分到 **4×4 个 16px 子格**、每子格带**四种颜色辅码**」,导出改为**二进制压缩格式**,并顺手修掉现有编辑器里会丢数据的 bug 与必卡的渲染路径。

---

## 1. 动机与范围

### 1.1 要解决的问题

| 现状 | 问题 |
|---|---|
| 单层 | 装饰(前景藤蔓/后景远景)与碰撞层混在一张网格里,做不了视差和遮挡 |
| 2×2 子格(32px) | 细节精度不够,画不出 16px 的砖缝、台阶、细边 |
| 无颜色调节 | 整张图只能靠 22 种预设纹理,做不出色调层次 |
| v3 文本格式 | 每格 4 字符;四图层后单张图会到几百 KB 纯文本 |
| 单文件 1751 行 HTML | 数据模型写死「二维 int 数组」,加图层无处安放 |
| 每次 pointermove 全量重绘 | 规模放大 16 倍后必卡死 |

### 1.2 明确不做

- 不做运行时随机地图生成(项目本来就已注释掉)
- 不做任意层数(固定四层)
- 不做 `.cyrm` **文本**导出(只保留"只读导入旧 v3 文本"用于一次性迁移)
- 不做 WebGL 渲染管线(Canvas 2D + 分层缓存足够)
- **不支持 `file://` 双击打开**——编辑器只通过本地 HTTP 服务器打开(§4.9)。这是刻意取舍:换来原生 Worker、无同源限制、能直接读写磁盘上的地图文件,代价是每次要先起服务器
- **不碰游戏侧任何代码**——只产出交接文档

## 2. 数据模型

### 2.1 四图层

```
格仍是 64px;地图格数可变(默认 125×75 = 8000×4800 像素,另有 150×100 = 9600×6400)
子格 = 16px,故 subCols = 格数 × 4, subRows = 格数 × 4

顺序   名称    内容                碰撞
(从外到内)
 0     前景    纹理 + 辅码          无(纯装饰)
 1     场景    纹理 + 辅码          ★ 唯一碰撞源
 2     后景    纹理 + 辅码          无(纯装饰)
 3     背景    RGBA8888 真彩        无
```

- 「场景」是**唯一**决定碰撞、寻路、地板判定的图层。
- 「背景」是任意颜色,不用预设纹理,不受辅码约束(它本身就是颜色)。
- 前/场/后三层共用同一套纹理调色板(1–22,与今天一致),但前/后层的**纹理类型(墙/通道/液体)被忽略**——它们只是贴图。

### 2.2 16px 子格与「取角」

**贴图图集不动**:`structure.png` 仍是 320×320、每块 32px 源图、绘制时放大 2× 成 64px。变的只是**格内细分从 2×2 变成 4×4**。

**渲染规则(取角)**:

```
子格全局坐标 (X, Y)   X ∈ [0, subCols), Y ∈ [0, subRows)
令 qx = X % 4,  qy = Y % 4
若该子格纹理为 T(1–22),则:
  从 structure.png 取 T 的源图区域中第 (qx, qy) 个 8px 象限
  (= 源图 32px ÷ 4 = 8px 一块)
  放大 2× 画到该子格的 16px 位置
```

于是:

- **一个 64px 格里 16 个子格填同一种纹理 T** → 拼回 T 的完整 32px 源图放大 2×,与今天 `shape=15` 的视觉**逐像素相同**。
- **只填一个子格** → 显示该纹理对应的 8px 象限放大 2×,即今天 `shape=1`(1/4 砖)的**更细版本**。

★ **象限由子格在格内的位置决定,不是存在数据里的字段**。因为每个子格可以有自己的纹理,它必须能独立推出自己该画哪一块。

★ 因此 **subCols / subRows 必须是 4 的倍数**(否则 `X % 4` 的语义在边缘不自洽)。编码器与解码器都要断言这一点。

### 2.3 辅码(descriptor)

**纹理层**的每个子格存一个 32 位描述符,`0` = 空气:

```
descriptor (u32)
  bit  0- 2   hue          0-7
  bit  3- 5   brightness   0-7
  bit  6- 8   saturation   0-7
  bit  9-11   alpha        0-7
  bit 12-23   texture      1-4095   (0 = 空气)
  bit 24-31   保留,固定为 0
```

**中性描述符** = `hue 4, brightness 4, saturation 4, alpha 7` —— 即"完全按原图,不改一点"。

**档位含义表**(三方共享,编辑器 / shader / 文档各引同一张表):

| 档 | hue 偏移 | brightness 乘数 | saturation 乘数 | alpha |
|---|---|---|---|---|
| 0 | −60° | ×0.6 | ×0.6 | 0 |
| 1 | −45° | ×0.7 | ×0.7 | 1/7 |
| 2 | −30° | ×0.8 | ×0.8 | 2/7 |
| 3 | −15° | ×0.9 | ×0.9 | 3/7 |
| **4** | **0°** | **×1.0** | **×1.0** | 4/7 |
| 5 | +15° | ×1.1 | ×1.1 | 5/7 |
| 6 | +30° | ×1.2 | ×1.2 | 6/7 |
| 7 | +45° | ×1.3 | ×1.3 | **1(原色)** |

★ **三列的中性档不在同一行**:hue / brightness / saturation 的中性在**档 4**,alpha 的中性在**档 7**(上表把档 4 那行加粗只对前三列成立,别顺手把 alpha 也当成 4/7)。默认描述符就是从三列各取中性值拼出来的 `(4, 4, 4, 7)`。

注意 hue 的 8 档是**不对称的**(−60°…+45°),这是设计如此(色相在 360° 上环绕,−60° 等价于 +300°)。brightness/saturation **取乘法而不是加法**(用户 2026-09-19 裁定):暗部不会被直接压成纯黑,中性档(4)恰好是恒等元。

**像素数学定义**(编辑器 JS 与游戏 shader **必须逐像素一致**):

```
输入:源像素 (r, g, b) ∈ [0,1],源 alpha a ∈ [0,1],描述符 (H, B, S, A)
1. (h, s, v) = RGB_to_HSV(r, g, b)          // 标准 HSV(h ∈ [0,360), s,v ∈ [0,1])
2. h' = fposmod(h + (H - 4) * 15, 360)
3. s' = clamp(s * SAT_MUL[S], 0, 1)
4. v' = clamp(v * BRI_MUL[B], 0, 1)
5. (r', g', b') = HSV_to_RGB(h', s', v')
6. a' = a * (A / 7)
输出:(r', g', b', a')
```

★ **是 HSV 不是 HSL**。`饱和度`/`亮度`取的是 HSV 的 S 与 V。这条如果不一致,编辑器里调好的颜色进游戏就变样——写进交接文档的"必须一致"清单。

### 2.4 编辑器的内存表示

```js
map = {
  id, name,
  subCols, subRows,                 // 16px 子格数
  layers: [
    { kind:'tex',   desc: Uint32Array(subCols*subRows) },   // 前景
    { kind:'tex',   desc: Uint32Array(...) },               // 场景
    { kind:'tex',   desc: Uint32Array(...) },               // 后景
    { kind:'color', rgba: Uint32Array(...) },               // 背景(0xRRGGBBAA)
  ],
  players: [{x,y}],                 // 单位 = 64px 格(与今天一致)
  enemies: [{type,x,y}],            // 单位 = 64px 格
  comments: []
}
```

**全部用 TypedArray**。原来是 `number[][]`(嵌套 JS 数组),每张图 4 层 × 150k 格会到几十 MB 且 GC 压力巨大;TypedArray 平坦、无 GC、单张图 2.4MB。

`desc` / `rgba` 的**下标 = `y * subCols + x`**(行主序),与文件里的排布一致。

## 3. `.cyrm` v4 二进制格式

### 3.1 文件布局

```
┌─ 明文头(不压缩;解压方必须先读它才知道要分配多大)──────────┐
│ off  size  field                                        │
│  0    4    magic        "CYRM" (0x43 0x59 0x52 0x4D)    │
│  4    1    version      4                               │
│  5    1    compression  0 = 无, 1 = deflate (zlib/RFC1950)│
│  6    4    body_size    u32 小端,解压后 body 的字节数     │
│ 10    4    body_crc32   u32 小端,解压后 body 的 CRC32    │
│ 14    2    sub_cols     u16 小端,16px 子格列数            │
│ 16    2    sub_rows     u16 小端,16px 子格行数            │
│ 18    1    layer_flags  bit0..3 = 前景/场景/后景/背景 存在 │
│ 19    1    reserved     固定 0                           │
└──────────────────────────────────────────────────────────┘
[20 …]  body(compression=1 时整段是 deflate 流)
```

- `body_size` 是**解压后**的大小,`PackedByteArray.decompress(body_size, ...)` 需要它。
- `compression=0` 时 `body_size` 就是文件长度 − 20。
- 所有多字节整数**小端**。

### 3.2 body 布局(解压后)

```
u16   meta_len
      meta_utf8      meta_len 字节的 UTF-8 文本
按 layer_flags 从 bit0 到 bit3 的顺序,每个"存在"的层一个块
```

**meta_utf8 就是今天那几行注释文本**,形状不变:

```
# player  3 4
# player2 10 4
# enemy  fly_bird 20 12
# <其它说明性注释>
```

复用它有两个好处:① 游戏侧 `MapFormat.parse_spawn_metadata()` 零改动;② deflate 压得掉,不占体积。

★ **spawn 坐标仍以 64px 格为单位**(不是子格)。游戏侧出生点、地板判定、敌人布点全在格级,这样改动面最小。解码方如需子格坐标自行 ×4。

★ **注释行原样保留**(现有编辑器只留第一条,是个 bug,见 §5 A15)。

### 3.3 纹理层块(kind = 1)

```
u8    kind = 1
u16   palette_count           调色板条目数
      palette_count × u32     描述符,小端
u8    index_width             1 或 2
      sub_cols × sub_rows × index_width 字节   行主序
```

- **索引 0 恒为描述符 0(空气)**。编码器必须把空气放在调色板第 0 位,这样空图 = 调色板 `[0]` + 全是 0 的索引流。
- `palette_count ≤ 256` 时 `index_width = 1`,否则 `2`。编码器自行选择;解码器按 `index_width` 读。
- 调色板**逐层独立**。空层的调色板只有 1 项,索引流全 0,deflate 之后几乎不占空间。

### 3.4 背景层块(kind = 2)

```
u8    kind = 2
      sub_cols × sub_rows × 4 字节   0xRRGGBBAA,行主序
```

不做调色板:背景是真彩,而且平滑渐变恰好是 deflate 最擅长的一类数据(实测这类数据 deflate 常在 20:1 以上)。如果将来体积成问题,再考虑加索引模式,但那是 v5 的事。

### 3.5 压缩

- `compression = 1` 用 **deflate(zlib 格式,RFC 1950)**,覆盖**整个 body**,不含明文头。
- 浏览器侧:`CompressionStream('deflate')`(原生,产出 zlib 格式)。
- Godot 侧:`PackedByteArray.decompress(body_size, FileAccess.COMPRESSION_DEFLATE)`。
- ★ **两端都没有自造压缩器**——这是刻意的:自己写 RLE 意味着自己写解压器,而解压器写错是那种"大部分时候对、偶尔静默出错"的 bug。
- ★ **风险与退路**:两端库对 zlib 头的处理历史上有过细微差异,而本设计期间**无法实跑验证**(要同时跑浏览器与 Godot)。因此:
  1. `compression = 0`(裸 body)是一条**完整可用的路径**,不是半成品;
  2. 编辑器导出面板上有「压缩」勾选框,默认勾上,取消即导裸二进制;
  3. 交接文档把「拿一份真 `.cyrm` 在 Godot 里解开并比对 CRC」列为游戏侧**第一件必做的事**。

### 3.6 旧格式迁移(只读)

编辑器保留「导入」能力,识别三种输入:

1. `.cyrm` v4 二进制 → 直接读
2. `.cyrm` v3 文本(`# cyrm-v3` 标记,每格 4 字符)→ 转换
3. 旧字母格式(单字符 `0-9`/`A`,无标记)→ 先 2×2 转 v3 语义,再走第 2 条

**v3 → v4 的展开规则**(必须写死,否则旧图会错位):

```
v3 的格值为 packed = texture*16 + shape,shape 是 2×2 掩码
对每一格,遍历 shape 的 4 个 bit:
  bit (qy*2 + qx) 为 1  →  新网格的 4 个子格
                            X ∈ [2*qx, 2*qx+1], Y ∈ [2*qy, 2*qy+1]
                          全部填 texture,辅码取中性 (4,4,4,7)
  bit 为 0              →  这 4 个子格保持空气
```

这条规则配合 §2.2 的取角映射,能保证**旧图迁移后视觉逐像素不变**:旧掩码的那一块 32px 区域,新网格用 4 个 16px 子格拼回来,每个子格取到的正是原来那 8px 象限放大 2×。

spawn 坐标不变(v3 与 v4 都以 64px 格计)。旧图的注释行全部保留。前/后/背景三层留空。

★ **迁移是一次性的**。迁移后 `.cyrm` 只有二进制一种形态,编辑器也**不再导出文本**。

## 4. 编辑器架构

### 4.1 文件拆分

现在是单个 1751 行 HTML。拆成**经典脚本**(不用 ES module):经典脚本没有构建步骤,而且 `globalThis.Core` 这个导出方式让 `smoke.js` 能在 node 里直接跑。

```
level_editor/
  serve.bat                起服务器并打开浏览器
  editor_server.js         node HTTP 服务器(§4.9),~100 行
  structure-editor.html    ~300 行  只剩 DOM 结构与 <script src>
  core.js                  数据模型 + 二进制编解码 + 迁移 + 校验
  tint.js                  辅码像素数学 + tinted-tile 缓存
  render.js                画布渲染 + 分层缓存 + 脏区
  ui.js                    工具栏 / 面板 / 事件 / 持久化
  io.js                    编解码 async 门面(Worker 调用方)
  worker.js                二进制编解码 + CRC32(Web Worker 入口)
  smoke.js                 保留,用 node 跑 core.js(见下)
```

★ **`smoke.js` 现在是从 HTML 里正则抠 `<script>` 块再 `new Function` eval 的**(`smoke.js:13-28`)。拆成外部 `.js` 后必须改成直接读那几个文件——**这个改动是必须的**,不改的话它会静默地什么都测不到(抠不到 script 块 → `Core` 为 undefined → 直接 exit 1,倒还算响亮,但别指望它自己发现)。

### 4.2 渲染架构

**问题**:今天的 `renderCanvas()` 每次指针移动就同步全量重绘。按新规模,fit 视图下一次要画 4 层 × 150k = 60 万次 `drawImage`——**必死**。

**四层缓存,从粗到细:**

```
① 地图缩略图    每张图一张,固定 2px/子格(= subCols*2 × subRows*2 像素)
                编辑时只更新脏格对应的那一小块矩形
                用途:zoom 很小(能看见整张图)时,一次 drawImage 顶掉 60 万次

② 视口离屏层    每层一张,尺寸 = 画布尺寸(★ 绝不建全图离屏:500×300 子格
                按 16px 是 8000×4800 = 153MB,浏览器会直接拒绝)
                编辑 → 只在"那一层"的离屏上重画脏格
                切图层 → 只重新合成(4 次 drawImage),不重画任何一层
                平移 → canvas 自拷贝搬移 + 只补新露出的边条(拖拽近乎零成本)

③ 格位图缓存    (纹理层)每个 64px 格的 16 个子格合成结果,按内容版本号缓存
                编辑某格 → 该格版本 +1 → 下次渲染只重建这一格

④ tinted-tile   (纹理, 象限, 描述符) → 16×16 小 canvas,LRU 上限 8192 张(≈8MB)
                贴图源只有 32×32,一张 tinted 小图 = 256 像素,手算极便宜
                绘制时直接命中缓存,零像素计算
```

**缩放阈值的分工**:

| zoom(px/子格) | 走哪条路 |
|---|---|
| < 8 | 缩略图放大(1 次 drawImage)+ 网格线;看不见子格细节,但拖得动 |
| ≥ 8 | 视口离屏层;首次建层时按 §4.3 闸 2 分帧构建 |

**选区拖动不再实时改数据**:拖动时只记 `(dx, dy)`,渲染时对选区内的格做**偏移查询**(纯读),松手才提交一次 `moveRegion`。今天这条路径每次 `pointermove` 都要深拷贝三份全图(`moveRegion` 的实现),是新架构里最贵的单点,直接归零。

### 4.3 稳定性:四道闸(硬需求)

> 用户 2026-09-19 明确要求:「防止网页卡崩」。

**闸 1 —— 一切有硬上限**

| 项 | 上限 | 理由 |
|---|---|---|
| 地图尺寸 | 400 × 300 格 | 现在 `clampMin(v, min, def)` 的第三参是"非数字时的默认值"而不是上限,输 99999 直接卡死 |
| 库条目数 | 60 | 每张 2.4MB |
| 撤销步数 | 200(差量) | 见下 |
| tint 缓存 | 8192 张 | ≈8MB |
| 缩略图 | 固定 2px/子格 | 400×300 格 → 3200×2400 = 30MB,已偏大,超大图降到 1px/子格 |
| 离屏画布 | ≤ 视口尺寸 | 绝不建全图离屏 |

用户输入一律**钳制**而不是报错回滚(输 99999 变成 400)。

**闸 2 —— 一切长循环有单帧预算**

单帧 CPU 预算 ~8ms,超了就 `await` 一次 `requestAnimationFrame` 继续。适用于:

- 全屏重建(缩放/换图/改窗口)
- 缩略图更新
- 油漆桶填充(500×300 跨环面时是 150k 格)
- IndexedDB 序列化

最坏情况是"慢慢画出来",不是"页面死掉"。

**闸 3 —— 二进制编解码进 Web Worker**

主线程一帧都不阻塞。因为编辑器只走 HTTP(§4.9),`new Worker('worker.js')` 原生可用——不需要 Blob URL 那种绕法,也**不需要降级路径**。这一条同时消掉了"某些浏览器上 Worker 起不来"这个不确定性来源。

`io.js` 仍是 **async 门面**,理由不再是降级,而是 Worker 通信本来就是异步的;写成 async 让 `ui.js` 里的导出/导入/自动存代码更直:

```js
async function encodeMap(map, {compress:true}) -> Uint8Array
async function decodeMap(bytes) -> map
```

Worker 里同时做 **CRC32**(文件头要用)与 **deflate**(`CompressionStream` 在 Worker 里同样可用)。

**闸 4 —— 全局错误围栏 + 崩溃前快照**

```
window.onerror / window.onunhandledrejection
  → 立刻把当前整个库写一份到 IndexedDB(独立的 crash 槽位)
  → 下次打开时若发现 crash 槽位比主槽位新,提示
    「上次异常退出,已恢复到崩溃前」
```

这条是兜底:**就算前面三道闸哪里漏了,作品也不会丢**,最坏只丢最后一笔。

| 吸管 | 拾取子格的纹理 **+ 辅码** 到当前画笔 | **新** |
| 渐变 | **仅背景层**。拖一条线定方向与长度,两端各选一色,线性插值 | **新** |

**画笔大小规则**(用户裁定):

- 单位仍是 **64px 格**,输入框步进 **0.25**。
- **整数大小只画整格**,吸附到 64px 格边界,不允许落在子格上。
- **小数(0.25 / 0.5 / 0.75)才画子格**,吸附到 16px 子格边界。0.25 = 1 子格,0.5 = 2,0.75 = 3。

**辅码编辑**:

- 顶部常驻四组 8 档选择器,画笔携带当前值(默认中性 `4,4,4,7`)。
- 另有「**只改辅码**」模式:选区内只动辅码、不碰纹理(整片墙变暗、整片半透明)。

**形状面板删除**(用户裁定)。原来 2×2 象限面板 + 四个预设全部去掉——在子格独立纹理的模型下,"形状"退化成"这一笔盖哪几个子格",而这正好由画笔大小表达。

### 4.6 持久化

三层,从"真身"到"草稿":

1. **真文件 `maps/*.cyrm`** —— 作品的真身。服务器启动时列出 `maps/` 下所有 `.cyrm`,编辑器直接打开/保存。`Ctrl+S` 写回原文件,`Ctrl+Shift+S` 另存为。服务端写入是**原子**的(先写 `.tmp` 再 rename),避免写一半断电把地图毁了。
2. **IndexedDB 草稿盘** —— 正在编辑的库(含未保存改动)防抖落盘,关标签页/崩溃后打开自动恢复。配额失败要**明确告知**,不静默吞掉。
3. **localStorage** —— 只存 UI 小状态(当前图层、缩放、面板开合)。★ 原来"玩家参考图位置"按**屏幕像素**存,换窗口大小/换缩放后语义就漂——**改成以格坐标存**。

### 4.7 编辑器侧校验(审计 C11)

导出前检查并在状态栏/弹窗里点名:

- 一个出生点都没有
- 出生点落在实心格里(用「场景」层的墙判定)
- 敌人落在实心格里
- 出生点/敌人坐标超出当前地图范围(改尺寸时产生的越界残留)
- 四层全空

**只警告,不阻止导出**(编辑器不该替用户做决定)。

### 4.9 本地服务器(`editor_server.js` + `serve.bat`)

编辑器**只通过它打开**。绑 `127.0.0.1:8777` —— 刻意避开游戏侧已占用的端口(7777 大厅 / 7800+ worker / 7999 测试)。用 **node** 写:仓库的编辑器工具链(`sync-tiles.js`、`sync-enemies.js`)本来就是 node,不引入新的运行时依赖。

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/` 与其余静态路径 | 提供 `level_editor/` 下的文件 |
| `GET` | `/api/maps` | 列出仓库 `maps/` 下的 `.cyrm`(名字 / 大小 / mtime) |
| `GET` | `/api/map?p=<name>` | 读一份地图,原样返回字节 |
| `PUT` | `/api/map?p=<name>` | 写一份地图(原子写) |

**必须做的两件事:**

- ★ **路径穿越防护**:`p` 只接受**裸文件名**(`^[A-Za-z0-9_\-]+\.cyrm$`),拒绝任何含 `/`、`\`、`..`、空字节的值。没有这条,一个本地网页就能读写整块磁盘。
- **只绑 `127.0.0.1`**,不绑 `0.0.0.0`。

**不做**:认证、目录浏览、TLS、多用户。它是本机自用工具,不是服务。

`serve.bat` = 起服务器 + 打开默认浏览器到 `http://127.0.0.1:8777/`。
