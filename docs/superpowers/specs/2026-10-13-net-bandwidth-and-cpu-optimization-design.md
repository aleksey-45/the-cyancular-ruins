# 联机流量与 CPU 优化（三条流 + 量测 + 只发变化）

**日期**：2026-10-13 ｜ **状态**：设计待仓主过目（实现计划已存在：[`plans/2026-10-13-stream-merge-metrics-and-delta.md`](../plans/2026-10-13-stream-merge-metrics-and-delta.md)）
**性质**：**协议层（档 3）** + 服务端 CPU + 量测补齐。不含：直连/隧道、量化、兴趣管理、复杂反作弊

## 1. 背景与实测

### 1.1 为什么第一目标是字节

本仓史的原始动机就在归档文档里：**3 Mbps 的公网服扛不住 8 人大乱斗的上行** —— 这是当年上 EasyTier 虚拟局域网的原因。
⇒ 对自建服务器，"带宽"是硬约束；"CPU"在本项目里**有富余**（一局一个 worker 进程，天然分摊到多核）。顺序因此是**先省字节，再谈省 CPU**。

### 1.2 现状字节（载荷口径，探针实测）

| | 旧（`Dictionary` RPC） | 现（手打包） |
|---|---|---|
| 世界包每条目 | 368 B | **51 B** |
| 本人包 | 884 B | **102 B** |
| N=8 服务器上行 | 587 KB/s | **72 KB/s** |
| N=16 服务器上行 | — | **143.85 KB/s** |

★ 这些都是**载荷**（不含 IP/UDP/ENet 头）——真链路**没有**线上字节的仪器（§1.4）。

### 1.3 ★ 编码器 CPU（本次新测，`.superpowers/net/zstd_vs_codec.gd`）

| 操作 | 单次（N=16） |
|---|---|
| 引擎 `var_to_bytes` | **20 µs** |
| `var_to_bytes` + zstd | **31 µs** |
| **我们手打包 `encode_world`** | **294 µs** ← 慢 15 倍 |

换算（N=16、60Hz）：

- **今天**：世界包是**广播** ⇒ 编 **1 次/帧** = 60 × 294 µs = **17.6 ms/s ≈ 1.8% 单核/局** ⇒ 可忽略。
- **按 peer 增量之后**：每个 peer 一份不同的包 ⇒ 编 **16 次/帧** = 960 × 294 µs = **287 ms/s ≈ 28.7% 单核/局** ⇒ **不可忽略**（8 核也就 3 局/核）。

⇒ **结论：先说"CPU 不是问题"是不成立的**（按现状），但**它不该用"放弃增量"来解，而该用"重写编码器"来解**。初判病根是**每个值都 `resize()` 一次**（见 §3.1）。

### 1.4 没有线上字节仪器（债单 §8.11）

`royale_soak` 报的"快照 KB/s"是 `var_to_bytes(**解码后**的 Dictionary)` ⇒ 量的是**内存形状**，对"只改编码"的改动**完全看不见**（实测：加 codec 前后读数不变）。
⇒ 今天所有带宽结论都是**载荷口径**；**没有这条仪器，本 spec 的任何效果都测不出来**。

### 1.5 与"通用压缩"那条路的对比（§5.4）

同一份载荷、三组 N：手打包 **7.0~7.45×**（定宽、与值无关；小包无帧头开销）· zstd **2.4~11.3×**（随 N 与冗余度上升）。
⇒ **不是谁压倒谁**：N ≤ 4 我们更小、N ≥ 8 接近；**两者削的是同一块冗余**（Dictionary 的每值 4 B 类型标签），叠加收益小。

---

## 2. 目标与非目标

**目标**
1. 编码器 **≤ 50 µs/包（N=16）** ⇒ 按 peer 增量后 ≤ 4.8% 单核/局。
2. **线上字节**（真链路读数）在世界包上降到全量的 **0.3~0.5 倍**（依据：实测变更率**世界 2.0/13、本人 4.1/34 字段/帧**）。
3. 每客户端**每帧 1 条包**（今天 1 广播 + N 本人包）。
4. 补上**线上字节**与 **ENet 主动丢包**的量测。

**非目标**：直连/隧道（用户裁定）· 量化（碰回滚面）· 兴趣管理（≤16 不需要）· 复杂反作弊（顺手项除外）· 降频（另案）。

## 3. 设计

### 3.1 编码器重写（先做，独立可验）

**病根初判**：`_put_f`/`_put_v2` 每写一个值就 `resize()` 一次（`snapshot_codec.gd:255+`；4.7.1 的 `encode_float()` 返回 void，所以实现是"resize + 写 + 接上去"）。N=16 一包 ≈ **384 次 resize**。
**做法**：按 schema **预算字节数、一次性分配**，写入用下标（`encode_float(offset, v)`），末尾不再 `append`；写原语尽量内联。
**判据**：同一个计时脚本改前/改后对比（`≤ 50 µs/包`）；且**往返保真判据必须仍绿**（`snapshot_size_probe` 的 ③ 逐字段一致）。

### 3.2 三条流 + 每客户端一条包

- **快照流**：`你的世界增量 + 你自己的状态` 合成**一条**（今天世界包广播 + 每个 peer 一条本人包）。
- **事件流**：同帧多个事件**合并成一条**（内含有序的 `(kind, payload)` 序列）★ 顺序语义显式定义：**先发生先写**。
- **控制流**：握手/低频（沿用现有通道）。
- ⚠️ **代价**：服务器 CPU 由"编 1 份"变"编 N 份"（见 §1.3）⇒ **依赖 3.1 先落地**。
- ⚠️ **通道**：快照走 `unreliable`（保持不变）；事件是否也要改通道，**由 3.4 的读数决定**（若被迫走不可靠，则不合并事件流）。

### 3.3 只发变化（增量）

**格式**：`lastframe`（基线 = 客户端**确认过**的服务器 tick）+ 每字段变化标记 + 值；没变的**一个字节都不发**（Q3 原句 *"not result in any bytes being emitted if the entity has not changed at all"*）。

**必须补齐的语义**（全部有 Q3/DP/Teeworlds 一手来源，详见调研笔记）：

1. **实体全序**：按 **role 升序**写，两端钉死（今天 `Dictionary` 顺序未定义 ⇒ 归并会走错分支）。
2. **消失要显式写删除**（倒地/离开/换边），否则**幽灵实体**残留。
3. **新实体走 `baseline` 支路**（进场全量一次，之后相对它增量）。
4. **整帧解不开 ⇒ 显式请求全量**（Q3 是 `valid=false` + 下包带 `clc_moveNoDelta`），**不是**等下一帧自然好。
5. **丢包空档帧标记为不可用**，不许当基线。
6. **基线窗口定长**（Q3 `PACKET_BACKUP-3 = 29` 包；DarkPlaces 64）—— 我们自定并写进注释。
7. **周期性强制全量**兜底（DP：*"forced full update every half second"*）。
8. **重连由服务器显式清基线**（Q3 `deltaMessage = -1`；本仓已有 `_ack_seq[role] = 0` 先例）。
9. **掩码别用定长**：变更率只有 2.0/13 与 4.1/34 ⇒ 用 Q3 的**标量"末位变化序号"**更省。

**上行新增字段**（前置，与输入包手打包那批**一次改**）：`最近成功解码的服务器快照 tick`（基线的来源）+ `本帧客户端 tick`（两端时间对齐）。

### 3.4 量测

**线上字节**（新增；债单 §8.11 的还账）：按 peer 累计**真实出包字节/包数**，窗口内求分位。
**ENet 那一层**（必须分开，否则读数与现象对不上）：`PEER_PACKET_THROTTLE`（ENet **主动丢**我们的不可靠包）/ `PEER_PACKET_LOSS` / `PEER_ROUND_TRIP_TIME`。
**沿用另一位作者那条线的口径**：未确认输入积压 / 预测回滚次数 / 服务端输入队列深度。
**顺手**：给 host 设**带宽上限**（我们现在传 0 = 不限；Q3 有 `sv_maxRate`/`client->rate`，我们是唯一没有上限的一侧）。

## 5. 顺序与依赖（为什么这么排）

1. **3.1 编码器重写** —— 独立、可单独验（计时 + 往返），且是 3.2 的前提。
2. **3.4 量测（线上字节）** —— 必须先有，否则 3.2/3.3 的效果读不出来（§8.11 的教训）。
3. **上行扩字段 + 输入包手打包** —— **一次改完线格式**（改两次 = 两次档 3 验证）。
4. **3.2 三条流 + 合包** —— 只改"怎么发"，不动载荷内容。
5. **3.3 增量** —— 依赖 1/2/3/4。

## 6. 边界与未决（照实）

- **未决**：基线窗口长度、周期全量的周期、`lc` 与定长掩码的最终取舍（待读数）、事件流是否独立通道（待读数）。
- **量化**：本轮不做，但**位数与做法已调研在案**（DarkPlaces `short[3]`×0.125 / Teeworlds `Quantize()`，且必须**两端同口径**才不破预测）。
- **外插**：我们**冻结**（丢包时不外插）是**保守且合法**的选择（Gaffer 反对外插；Unity 允许有界 20 tick）⇒ 若将来做，**必须写死上限**。
- **引用口径**：深度系数 1.5、冗余 3 条**都是我们自定**（官方是 Unity 的 1.25 抖动乘子 / 4 条）⇒ **别写成有出处**。
- **不做**：跟"16 人不需要兴趣管理"与"量化误差 vs 判定半径"这两条**没有**一手来源 —— 前者只能挂本仓实测，后者**不许写成结论**。
