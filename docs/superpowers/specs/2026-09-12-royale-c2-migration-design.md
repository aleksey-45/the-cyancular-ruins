## 1. 终态

全项目只剩**一条**联机链路，1v1 与大乱斗是同一条（人数只是 N）：

```
main_menu → 大厅配对 → worker 子进程 → claim_role
  → 客户端进对局场景后 主动拉一次 match_sync（昵称/色相/选项/出生点/role 集合）
  → C2：本地步进 + PredictionRollback.reconcile()
  → 服务器每物理 tick 每 role 恰好消费 1 个带 seq 的 FIFO 输入包，回带 ack_seq
  → 快照拆两条：本人包（c2 + ack，定向） / 世界包（全部玩家渲染字段，广播一次）
```

**四条 C2 不变量**（迁移的验收线，1v1 已有、大乱斗必须一并满足）：

1. 服务器每物理 tick 每 role 恰好消费 1 个 FIFO 输入包（`q.pop_front()`）；
2. 快照广播在**消费本帧输入之前**，载荷带 `ack_seq` **与**权威整态 `c2 = capture_state()`；
3. COUNTDOWN 冻结 = 清空队列 **且** `reset_state()`（连 held/axis 一起清）；
4. `weapon_base` 的帧逻辑由**物理 tick** 驱动（`tick(delta)`），不是 idle `_process`。

## 2. 实测数字（本设计新增的测量）

新增 `tests/snapshot_size_probe.tscn`（场景模式）实测单玩家条目构成，与 `docs/royale-soak-2026-09-12.md` §2.2 的「≈0.96 KB/人」互相印证（实测 948 B）：

| 组成 | 字节 |
|---|---|
| 单玩家条目（现方案）= 渲染散字段 + c2 | **948 B** |
| 其中 c2 权威整态（29 字段） | **664 B（70%）** |
| 其中渲染散字段（11 字段，含 ack） | 272 B |
| 世界包瘦身版（短键 + 去 `vel`/`waterproof`） | 176 B/人 |

**结论：旧协议把 70% 的体积花在「只有本人需要」的 c2 上，却每人各发一遍。**

| N | 现方案 服务器上行 | 拆包后 服务器上行 | 世界包 | 现字段表分片 |
|---|---|---|---|---|
| 2 | 222 KB/s（1.8 Mbps） | 112 KB/s | 0.53 KB | 2 |
| 4 | 889 KB/s（7.1 Mbps） | 223 KB/s | 1.06 KB | 3 |
| 6 | 2000 KB/s（16.0 Mbps） | 335 KB/s | 1.59 KB | 5 |
| **8** | **3555 KB/s（≈29 Mbps）** | **446 KB/s（≈3.6 Mbps）** | 2.13 KB | 6 |

⇒ **拆包一道，所有人数档都不再撞带宽墙**（8 人降 8×）。剩下的只有 N≥6 世界包超 MTU（2 片，丢一片整帧丢）—— 那是丢包概率问题，不是带宽问题，本批接受。
⇒ 瘦身后 1 片可撑到 N=7（N=8 差 16 字节）；**本批不做**，读数留档。

### 2.1 贴身缠斗的实测（`tests/brawl_rollback_probe.tscn`，本设计新增）

**为什么量它**：设计初稿把「N 人 C2 的回滚频率」列为 ★★★ 风险，但那个判断**一直是定性的** —— `replica_ghost_probe` 的「0 回滚」是固定场景（预测端被一个**静止**幽灵体挡住），真实缠斗里两边都在动。「每具身体贡献多少回滚」这个单价从来没量过。

**怎么量**：权威侧（A + N−1 具真身，层 AUTH 互相碰撞）与客户端侧（P + N−1 个副本幽灵体，P 认层 GHOST）活在同一个物理空间里，靠层分开；对手按相位错开的脚本持续贴身推挤；控制器按 `DELAY=8` tick 喂权威整态。地图宽 200 格（12800px），整趟不跨接缝。

**健全性对照（决定性的那条）**：对手**站着不动**时回滚 **恰好 0**、分歧 0.23px（N=2 与 N=8 都是，两次跑一致）—— 与 `replica_ghost_probe` 的 0 回滚吻合，**证明探针量到的是真信号**。

| 变体 | N=2 | N=4 | N=8 | 修正量 中位 / p95 |
|---|---|---|---|---|
| 对手不动（健全性对照） | **0** | — | **0** | 0 / 0 px |
| 幽灵体摘除（负向对照） | 224 | — | 240~244 | **75 / 82 px** |
| 幽灵体·插值（**今天的生产行为**） | 8 ※ | 98~240 ※ | 166~174 | 3~5 / 11~12 px |
| 幽灵体·最新（L1） | 221 | 207~231 | 159~196 | 2~4 / 12~13 px |
| 幽灵体·最新+内缩（L1+L3） | 210 | 210~225 | 232 | 6~7 / 16~17 px |

※ **INTERP 这一列不可复现**（N=4 在两次跑之间摆动 98↔240）：它的幽灵体位置取决于副本插值时钟的 idle 相位，探针里不可控。LATEST / INSET / NONE / STATIC 四列可复现（±10%）。这正是**不据 INTERP 列下结论**的原因。

**三条结论**：

1. **这不是「N 人」风险 —— 它在 N=2 就已经完全存在。** N=2/4/8 的斜率 37/35/30 次/秒，持平。也就是说：它**今天就在跑的 1v1 C2 路径里**，不是大乱斗引入的。
2. **L1 与 L3 都买不到它们被指望买到的东西。** L1 无效（被噪声淹没）；L3 无效且 N=8 反而更差（159~196 → 232）。原因：投递延迟 **8 tick**，按 700px/s = 对手能走 **93px**；L1 消掉的是插值那 **1 tick（12%）**，误差主项根本不是它。
3. **严重度是「频率高、幅度小」。** 有幽灵体时每次修正中位 **2~7px**（玩家碰撞箱 80px 宽、瓦片 64px）→ 基本看不出来；对照（摘掉幽灵体）中位 **75px** → 直接瞬移穿过对手，不可玩。**故幽灵体本身是必需的**（这条由对照证明）。

**★ 一条被实测证伪的推断（留档，别再沿它走）**：本节初稿从「对手静止时回滚恰好 0」推出
「静态时重放天然保真 → 主项是回放不保真」，据此定了「回滚时把对手身体倒回同代位置」的方案。
**那是混淆** —— 对手不动时**幽灵体零滞后**，两个变量被绑在一起了。判别实验把它们分开：

| 做法 | 结果 | 判读 |
|---|---|---|
| 重放期间把 restore 目标整体 **+5000px** | 回滚数 **一字不变**（179） | 同帧移动刚体**对物理不可见** |
| 把幽灵体**冻在固定位置**（跨帧生效） | 179 → **225** | 跨帧移动**可见** |

⇒ `move_and_slide()` 在同一帧内看不到静态刚体的位移（物理空间要等下一个物理步），而整个回滚
重放跑在**一个** `_physics_process` 里。**「倒回对手身体」在本引擎的帧结构下做不到**，不是接线问题。

**★ 第二条被证伪的杠杆：幽灵体外推**（用快照里带的对手速度补偿延迟）：

| 变体 | N=2 | N=4 | N=8 | 修正量 p95 |
|---|---|---|---|---|
| 幽灵体用旧位置（今天） | 221 | 231 | 159 | 12~13 px |
| 幽灵体外推 | 222 | 214 | **214** | **65~77 px** |

⇒ **频率不降**（N=8 反而 +35%），**伤害涨 5 倍** —— 对手贴墙/急停时速度还在，外推把幽灵体推过头。

### ★ 真正定案的杠杆：`_close_enough` 的位置容差

**频率不随幽灵体的准度变**：摘除（修正 75px）/ 准确（2px）/ 推歪（77px）三档回滚次数**都是 ~220**。
1.0px 容差下，只要贴身、只要对手身体不是分毫不差，每帧都不成立 → 每帧一次。
**幽灵体决定伤害大小，不决定频率。**

容差扫描（同一场景、同一 N；**每档跑了 3 次**，下表给区间）：

| 容差 | N=2 | N=4 | N=8 | **接触期偏差 中位 / p95** |
|---|---|---|---|---|
| **1px（历史基线）** | 221 / 221 / 221 | 178~218 | 159~239 | 1.5~1.6 / 25~29 px |
| **2px（采纳）** | **9 / 9 / 9** | 75~89 | **13 / 17 / 128** ⚠ | 1.6 / 25~30 px |
| 4px | 7 / 7 / 7 | 8~36 | 6~29 | 1.6 / 25 px |
| 8px | 5 | 8~9 | 11~16 | 1.6 / 25 px |

**怎么读这张表（别只看单次）**：

- **N=2 稳如磐石**：221 vs 9，三次同值，−96%。
- **N≥4 的读数本身离散大**（1px 那档 N=8 就在 159~239 之间摆动）。**2px 在 N=8 摆动到 10 倍
  （13 / 17 / 128）**，所以「2px 砍掉 95%」这句话**只对 N=2 成立**；N=4 是 −55~60%。
- **4px 在 N≥4 稳定更低**（N=4 8~36、N=8 6~29），且**接触期偏差与其它档逐项相同** ——
  即它也一分钱没花。⇒ 若日后嫌 N≥4 的频率仍高，**下一步是 4px，不是重开新方案**。
- ★ 三档的接触期偏差**完全一致**（中位 1.6、p95 25）说明：稳态偏差由接触几何决定，
  **不由容差决定**；容差只决定"要不要为这点偏差每帧回滚一次"。

⇒ 反过来证明：**1px 容差下那每帧一次的回滚本来就没买到精度**（它从 8 tick 前的权威态重放，
落点与不重放几乎一致）→ 放宽容差近似**纯赚**。

**未测的量（不得当成已知）**：**每次回放每步的碰撞成本随 N 涨**（重放要 `move_and_slide()` 扫 N−1 个幽灵体）—— 结构上成立、本探针**没有测**。这是「N 相关」的真实所在，与上面「频率与 N 无关」并不矛盾。

## 4. 改造

### 4.1 快照拆两条包（`server/match_host.gd:_broadcast_snapshot`）

- **`NetBus.snapshot_world(world)`** — `unreliable`，**一次 `rpc()` 广播**：`{tick, players:{role: 渲染字段}, enemies}`。
  ★ `rpc()` 在 ENet 层是单次序列化 + `enet_host_broadcast`，**这是消掉 O(N²) 的关键**；逐 `rpc_id` 循环会退回 O(N²)。
- **`NetBus.snapshot_own(data)`** — `unreliable`，逐 `rpc_id` 定向：`{ack_seq, c2}`。
- 拆开后**互不连累**：c2 丢只少一个回滚锚点（下次补），世界包丢只冻结一帧副本插值。
- 客户端：`_on_snapshot_world` 喂 N-1 个副本 + 局部渲染态；`_on_snapshot_own` 喂 rollback。旧的单包 `snapshot` RPC 与两处消费删除。
- **离线 peer 守卫**：原实现逐 peer 判 `multiplayer.get_peers()`。改广播后该守卫只能退化为「有无在线 peer」的总判；`channel 0` 报错次数**不得比现状更差**（现状：2 人局 0 次、4 人局 3 次，见 soak 报告 §6.1）。

### 4.2 初始状态改「进场拉取」

- 客户端对局场景 `_ready` 末尾 `NetBus.rpc_id(1, "match_sync")`；服务器按 role 回一份 `{names, hues, options, spawns, roles}`。
- 杀掉 B2 那个竞态类（「推给一个正在切场景的客户端」），并把 §3G 的两份出生点合成**一份权威计划**（`RoyaleHost.start_on` 算好传给 `_init`，`_init` 不再第二次 `plan_spawns`）。
- `match_start(role, spawn, map_path)` 保留（客户端要立刻知道 `map_path` 才能建世界）。

### 4.3 大乱斗客户端接 C2（`scenes/royale_game.gd`）

- 删 `set_server_rendered(true)`；加 `_rollback = PredictionRollback.new()` + `bind(_local)`。
- `_physics_process` 在玩家步进前：`note_post_step(prev_seq, capture_state())` → `reconcile()`；包尾 `note_input(seq, pkt)`。
- 输入包加单调 `"seq"`（现在没有 → `ack_seq` 恒 0 → 回滚锚点全失）。
- **补上现在缺的输入锁收口**：`royale_game` 建了 `PauseMenu` 却没接 `toggled`，服务器渲染下被掩盖；接 C2 后不补 = 「开着菜单还能跑」。改成与 `pvp_client` 同款的 `_refresh_input_lock()` 单收口（`_round_locked or _menu_open`）。
- 顺手核实（**结论：不是缺口，无需补**）：`mag_ammo` / `_reloading` 不入 `capture_state` —— 但 `reload_active()` 在 PvP 两端都返回 false（客户端靠 `level_0.pvp_mode`、服务器靠 `input_is_network()`，`weapon_base.gd:104-118`），故 PvP 下 `mag_ammo` 恒为 `mag_size`、`_reloading` 恒 false，**不构成分歧源**。此结论对大乱斗与 1v1 同款成立。

### 4.4 幽灵体（**按 §2.1 实测重定**）

**做 · 倒地时幽灵体不跟着旋转**（`scenes/player/player_replica.gd`）
- 倒地时副本根节点设 `rotation = -PI/2 * facing`（`:119`）做转体，而幽灵体是**子节点** → 碰撞箱跟着转 90°；但服务器 `player.gd` 的倒地分支**不旋转**（全文件零 `rotation`），尸体停在最后姿态的箱子上。紧邻的注释写着「幽灵体不跟着变……否则'倒地的对手还挡不挡路'两端不一致」—— 意图正确，被 `rotation` 那一行抵消了。
- 修法：`_ghost.global_rotation = 0.0`（每帧或随姿态切换时设）。**独立成立，与回滚无关** —— 大乱斗 2s 一复活，倒地是常态，这是持续分歧源。

**不做 · L1 的「幽灵体用最新权威位置」** —— 实测无效（§2.1 结论 2）：只去掉 8 tick 里的 1 tick。
**不做 · L3 的「幽灵体内缩」** —— 实测无效，且 N=8 反而更差（159~196 → 232）；它还要拿「对手挡住我」的手感去换。**不往上加码**。

### 4.4b 真杠杆：`_close_enough` 的位置容差（`core/prediction_rollback.gd`）

**★ 本节曾写作「回放保真（回滚时把对手身体倒回同代位置）」—— 那条已被实测证伪，见 §2.1。**
原文的机制推断是错的（把「对手静止时回滚恰好 0」误读成「静态时重放天然保真」，其实是**对手不动
→ 幽灵体零滞后**，两个变量被绑在一起了）。

**现在这条杠杆的依据（两轮实测）**：

1. 频率**不随幽灵体的准度变** —— 摘除（修正 75px）/ 准确（2px）/ 推歪（77px）三档都是 ~220 次。
2. 它**随容差变** —— 1px → 2px 就把 ~37 次/秒 砍到 ~1.5~2 次/秒（−95%），
   而**接触期偏差中位/p95 一行不变**（1.6 / 25~30 px，与 1px 容差逐项相同）。

⇒ 1px 容差下那每帧一次的回滚**本来就没买到精度**（它从 8 tick 前的权威态重放，落点与不重放
几乎一致）→ 放宽容差是**近似纯赚**。

**做法**：`PredictionRollback.pos_tol`（默认 1.0 = 与历史行为逐帧一致），由接入方设。
**代价（要写清楚）**：容差内的**位置**误差不再纠正 —— 服务器上你被挡住的地方与屏幕上看到的
可差一个容差。`down` 与 `hp` 仍是精确比较，所以命中/倒地**不受影响**；被击退通常 ≫ 容差，
也照旧纠正。

**未定项**：具体取值（2px / 4px）待用户裁定；接线后要加源码守卫（与 `map_px` 同款，
不接线是静默的）。

**附带修（1 行）**：`_close_enough` 比位置原先用裸 `distance_to`，**不是环面最短向量** ——
跨接缝那一帧客户端与服务器可能相差一整幅地图宽 → 误判分歧、多一次回滚。
已改用 `MazeGenerator.toroidal_delta_px`（`map_px` 由接入方设；`pvp_client` 已接线并有源码守卫）。

### 4.5 相机不放大回滚抖动（L4，`scenes/player/camera_2d.gd`）

现状是**硬跟随**：`_base_pos.x = target.global_position.x; global_position = _base_pos`（`:31-33`）→ C2 一帧内修正几像素，**整个画面跟着瞬移同样距离**。

- 正常移动仍 1:1 硬跟随（**手感零变化**）；只对「超出正常单帧位移」的部分**限速追赶**。
- 三个量：`max_step`（正常单帧位移上限，由 `PlayerParams` 推导：`move_speed 700`→11.7 px/帧、`jump_velocity -1000`→16.7 px/帧，取约 1.5× 安全系数）、`snap_dist`（超过即直落，用于复活/传送，避免镜头横穿地图）、**开关默认 OFF**。
- 只有 PvP 客户端打开 → 单机逐帧不变。
- 注：`weapon_base` 的鼠标→世界换算走 `get_base_global_position()`，用的是相机**实际**位置 → 限速后准星与画面仍自洽。
- **附带发现（文档漂移 + 死参数）**：`PlayerParams` 有 `cam_lookahead_x/y`、`cam_smooth_x/y`、`cam_deadzone`（`:44-49`），CLAUDE.md 也写着「相机带前瞻/死区」，但 `camera_2d.gd` **一个都没用**。本批只登记与修正文档，不顺手接线（那是手感改动，需另行裁定）。

### §7 ★★★ 风险的展开与处置（**已由 §2.1 实测重写**）

**先纠正设计初稿的两条错误判断**（它们来自「方向文档的定性说法」，实测都不成立）：

| 初稿说法 | 实测 |
|---|---|
| 「N 人 C2 的回滚频率是风险，随 N 上升」 | **错**。N=2/4/8 斜率 37/35/30 次/秒 **持平** —— 不是 N 人风险，**N=2 就已完全存在**（即：今天在跑的 1v1 C2 里就有） |
| 「L1 砍掉幽灵体 1 tick 滞后能减回滚」 | **错**。投递延迟 8 tick、按 700px/s = 93px；L1 只消掉 1/8 → 被噪声淹没 |

**真实机制（三层，按贡献排序）**：

1. ★ **回放不保真（主项）**：`_handle_ack` 回滚时 `restore_state(S)` 后重放输入，但**对手的幽灵体没有被倒回** —— 它们停在**当前**位置，而当初那次预测用的是**更早**的对手位置 → 重放算出的碰撞与原始预测对不上 → `_captures[s]` 被写成错误时代的状态 → 下一个 ack 再不符 → **级联回滚，每两帧一次**。**决定性证据**：对手静止时重放是保真的 → 回滚**恰好 0**、分歧 0.23px。
2. **投递延迟**（`DELAY=8` tick）：对手在客户端眼里是 133ms 前的位置。这是**因** —— 它导致第 1 条。
3. **幽灵体是 `StaticBody2D`（mask 0），只挡你、不被你推**，而服务器是双向动量交换 —— 结构性，**消不掉**，但实测修正量小（见下），不是主项。

**严重度是「频率高、幅度小」**：有幽灵体时每次修正中位 **2~7px**、p95 12~17px（玩家碰撞箱 80px、瓦片 64px）→ 基本看不出；摘掉幽灵体的对照中位 **75px** → 直接瞬移穿过对手、不可玩。**所以幽灵体本身是必需的**，这条由对照证明。

**杠杆与处置**：

| # | 杠杆 | 处置 | 依据 |
|---|---|---|---|
| **真杠杆** | **`_close_enough` 位置容差**（1px → 2px：N=2 −96%、N=4 −60%，零实测代价） | **做**（§4.4b，已采纳 2px） | 三轮实测：频率只随容差变 |
| ~~回放保真~~ | ~~回滚时倒回对手身体~~ | **不可行** | `move_and_slide` 同帧看不到刚体位移（§2.1 判别实验） |
| ~~L2 幽灵体外推~~ | ~~速度 × 延迟~~ | **证伪** | 频率不降、修正量 p95 12→65~77px（§2.1） |
| 附带 | 环面 `_close_enough`（1 行）+ 接线 | **做** | 探针第一版就踩到它的放大版;不接线则静默惰性 |
| 附带 | 倒地幽灵体旋转 bug | **做** | 独立真 bug，与回滚无关 |
| L4 | 相机不放大回滚抖动 | **做** | 不减少回滚，压 p95 12~17px 那部分的观感成本 |
| L1 | 幽灵体用最新权威位置 | **不做** | 实测无效（只消 1/8 的误差） |
| L3 | 幽灵体内缩 | **不做** | 实测无效，N=8 反而更差；且要拿手感去换 |


**为什么没有退路**：方向文档 §3.2 留的「本地玩家 C2 + 对手服务器渲染」混合式被「只留一套模型」的裁定删除。剩余杠杆全在客户端侧。

**未测的量（不得当成已知）**：
1. **每次回放每步的碰撞成本随 N 涨**（重放要 `move_and_slide()` 扫 N−1 个幽灵体）—— 结构上成立、**本探针没有测**。这才是「N 相关」的真实所在（频率与 N 无关，但**每步成本**与 N 有关）。
2. **headless 量不到观感**（`royale_soak_probe` 无渲染）→ 修正量 2~7px 在真机上是否可感，只能真机评；L4 的验收同样只能真机。
3. **探针是 1-D 水平推挤**，不含跳跃/水中/垂直夹缝；`INTERP` 列在探针里不可复现（见 §2.1 的 ※），故**没有**「今天生产行为 vs 修好之后」的干净对照 —— 那要等批次 1 落地后用同一个探针量。

**性质说明（已更正）**：这**不是**「大乱斗从零回滚变成有回滚」——它是**1v1 今天就有的既有缺陷**，大乱斗只是继承它。M 具身体不改变频率，只抬高重放的每步成本。
