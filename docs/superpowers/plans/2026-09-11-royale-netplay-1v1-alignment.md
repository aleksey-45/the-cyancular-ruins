## 1. 目标模型（= 1v1 现在这套）

1v1 的联通链路是（见 `CLAUDE.md` §网络与 PvP）：

```
main_menu → matchmaking(大厅 RPC:建房/加入) → 大厅 RoomManager 配对
  → 大厅为这局拉起独立 worker 子进程(--worker --port P)
  → 两端 go_match(role, port) 转连 worker,claim_role 报到
  → worker 内 MatchHost 权威模拟(双方 Player + NetworkInputSource)
  → 客户端 pvp_client:本地 C2 预测 + 每物理帧 reconcile()
```

**必须保持的四条 C2 不变量**（它们既是 1v1 的资产，也是迁移的验收线）：

1. 服务器每物理 tick **每 role 恰好消费 1 个 FIFO 输入包**；
2. 快照广播在**消费本帧输入之前**，载荷带 `ack_seq` **与**权威整态 `c2 = capture_state()`；
3. COUNTDOWN 冻结 = 清空队列 **且** `reset_state()`（连 held/axis 一起清）；
4. `weapon_base` 的帧逻辑由**物理 tick** 驱动（`tick(delta)`），不是 idle `_process` —— 重放确定性。

## 2. 差距清单（现状 → 目标）

| 维度 | 大乱斗现状 | 1v1 目标 | 迁移工作量 |
|---|---|---|---|
| **客户端预测** | `server_rendered`（本地玩家位置/姿态全由快照插值） | **C2 客户端预测**：本地自步进 + `reconcile()` 分歧回滚 | ★★★ 最大一块 |
| **输入包** | 每 tick 上报，无 `seq` 语义要求 | 单调 `seq` + 服务器 `ack_seq` 回带，1:1 同序 | ★★（协议已具备，客户端要接） |
| **初始状态** | 服务器**推** 4 条一次性 RPC（与切场景竞态） | 对局场景**进场拉取**一次（见 §3.3） | ★★ |
| **role 契约** | 人数当上界（B1） | 显式 role 集合，与人数解耦 | ★ |
| **房间拆除** | 散在三处（C） | **单一拆除函数**（见 §3.4） | ★ |
| **出生点** | 算两遍、广播那份空转 | **单一权威计划**，随初始状态下发一次 | ★ |
| **对手副本** | N 个 `PlayerReplica`（位置插值已有），**零碰撞体**（纯视觉） | 同左 + **幽灵碰撞体**（见 §3.2b）——否则本地预测对"对手挡住我"完全无信息 | ★★ |
| | | **★ 2026-09-12：幽灵碰撞体已提前落地**（1v1 与大乱斗两端都加，见 `docs/superpowers/plans/2026-09-12-pvp-collision-grenade-and-royale-soak.md`）。§3.2b 本条剩下的只有"量化回滚下降幅度"——`tests/replica_ghost_probe.tscn` 已给出 1v1 的对照读数（幽灵体在位 0 回滚 / 摘掉 277 回滚），大乱斗那条仍待 C2 迁移时量 | |

**不需要改的**：`RoyaleHost` 的回合状态机（限时/淘汰/终局）、`MatchHost` 的裁决/复活/计分、HUD/小地图/反馈层、`ui/pvp_hud.tscn` 的声明式布局、发布工具链。

## 3. 迁移步骤（按依赖排序）

### 3.1 先立"不变量探针"，再动客户端（前置，必须最先做）

C2 四不变量在本层刚被 1v1 侧钉进 `tests/kh_l5_probe.gd`（含 `_on_input` 的入队行为）。迁移**必须先让大乱斗也吃这组断言**，否则改客户端时没有任何东西告诉你"预测回滚被改坏了"。

- 验收：大乱斗开一局，服务器仍满足四条（断言级），客户端 `reconcile()` 有读数（分歧次数/收敛）。
- **反证要求**：把 `q.pop_front()` 改成 `pop_back()`、把快照挪到消费之后 —— 探针必须红。

### 3.2 大乱斗客户端接 C2（最大一块）

- `scenes/royale_game.gd` 去掉 `set_server_rendered(true)`，改走 `pvp_client` 那套：每帧在玩家步进前 `note_post_step(prev_seq)` + `reconcile()`。
- 验证 `capture_state()` / `restore_state()` 覆盖大乱斗需要回滚的**全部**状态（本层已知：`mag_ammo`/`_reloading` **不入** `capture_state`，这是 1v1 就有的既有缺口，迁移时要一并确认是否补）。
- N 个对手仍是 `PlayerReplica`（位置双快照 alpha 插值），但回滚发生时本地玩家会被拉回，副本不受影响。
- **★ 风险的确切机制（读代码后更正，勿再沿用"重放成本随 N 上升"这种笼统说法）**：
  - `PredictionRollback._step()` 只调 `_p._physics_process(PHYS_DT)` —— **只步进本地玩家**。故**每次回滚的重放长度 ≈ 未确认输入数 ≈ RTT × 60Hz，与人数无关**。
  - **与 N 相关的是回滚频率**：客户端只预测自己的玩家；对手在客户端是 `PlayerReplica`（`extends Node2D`，**零碰撞体**，纯视觉），而服务器给每个玩家都设了 `collision_mask |= 2` → **服务器上 N 具玩家身体彼此物理碰撞**。于是"有没有被对手挡住/挤开"这件事**客户端不可预测** → 贴身即分歧 → 回滚。1v1 最多 1 具身体，大乱斗最多 7 具。
  - **间接路径**：快照每人一份 `c2` 整态、体积 ×N → unreliable 丢包/延迟上升 → `ack` 回来更慢 → 上面的重放区间被撑长。
  - **这暴露的是设计缺口而非调优问题**：客户端预测自己却不模拟对手身体。**§3.2 必须处理它**，两条路选一：① 给 `PlayerReplica` 加**幽灵碰撞体**（副本已有插值位置，能让本地预测感知挡路；分歧幅度显著减小但**不归零**，因副本位置是插值/落后的）；② 接受"贴身频繁回滚"并实测观感。
  - 退路仍是"本地玩家 C2 + 对手服务器渲染"的混合式；先做单人局验证再铺开。
- 验收：`pvp_reconcile_smoke` 同款断言在大乱斗场景下通过；真机手感（用户）。

### 3.2b 给 `PlayerReplica` 加**幽灵碰撞体**（与 §3.2 同批，不可分开发布）

**为什么必须做**：C2 下客户端只预测**自己的**玩家（`PredictionRollback._step()` 只调 `_p._physics_process`），而对手在客户端是 `PlayerReplica` —— `extends Node2D`，**一个碰撞体都没有**。可服务器给每个玩家都设了 `collision_mask |= 2`，即**服务器上 N 具玩家身体彼此物理碰撞**。于是"对手挡住我"这件事在客户端**信息上就不存在**：本地预测会直接穿过去，服务器却把你挡住 → 分歧 → 回滚。**这不是调优问题，是预测所依据的世界与权威世界不一致。**

**做法**：给 `PlayerReplica` 挂一个**只参与碰撞、不参与任何逻辑**的幽灵体。

- **节点**：`StaticBody2D`（副本自身不由物理驱动，位置由父节点的插值决定；用 `CharacterBody2D` 反而会引入它自己的 `_physics_process` 与 `move_and_slide` 竞争）。作为副本的子节点 → **位置、朝向、环面回绕全部自动跟随**，无需额外代码。
- **层**：`collision_layer = 2`（与 `Player.tscn` 一致）、`collision_mask = 0`（它不需要感知任何东西，只被本地玩家的 `move_and_slide` 撞到）。
  - **★ 2026-09-12 更正**：本节原写「本地玩家 `collision_mask = 5` 已含 2」——**是错的**。碰撞层是位标志（层1=1、层2=2、层3=4），`5 = 0b101` = 层1（地形）+ 层3（敌人），**不含层2（玩家）**。照原文做会得到一个「本地玩家永远不会撞上去」的幽灵体：看起来实现了，实际无效，且**不会有任何报错**。正确做法是客户端 `_ready` 里补 `local.collision_mask |= 2`（与 `server/match_host.gd` 给服务器玩家做的同一件事）。另注：`Player.tscn` 的场景常量**不能**直接改成 7 —— `tests/enemy_logic_smoke.gd` 有 `player mask == 5` 断言。
- **形状**：与玩家姿态**同源**。玩家是 `Pose→CollisionPolygon2D`（运行时只启用当前姿态的箱子），副本快照里**已经有 `pose`**，故按 pose 切换启用对应的那一份即可；退一步用单个站姿矩形也是可接受的近似（先近似、后对齐）。
- **★ 明确的前提：它只**减小**分歧，**不消除**。** 幽灵体的位置是**插值后、落后约一 tick** 的视觉位置，不是服务器那一 tick 的精确位置 → 贴身高速相对运动时仍会有差异 → **仍会回滚**，只是频率与幅度大幅下降。**验收要按"下降多少"衡量，不能按"是否归零"验收。**
- **★ 副作用清单（必须逐条核，否则会以别的方式坏掉）**：
  - **敌人 mask 含层 2**（敌人 `mask 侦测玩家`）→ 客户端上敌人可能把幽灵体**当成玩家**（吸引/接触判定）。PvP 1v1 里 `ENABLE_BIRDS = false` 无鸟；**大乱斗若有鸟（`RoyaleHost` 自己的刷鸟逻辑），必须先确认幽灵体会不会被它们盯上**，否则要额外加一个"敌人不感知"的层组合。
  - **子弹 mask = 5（地形+敌人）不含层 2** → 子弹不会打在幽灵体上，**无需处理**（但要写下来，避免后人误加）。
  - **打破既有契约**：`player_replica.gd` 与 `CLAUDE.md` 都把副本描述为**"纯视觉副本"**。加碰撞后这句话不再成立 → **必须同步改注释与 `CLAUDE.md`**，否则下一个人会把幽灵体当成 bug 删掉。
  - 副本**不做姿态碰撞箱的运行时启停**（`Player` 有这套），幽灵体要么跟 pose 走，要么恒定站姿——**不要**为了"更精确"把玩家的碰撞箱管理整套复制过来。

**验收（量化，不是布尔）**：取 `PredictionRollback.rollback_count()` 作读数（`pvp_reconcile_smoke` 已在用），在**两名玩家持续贴着走**的固定场景下对比"有/无幽灵体"的回滚次数。基线值得先量一次——**1v1 现在贴身缠斗时的回滚次数同样值得量**，它是大乱斗那条风险的参照点（1v1 只有 1 具身体，所以它给出的是"每具身体贡献多少回滚"的单价）。

**退路**：若加了幽灵体回滚仍频繁到影响观感 → 回到 §3.2 的混合式（本地玩家 C2 + 对手服务器渲染），此时幽灵体自然不再需要。

### 3.3 初始状态改为"进场拉取"

替掉 B2 那条"服务器推 4 条一次性 RPC"的模式：

- 对局场景 `_ready` 后主动请求一次 `match_sync`（names / hues / options / spawns / role 映射），服务端**一次性回一份完整快照**。
- 收益：① 彻底消掉"推给一个正在切场景的客户端"这个竞态类（B2 的根因）；② 顺带消掉出生点双算——**只有一份权威计划**，随 sync 下发；③ 二局/重连天然可用（重新拉一次即可）。
- `PvpSession` 里那些为绕过竞态而加的缓存（`8a1288b` 的临时手法）随之删除。
- 验收：跨真实切场景证明三份 payload 到达消费者；**反证**：让 sync 回空 → 场景必须红/降级可见，而不是静默。

### 3.4 role 契约与房间拆除收口

- **role**：大厅与 worker 之间**显式传 role 集合**（或每次离开后重编号并广播），不再用"人数"兼作上界。worker 的校验改为"role 在集合内"。
- **拆除**：抽一个 `_teardown_room(room)`（杀 worker + 延迟归还端口 + 通知/踢人 + 从注册表移除），`ai_duel` / 超龄清扫 / `on_peer_left` / `royale_leave` **全部**调它。本层为同一失败模式补过三次端口泄漏，收口后才是治本。
- 验收：四条拆除路径逐条跑一遍，端口集合回到基线；**反证**：任一路径漏调 → 断言必须红。

### 3.5 收尾

- 删掉因迁移而失效的临时代码：`PvpSession` 的缓存字段、`royale_probe` 对推送路径的依赖、`RoyaleHost` 的第二份散点计划。
- 更新 `CLAUDE.md`：删掉"D2 大乱斗走 server_rendered **临时方案**"的性质说明，改为"与 1v1 同一套 C2 模型"。
- `docs/pvp-c2-retrospective.md` 补一节"大乱斗接入"的复盘。

## 4. 取舍与不做

- **不为兼容 KH 原生流程而保留它的结构**（用户明确）。迁移中若某处"为了少改而将就 KH 的形状"，一律按 1v1 的形状改。
- **不把 AI 补位接进界面**（D13 不变）；`--ai-roles` 在服务器侧保持可用。
- **不动 1v1 的既有链路**——它是目标形态；本计划对大乱斗的改动不应让 `pvp_match_smoke` / `pvp_reconcile_smoke` / `pvp_twin_smoke` 变红。
- **不做**"顺手把 KH 大乱斗的其余小毛病都清了"——那些随 §3 的替换自然消失，单独修是白费。

## 5. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| **N 人 C2 的回滚频率**（不是"每次重放更贵"——见 §3.2 的机制说明） | ★★★ | §3.2b 的**幽灵碰撞体**（只减小不归零，验收按"下降多少"量化）；先量 1v1 贴身的回滚基线当参照；不行退混合式 |
| `capture_state` 覆盖不全导致分歧不自愈 | ★★ | §3.1 的断言先行；分歧读数必须可见 |
| 迁移期 1v1 被带坏 | ★★ | 三个 PvP 冒烟是硬门，任何一步绿变红即停 |
| 又出现"验收门假绿" | ★★ | 本层已被抓过四次假绿；每条新断言都必须给出"什么错误改动仍会通过"的答案并做反证 |

## 6. 排期建议

§3.1（断言）→ §3.4（契约与拆除，独立且低风险，可先落地）→ §3.3（拉取式初始状态）→ **§3.2 + §3.2b（C2 客户端 + 幽灵碰撞体，同一批）** → §3.5（收尾）。

§3.1 与 §3.4 可以合起来当第一个可提交的小步。**§3.2 与 §3.2b 必须同批**——只上 C2 不上幽灵碰撞体，会得到一个"贴身就疯狂回滚"的版本，而那是**信息不足**导致的，不是能靠调参缓解的；反过来只上幽灵碰撞体而没上 C2，则什么也测不出来（还没有回滚）。这一批单独成层并预留真机联调时间，**并且先量 1v1 贴身缠斗的回滚次数作为参照**（`PredictionRollback.rollback_count()`）。
