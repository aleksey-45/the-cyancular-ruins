L5（大乱斗搬入）终审报出两处阻塞缺陷，根因都不在"某个文件写错了"，而在 **KH 大乱斗自带的那套联机方案**：

| # | 症状 | 根因（方案层） |

## 1. 目标模型（= 1v1 现在这套）

1v1 的联通链路是（见 `CLAUDE.md` §网络与 PvP）：

```
main_menu → matchmaking(大厅 RPC:建房/加入) → 大厅 RoomManager 配对
  → 大厅为这局拉起独立 worker 子进程(--worker --port P)
  → 两端 go_match(role, port) 转连 worker,claim_role 报到
  → worker 内 MatchHost 权威模拟(双方 Player + NetworkInputSource)
  → 客户端 pvp_client:本地 C2 预测 + 每物理帧 reconcile()
```

**必须保持的四条 C2 不变量**（它们既是 1v1 的资产，也是迁移的验收线）：

1. 服务器每物理 tick **每 role 恰好消费 1 个 FIFO 输入包**；
2. 快照广播在**消费本帧输入之前**，载荷带 `ack_seq` **与**权威整态 `c2 = capture_state()`；
3. COUNTDOWN 冻结 = 清空队列 **且** `reset_state()`（连 held/axis 一起清）；
4. `weapon_base` 的帧逻辑由**物理 tick** 驱动（`tick(delta)`），不是 idle `_process` —— 重放确定性。

## 2. 差距清单（现状 → 目标）

| 维度 | 大乱斗现状 | 1v1 目标 | 迁移工作量 |
|---|---|---|---|
| **客户端预测** | `server_rendered`（本地玩家位置/姿态全由快照插值） | **C2 客户端预测**：本地自步进 + `reconcile()` 分歧回滚 | ★★★ 最大一块 |
| **输入包** | 每 tick 上报，无 `seq` 语义要求 | 单调 `seq` + 服务器 `ack_seq` 回带，1:1 同序 | ★★（协议已具备，客户端要接） |
| **初始状态** | 服务器**推** 4 条一次性 RPC（与切场景竞态） | 对局场景**进场拉取**一次（见 §3.3） | ★★ |
| **role 契约** | 人数当上界（B1） | 显式 role 集合，与人数解耦 | ★ |
| **房间拆除** | 散在三处（C） | **单一拆除函数**（见 §3.4） | ★ |
| **出生点** | 算两遍、广播那份空转 | **单一权威计划**，随初始状态下发一次 | ★ |
| **对手副本** | N 个 `PlayerReplica`（位置插值已有） | 同左，但需接受回滚后的校正 | ★ |

**不需要改的**：`RoyaleHost` 的回合状态机（限时/淘汰/终局）、`MatchHost` 的裁决/复活/计分、HUD/小地图/反馈层、`ui/pvp_hud.tscn` 的声明式布局、发布工具链。

## 3. 迁移步骤（按依赖排序）

### 3.1 先立"不变量探针"，再动客户端（前置，必须最先做）

C2 四不变量在本层刚被 1v1 侧钉进 `tests/kh_l5_probe.gd`（含 `_on_input` 的入队行为）。迁移**必须先让大乱斗也吃这组断言**，否则改客户端时没有任何东西告诉你"预测回滚被改坏了"。

- 验收：大乱斗开一局，服务器仍满足四条（断言级），客户端 `reconcile()` 有读数（分歧次数/收敛）。
- **反证要求**：把 `q.pop_front()` 改成 `pop_back()`、把快照挪到消费之后 —— 探针必须红。

### 3.2 大乱斗客户端接 C2（最大一块）

- `scenes/royale_game.gd` 去掉 `set_server_rendered(true)`，改走 `pvp_client` 那套：每帧在玩家步进前 `note_post_step(prev_seq)` + `reconcile()`。
- 验证 `capture_state()` / `restore_state()` 覆盖大乱斗需要回滚的**全部**状态（本层已知：`mag_ammo`/`_reloading` **不入** `capture_state`，这是 1v1 就有的既有缺口，迁移时要一并确认是否补）。
- N 个对手仍是 `PlayerReplica`（位置双快照 alpha 插值），但回滚发生时本地玩家会被拉回，副本不受影响。
- **风险**：大乱斗 TTK 长、人数多 → 回滚重放的成本随 N 上升。需要实测；若不可接受，退路是"本地玩家 C2 + 对手仍服务器渲染"的混合式。
- 验收：`pvp_reconcile_smoke` 同款断言在大乱斗场景下通过；真机手感（用户）。

### 3.3 初始状态改为"进场拉取"

替掉 B2 那条"服务器推 4 条一次性 RPC"的模式：

- 对局场景 `_ready` 后主动请求一次 `match_sync`（names / hues / options / spawns / role 映射），服务端**一次性回一份完整快照**。
- 收益：① 彻底消掉"推给一个正在切场景的客户端"这个竞态类（B2 的根因）；② 顺带消掉出生点双算——**只有一份权威计划**，随 sync 下发；③ 二局/重连天然可用（重新拉一次即可）。
- `PvpSession` 里那些为绕过竞态而加的缓存（`8a1288b` 的临时手法）随之删除。
- 验收：跨真实切场景证明三份 payload 到达消费者；**反证**：让 sync 回空 → 场景必须红/降级可见，而不是静默。

### 3.4 role 契约与房间拆除收口

- **role**：大厅与 worker 之间**显式传 role 集合**（或每次离开后重编号并广播），不再用"人数"兼作上界。worker 的校验改为"role 在集合内"。
- **拆除**：抽一个 `_teardown_room(room)`（杀 worker + 延迟归还端口 + 通知/踢人 + 从注册表移除），`ai_duel` / 超龄清扫 / `on_peer_left` / `royale_leave` **全部**调它。本层为同一失败模式补过三次端口泄漏，收口后才是治本。
- 验收：四条拆除路径逐条跑一遍，端口集合回到基线；**反证**：任一路径漏调 → 断言必须红。

### 3.5 收尾

- 删掉因迁移而失效的临时代码：`PvpSession` 的缓存字段、`royale_probe` 对推送路径的依赖、`RoyaleHost` 的第二份散点计划。
- 更新 `CLAUDE.md`：删掉"D2 大乱斗走 server_rendered **临时方案**"的性质说明，改为"与 1v1 同一套 C2 模型"。
- `docs/pvp-c2-retrospective.md` 补一节"大乱斗接入"的复盘。

## 4. 取舍与不做

- **不为兼容 KH 原生流程而保留它的结构**（用户明确）。迁移中若某处"为了少改而将就 KH 的形状"，一律按 1v1 的形状改。
- **不把 AI 补位接进界面**（D13 不变）；`--ai-roles` 在服务器侧保持可用。
- **不动 1v1 的既有链路**——它是目标形态；本计划对大乱斗的改动不应让 `pvp_match_smoke` / `pvp_reconcile_smoke` / `pvp_twin_smoke` 变红。
- **不做**"顺手把 KH 大乱斗的其余小毛病都清了"——那些随 §3 的替换自然消失，单独修是白费。

## 5. 风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| N 人 C2 回滚的重放成本（TTK 长 + 人多） | ★★★ | §3.2 先做单人局验证；不行退混合式 |
| `capture_state` 覆盖不全导致分歧不自愈 | ★★ | §3.1 的断言先行；分歧读数必须可见 |
| 迁移期 1v1 被带坏 | ★★ | 三个 PvP 冒烟是硬门，任何一步绿变红即停 |
| 又出现"验收门假绿" | ★★ | 本层已被抓过四次假绿；每条新断言都必须给出"什么错误改动仍会通过"的答案并做反证 |

## 6. 排期建议

§3.1（断言）→ §3.4（契约与拆除，独立且低风险，可先落地）→ §3.3（拉取式初始状态）→ §3.2（C2 客户端，最大且需要真机联调）→ §3.5（收尾）。

§3.1 与 §3.4 可以合起来当第一个可提交的小步；§3.2 单独成层并预留真机联调时间。
