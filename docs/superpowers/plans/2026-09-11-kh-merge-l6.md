# KH 合并 L6 实施计划（PvP 客户端合流）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** 把 KH 的 PvP 客户端加成（反馈层 / 对局选项 / 对手色相 / 血条 / 小地图 / 拖尾 / 击杀播报 / 暂停菜单的输入锁）接进 main 的 `scenes/pvp_client.gd`，**并保持 C2 客户端预测与 `server_rendered` 保底两条路径都完好**。

**Architecture:** **main 的文件是基底，只做加法。** 侦察已定论：KH 的 `pvp_client.gd` **不是 main 的加法版，而是把 main 的 C2 整条链路删掉后的 server_rendered 版**（14 处危险差异）。所以本层的正确形状是「把 ~15 处加成搬进来」，而**其余每一处都保持 main 的样子**——包括那些 KH 看着"更简洁"的地方。

**Tech Stack:** Godot 4.7.1 标准版 · GDScript · 探针用场景式（`.tscn` + `--quit-after`，单位**帧**）或 `-s`

## 执行顺序

```
T1  kh_l6_probe（先立不变量探针 —— 必须在动 pvp_client 之前）
 → T2  pvp_client 反馈层加法（血条/小地图/拖尾/击杀播报/反馈层/滚轮切枪）
 → T3  pvp_client PvP 语义加法（match_options 客户端闸门 / peer_hues / hit_confirm）+ U2 实测
 → T4  退出路径收口（三条全走 safe_change_scene + U4 的两条独立风险）
 → T5  notify_direct_hit 调用者（+ U3 的 hit_marker，先确认无双标记）
 → T6  验收探针补齐 + 全量回归 + 文档 + 交付说明
```

**为什么 T1 必须在最前**：本层的全部风险是"加法过程中把 C2 弄坏"，而 C2 弄坏是**静默的**（不报错，表现为橡皮筋/手感错乱）。先立探针，后续每个任务的验证才能引用它；否则改完再补探针，等于没有网。
