# 硬阻挡预测与 CPU 重放验证

验证日期：2026-10-24。运行环境为 Godot 4.7.1、GNS、Zstd 与官方 EasyTier。角色继续使用矩形硬阻挡；团队模式按阵营筛选。

## 90 px 现场

保存现场为角色 1、权威 tick 1266、本地预测到 1273。对手 4 的新输入在 tick 1267 开始反向移动并开启 Beta 加速，改变双方跨地图接缝的接触位置。输入信息经服务端到另一客户端的应用路径约 89 ms。该现场的预测终点变化为 91.869 px。

把相同已知输入交给真实 `AuthorityWorld` 和客户端整组预测，在每个 tick 比较八名角色，最大位置差 0.000122 px。此对照使用原测试地图，未恢复当时完整的毁后地图，验证范围是已保存运动与输入下的接触时序。相同输入下没有复现该大误差；原现场的新输入到达仍会改变已经预测的未来。此项保持未关闭。

[Valve 的网络说明](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)指出，客户端无法即时知道其他玩家的新操作。[Rocket League 的 GDC 资料](https://media.gdcvault.com/gdc2018/presentations/Cone_Jared_It_Is_Rocket.pdf)第 176 页也将其他车辆的不可预测性与昂贵校正列为整体物理预测的边界。这说明需要区分未知操作和已知输入实现分歧，不能据此接受任意幅度或频率的校正。

## 持续输入

服务端在输入变化和新动作到达时转发提示。远端预测使用最后已知的持续移动轴和按键，直到显式变化或新的权威状态更新它；单次动作按序号去重。服务端和本地输入队列在真实断流时仍采用六 tick 延续规则。

行为夹具让权威角色每 tick 接收持续包，远端只收到起步与松键提示，核对位置、速度、跳跃、加速和动作只执行一次。[Unity 的输入预测文档](https://docs.unity.cn/Packages/com.unity.netcode%401.5/manual/intro-to-prediction.html)采用已知 tick 的输入进行模拟，对未知未来输入延续最后已知记录。

## 爆炸与地形碰撞

第二场角色 5、tick 3348 的 109.476 px 校正中，客户端已经准确预测同 tick 的伤害 35、HP 15 和击退向量 `(2439.936, 1745.484)`。预测轨迹的向下冲量被地面裁掉，权威轨迹则穿过爆炸破坏后的地面。使用保存状态与输入，仅改变爆区的碰撞几何，复现 109.47644 px 差异，前后端点与原记录分别差 0.000366 和 0.000173 px。这是局部几何因果对照，未恢复原局完整子格 HP 历史。

当前实现将已知爆炸造成的临时地形伤害纳入相同重放阶段。权威和预测共用 `Explosion.sub_damage`，角色伤害结算后更新子格并提交碰撞。客户端保存所改子格的原 HP，恢复权威状态或清理预测时撤销临时结果；权威 `map_revision` 不因预测变化。收到 TERRAIN 时先撤销临时结果，再应用权威 HP，并按消息 tick 保留尚未被该更新覆盖的未来爆炸。

真实 `Level0` 场景对照中，未预测地形时与参考结果相差 110.213 px；加入共享破坏公式后相差 0.000273 px。此夹具的初始地图没有旧局外沿的既有破坏，横向端点与原日志有所不同，垂直差异为相同的 109.476 px。行为测试还覆盖重复重放不叠加伤害、完整恢复 HP/宏格、较早更新保留未来预测，以及权威替换后不重复破坏或复原已确认破坏。

[Unity 物理预测文档](https://docs.unity.cn/Packages/com.unity.netcode%401.4/manual/physics.html)将物理放入预测重放循环，并区分预测物理与客户端表现物理。这里的处理重点是角色、冲量和碰撞环境使用一致的模拟时间；伤害归属、地形最终 HP、计分和复活仍由服务端决定。

## 开火与弹丸生命周期

地形修复后的 60.020 秒对局中，角色 5 在 tick 3091 首次预测了第 15 枪，但随后重放读到已包含第三颗榴弹的可见场景，将同一次开火拒绝；下一份权威状态恢复射击后坐力时产生 33.471 px 校正。行为夹具固定权威状态和输入，只增加当前可见子弹，旧实现出现位置、弹药与射击序号分歧。当前开火上限读取模拟 tick 的逻辑弹丸；重复重放结果一致，三颗实际存活榴弹仍会阻止第四枪。多人服务端与预测均按角色及武器类型计数。

同场角色 1 的 53.369 和 37.379 px 校正涉及弹丸 `562949953453824`：服务器 tick 2411 的实体列表中已无该弹丸，且没有该弹丸的权威命中，客户端却在 tick 2424、2425 预测了受击。当前普通弹丸结束时按 tick 合批发送可靠 ID，重放保留其终止时间。行为夹具在当前环境已不再阻挡原弹道的条件下，验证结束记录阻止旧弹丸命中，并在权威状态覆盖后清理历史。该现场尚无原始逐 tick 弹道和终止日志，不能将其旧路径完整还原；结束记录修复的是已终止弹丸在当前地形重放中复活的机制。

[Unity 的预测生成文档](https://docs.unity.cn/Packages/com.unity.netcode%401.5/manual/ghost-spawning.html)要求预测和权威采用相同生成条件，并说明预测实体按出生 tick 恢复、与服务端匹配或撤销。这里将影响角色运动的开火条件和弹丸生命周期放入同一模拟时间线；可见节点仅承担表现。

## 当前 CPU 实现

`ActorCollider` 是 `RefCounted` 数据对象，按角色的碰撞更新版本缓存姿态和变换基底对应的局部边界；查询时读取角色当前位置并作环面映射。每次角色移动准备一次障碍矩形，供两轴共用。预测在一次恢复或推进开始时准备角色顺序与碰撞引用，整段重放复用。游泳直接读取当前逻辑矩形的脚底；攀爬仅在已攀附或出现攀附输入时查询地图。

普通弹丸的结束消息在已预测命中曾影响角色时请求重放；没有角色接触的弹丸只更新生命周期和表现。命中判定、伤害和结束时间仍完整保留。`client_state.counts` 分别记录 `projectile_end_contacts` 和 `projectile_end_updates`，两项是消息处理分类，不等于额外重放次数。

离线负载从实际八人记录提取 tick 1320、地图版本 557，恢复记录中的地形变更，重放 20 tick。每版运行 160 次，计时分位数排除前十次热身；该负载没有完整恢复原场所有弹丸和输入历史，适用于固定运动片段的 CPU 对照。

|---|---:|---:|
| P50 | 20.954 ms | 16.004 ms |
| P95 | 26.737 ms | 17.879 ms |
| 最大值 | 28.295 ms | 19.631 ms |

P95 降低约 33.1%。这些是单实例、无渲染固定片段的计时，不能作为整局帧率或八个可见窗口的 GPU 结论。

该早期比较夹具在重复迭代时保留了相同未确认输入记录，计时包含额外队列遍历，运动步数仍为每次 20 tick。当前夹具每次清空并构造固定数量输入；补测 20 tick 的 P50/P95/最大为 15.826/20.143/26.626 ms。不同夹具及运行时段的数字不可直接计算改善百分比。较长重放窗口仍可能超过一个物理 tick 的预算。

同一当前夹具的 32 tick 补测为 27.791/31.877/33.384 ms（P50/P95/最大）。20 tick 与优化前记录、32 tick 与生命周期阶段记录逐 tick 比较，八名角色全部运动字段差均为 0。该补测在实战结束后执行，源码和逐次采样见 `current_bounded_20`、`current_bounded_32` 与 `bounded_comparison.json`。当前 32 tick 成本仍不满足 16.667 ms 预算。

原始证据位于 `.test_logs/prediction_cpu/`，含各阶段计时、Godot profiler 输出、逐 tick 运动状态、源文件及比较脚本。原 90 px 现场与逐 tick 权威对照分别为 `.test_logs/combat_contact_case.json` 和 `.test_logs/hard_contact_authority_probe.json`。

## 公网中继现场

第一场为 `.test_logs/network/gns_prediction_cpu_relay_8/`，60.014 秒八人 Beta 大乱斗，包含一次 token 重连；147 份源码与 GNS DLL 已冻结。八端自然结束并最终收敛到 0 px，武器不一致和发送错误均为 0。此场在最终边界缓存优化前执行，不能作为最终源码验收。

该场记录 26 次 ≥32 px、无 ≥128 px，最大 76.965 px。其中 21 次连续发生于角色 8 的上行输入确认停滞：确认序号保持为 3，客户端仍每秒发送约 60 个 INPUT。服务端该连接的 GNS 有序到达质量降至 0.633，接收包率约从 60 降到 38 包/秒。GNS 的[字段定义](https://github.com/ValveSoftware/GameNetworkingSockets/blob/master/include/steam/steamnetworkingtypes.h)是按序到达比例，不能把 0.633 直接换算成精确丢包率。

另有一条 76.556 px 为时钟重建；其间实际 STATE 接收最长间隔为 421.883 ms。其余四条包含两次新命中、一次无命中的接触场景和一次死亡预测被权威状态恢复；接触场景尚需完整因果验证。全局 RTT P95 为 66 ms，不能单凭此值排除局部单向断流。

该场无 >50 ms 对战卡顿，但有 19 次客户端处理超过 16.667 ms，重放均为 32 tick，最长处理 31.501 ms。这仍是 CPU 成本，不能计作网络传输卡顿。

## 连续时钟与保存现场

角色 7、tick 2400 的 387.600 px 记录中，地图版本始终为 1111、无命中，RTT 样本为 256 ms。此前 tick 2382 的反馈将时钟前移 14 tick，本次又后移 13 tick，同时原地改写未确认输入和动作的目标 tick。这个调度跳变直接改变下落的模拟时间。

使用实际地形变更、权威状态及输入提示重建 tick 2400，时钟 2412 的分支得到 `(1919.390, 2052.000)`，与记录终点差 0.000345 px。保持连续时钟 2425 得到 `(1930.605, 2438.948)`，与校正前记录的垂直位置差 0.000244 px，整体仍有 11.258 px 横向差异。此项确认的是调度造成的垂直跳变，未把全部横向变化归结于时钟。

当前反馈只平滑更新到达余量，通过原有 1.02/0.96 速率连续推进，输入和动作的目标时间戳保持不变。真实时钟越出预测窗口时从新权威状态重建。行为测试覆盖正负大偏差、重复反馈与时间戳不变，原实现失败、当前通过；离线证据为 `.test_logs/clock_case_repro.json`。[DDNet 平滑时钟源码](https://github.com/ddnet/ddnet/blob/master/src/engine/client/smooth_time.cpp)通过当前时间与目标时间的连续插值调整时钟，并处理延迟尖峰。

连续时钟场 RTT P50/P95/最大为 50/70/127 ms，HIT 传递 P95 为 48 ms，八端最终位置差为 0 px，无超预算客户端处理或 >50 ms 战斗卡顿，完整采样最大帧间隔为 33.722 ms。网络条件也较前两场改善，不能把差异全部归结于调度修改。六条 ≥32 px 中最大两条为以下分目标确认缺陷。

## 分目标命中确认

连续时钟场角色 5 在 tick 2970 的爆炸致死预测为正确结果：服务端同 tick 命中角色 2、4、5，角色 5 的最终 HP 为 -14。客户端于 `05:30:57.345Z` 先收到角色 2 的 HIT，`05:30:57.349Z` 重放时却将角色 5 恢复为 HP 12、站立，产生 94.026 px 校正。直到 `05:30:57.361Z` 自己的 HIT 到达，再次倒地并产生 115.528 px 校正。这是把某一目标的确认误当成整次攻击完成所造成的错误，不能归为正常延迟。

当前匹配键为攻击 ID、tick、阶段和受击者。爆炸、光束对尚未确认的目标继续预测，已经确认的目标使用其权威结果。行为测试使用真实角色分别覆盖爆炸和光束，先确认其他受击者，再确认本地玩家；重复重放核对死亡、HP 和冲量保持一致且不叠加。原实现失败记录为 `.test_logs/partial_hit_before.output.log`，当前通过。

[Unity 的预测边界文档](https://docs.unity.cn/Packages/com.unity.netcode%401.3/manual/prediction-details.html)说明，交互实体的部分状态先到达时，需要关注共同模拟的一致性。本项目此处的具体缺陷是命中确认范围错误，修复作用于单个受击者的结果匹配。

## 末次验证与剩余问题
