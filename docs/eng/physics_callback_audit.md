# 28.416 ms 区间的物理回调检查

2026-10-27。对象为 `match_8_relay_regions_trace/client1` 的 frame 623。此次检查使用已有日志与原始报文，并构造离线组件案例；未修改生产预测逻辑，未重跑八人对局。

## 原帧的实际工作

`physics_nodes` 是 `_physics_process` 节点回调的墙钟区间，包含收包派发、权威恢复、客户端预测和地形提交，不等同于 Godot 物理求解器的 CPU 时间。

原区间长 28.416 ms，idle 节点 1.495 ms，随后物理节点 19.885 ms，未覆盖时间 7.036 ms。物理节点内部非重复分解为：权威处理 14.428 ms、输入/发送/正常推进 3.791 ms、消息派发 1.375 ms，以及其余 0.291 ms。

该物理回调收到了七条 `BULLET_SPAWN`，均为角色 4 在 tick 547 发射的 S686 弹丸。已处理的权威状态为 tick 546，本地预测已推进至 549。[出生事件入口](../../scenes/pvp_match_client.gd)在出生身份发生变化且尚未被 STATE 覆盖时请求重放；这里尚未根据本地历史判断弹丸是否会产生影响。

于是恢复 tick 546 的检查点，重放 547、548、549，然后正常前进至 550。原帧逐步记录：

| 步进 | 耗时 | 其中战斗模拟 | 其中地形碰撞提交 |
|---|---:|---:|---:|
| 重放 547 | 1.865 ms | 0.492 ms | 0.006 ms |
| 重放 548 | 6.831 ms | 4.705 ms | 1.650 ms |
| 重放 549 | 2.301 ms | 0.989 ms | 0.012 ms |
| 正常 550 | 3.494 ms | 0.920 ms | 0.008 ms |

四步共 14.491 ms，另有检查点恢复和重放准备等工作。恢复阶段本身为 2.547 ms，包含地形还原、角色、输入和账户恢复，不能全部算成角色状态赋值。

tick 548 在此前已预测过角色 8 的榴弹爆炸，爆点 `(1839.772, 1846.011)`，修改 172 个子格。恢复到 546 时先撤销这份地形，再在重放 548 时重新执行爆炸及碰撞提交。原帧普通位置校正距离为 0。

## 原始数据构造的离线案例

从完整报文前缀解码 tick 546 的角色、弹丸、时间账户状态，原始待确认输入、七条出生消息，以及下一次正常输入。保留原有生产类运行，并另用诊断子类细分计时；诊断场景、脚本与结果都位于工作区 `work/physics_callback_20261027/`。

案例确实在 tick 548 重现同一爆点和 172 个子格变化。新增七枚普通弹丸后，恢复重放得到的完整本地预测状态，与新增弹丸前已存在的本地结果逐项一致。原帧记录只证明位置未校正；完整状态相等的断言来自该离线案例，不能冒充原场保存了完整预测历史。

每组预热三次，记录十五次。未经额外诊断包装的生产类中，3 tick 重放中位耗时 10.545 ms，随后正常推进 1.180 ms。它不是整个在线回调的原样墙钟重现：没有八个客户端并行负载，也未恢复此前全部 64 tick 账本、32 个代理锚点和已退休弹丸历史。

细分探针的结果：

| 工作 | 次数/范围 | 中位墙钟耗时 |
|---|---|---:|
| 地形还原、再次爆炸写入与碰撞提交的并集 | 还原 172 个 HP；扫描得到 174 个候选；再改 172 个 HP、触发 156 次破坏回调；两轮各三块碰撞提交 | 6.791 ms |
| 弹丸接触查询 | 73 次，查询玩家候选 | 1.305 ms |
| 弹丸实际运动整段 | 74 次 `simulate_tick`，包含原生运动查询 | 0.548 ms |
| 本地角色步进 | 三次重放和一次正常推进 | 0.610 ms |

地形并集按每个样本计算：`terrain_restore_total + terrain_predict_total + terrain_commit_total - 恢复阶段已经包含的 terrain_commit`，再取中位数。不能直接把嵌套阶段相加。爆炸扫描约 0.886 ms，扣血及历史/回调约 1.980 ms，全部碰撞提交约 2.476 ms；这些子项与上面的地形并集存在包含关系。

细分模式下重放为 12.079 ms；相同诊断类关闭逐项计时后为 10.904 ms，生产类为 10.545 ms。该顺序对照显示探针有可见扰动，差值还包含运行波动，因此细分数字用于定位热点，不是原场每个子函数的精确时间。

另做静态 PackedInt32Array 写入微检查：172 次写入在 20,480、81,920、327,680 项数组上均约 5–7 微秒，没有随数组容量放大。因此此次没有证据把扣血成本归为“每改一个 HP 就复制整张 HP 数组”。

## 代理采样的固定成本

原 frame 623 有 63 个 `proxy_sample` 区间，累计 3.653 ms，但实际新生成运动步只有 12。两次几何检查使轨迹失效，十二次检查保留了轨迹。

缓存保留的是运动轨迹；[采样入口](../../scenes/player/player_replica.gd)仍会执行 `restore_motion_state`、位置包装、朝向/姿态、权威 HP 和碰撞层恢复，把采样值写回隐藏 Player 节点。因而“缓存命中”尚不等于一次低成本的数组读取。现有日志不能继续将 3.653 ms 精确拆成新步进与这些节点恢复，各自比例仍需专门计量。

## 原因与边界

这一案例的主要开销来自客户端重放所包含的重复地形处理、代理状态恢复和逐弹接触查询。本地角色或弹丸实际运动不是最大的部分。

新增弹丸的出生点为 `(1809.281, 1131.453)`；tick 546 本地位置为 `(1560.656, 514.244)`，环面距离约 665 px。弹速约 1100 px/s，三个 tick 的无阻挡行程约 55 px。离线案例验证其在这个窗口没有改变本地结果。出生入口仍以“新增身份”为依据使本地历史失效，是这次重复工作的重要来源；结束、命中等入口已有的局部影响检查没有自动覆盖到出生入口。

此次检查没有据此简化历史碰撞、取消爆炸预测或改变 tick 调度。下一处具体问题是为远端弹丸出生补足本地影响判定及正确的弹丸独立追赶路径；同时，代理缓存命中后不必要的节点恢复也值得单独处理。
