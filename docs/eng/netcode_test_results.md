## 最近一次公网失败

目录：`.test_logs/network/netcode_v2_final_relay_8_20261024150454`。该版本包含按实际开火、朝向和光束查询判断输入失效的修改，尚未包含随后修复的提示积压与收包预算。

- 战斗 120.022 秒，RTT 中位数 508 ms、P95 556 ms、最大 595 ms；不能与此前 RTT 明显较低的公网运行直接比较优化幅度。
- 战斗内 ≥32 px 校正 1576 次，其中 ≥128 px 270 次，最大 479.43 px。客户端卡顿 5337 次，最大 461.624 ms；tick 卡顿中的重放最大耗时为 96.935 ms。
- 服务端战斗区间未记录 >50 ms 卡顿，最大权威 tick 20.847 ms。客户端记录的 STATE 收包间隔最大约 11.675 秒；已采样的轮询间隔最大约 110 ms，不能覆盖客户端后来停止推进日志的完整时期。
- GNS 发送错误为零，解码 `missing_base` 为零，可靠待发字节为零。这些结果不足以证明公网链路正常，也不能把全部客户端停顿归因于网络。
- 首次主动断线重连成功；后来出现自发掉线。服务端在 15:06:33 UTC 记录部分连接关闭，client1 直到 15:08:54 UTC 才处理断开，随后因席位过期无法重连。client1/client2 未正常结束，其余六个客户端返回同一房间，运行整体失败。

源码审查发现两个会放大积压的独立问题：`PlayerReplica.receive_input` 每次到包都重新提交全部提示历史，而该历史只随 STATE 确认清理；原生轮询一直收取到队列为空，没有单次预算。这是实际存在的本机处理问题。日志尚不能证明它们解释了全部公网断流和掉线。

## 失败后修复和验证范围

修复内容：

1. 收包只提交新增提示，持续和动作提示分别限制为 128/48 条；输入队列同时限制目标 tick 与实际可用 tick。
2. 每次原生轮询最多取 256 条消息，剩余消息留到下一轮。第一版曾同时合并 INPUT/STATE；10 月 25 日审查后取消 INPUT 整包合并，STATE 继续保留最大序号，避免迟到旧包覆盖新状态。
3. 保留可靠顺序屏障；STATE 仍以客户端已确认快照为基线。主动合并的包单列计数，避免把应用层省略算成物理丢包。

Windows x64 原生扩展已重新构建，日志为 `.test_logs/network/netcode_v2_validation/gns_build_final.log`。仅运行两个现有探针，均退出 0、打印成功标识且无 SCRIPT ERROR：

## 2026-10-25：输入完整性与预算修订

接收端保留所有 INPUT 包，由输入缓冲逐记录去重；有限冗余包不再被假定为覆盖旧包。提示淘汰保护当前可恢复区间，窗口内溢出记录缺失序号；缺口未被权威 ACK 覆盖时冻结预测和旧事件重放，新 STATE 只恢复权威锚点，覆盖缺口后重新开始预测。

原生增加 512 KiB/2 ms 软预算和最多 64 条预取，脚本派发另有 512 KiB/2 ms 软预算。延后批次保序，回调和发送重试保持运行；缓存容量和消息年龄越界则关闭相关连接，交给正常重连恢复。具体边界及统计字段见[联机文档](netplay.md)。这些预算不保证单条消息或整帧绝不超时。

Windows x64 构建日志：`.test_logs/network/netcode_v2_validation/gns_budget_build.log`。本轮定向检查日志保存在 `.test_logs/network/netcode_budget_20261025/`，三个探针均退出 0、打印成功标识且无 SCRIPT ERROR：

| 探针 | 验证内容 |
|---|---|
| ProtocolProbe | 两个包含独有未来帧的 INPUT 包乱序到达后仍保留全部命令，重复动作只执行一次；STATE 合并和可靠顺序屏障保持有效 |
| PlaybackLifecycleProbe | 连续 512 次提示不挤掉冻结窗口所需输入；60 条窗口内动作溢出后冻结回滚；覆盖 ACK 后恢复；本地未确认动作继续保留 |
| TransportProbe | Zstd 和未压缩的 700 KiB 基线均完整接收；16 条可靠事件经过 15 次预算让出后保序完成，待派发峰值 16；过期批次触发正常断线通知 |
