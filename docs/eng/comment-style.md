# 代码注释规范（`.gd` / `.tscn` / `.sh`）

> **这份文档是什么**：注释的**形式**约定。它不管"该不该写注释"，只管"写出来长什么样"。
> **为什么有它**：2026-10-13 全仓审计（[记录](../2026-10-13-comment-doc-and-native-audit.md) §2.9）实测——`.gd` 注释共 **11502 行**，其中 **6314 行（55%）带 Markdown 标记**（`**加粗**` 4935 处 + 反引号 5811 处）；注释占**非空行的 32%**，**7 个文件注释行 ≥ 代码行**；另有 **12 行**注释引用 `.superpowers/` 里的文件，而那个目录 **gitignore、不入库**。这三样合起来说明一件事：**注释是写给"读过全部计划与上一次对话的模型"的，不是写给"下一个改这行的人"的。**
> **不适用**：`.md` 文档照常用 Markdown —— 那里**会被渲染**。本规范只管代码注释。

## 1. 不在代码注释里写 Markdown —— 引擎不渲染它

- **事实**：Godot 内置帮助面板渲染的是 **BBCode**（`[b]` / `[code]` / `[param x]` / `[method foo]`），不渲染 Markdown；而 `.gd` 在 GitHub 上按代码渲染，也不渲染。⇒ `**加粗**` 与反引号在**任何**界面里都是字面字符。
- **规则**：注释里只用两个标记 —— **`★`**（值得注意的不变量或陷阱）与 **`⚠`**（已知边界 / 已登记的债）。需要强调就换行、分段、或把结论前置，不要靠加粗。
- **改写示例**：

```gdscript
# 反例：README 里能渲染，这里不能
# 这个数**不是**随手取的：记分条**实测高 52px**
# 正例
# 这个数不是随手取的：1v1 记分条实测高 52px（见 docs/eng/ui.md）。
```

- **例外**：反引号包住标识符（`` `TOP_OFFSET` ``）在**人读**时仍有定位价值。本规范允许保留，但**不再新增**；同一段里出现 3 个以上反引号就该改成成句的中文。

## 2. 文档注释用 `##` + BBCode，别用 `#`

- public API（`class_name` / `signal` / `func` / `@export` / `const`）之上用 **`##`**，因为只有 `##` 会进编辑器的 F1 帮助与 Inspector 提示。
- 需要格式化时用 BBCode：`## 命中时把 [param damage] 交给 [method take_hit]。`
- **现状**：163 个 `.gd` 里只有 **34 个**含 `##`（全仓 256 行）⇒ 今天 public API 的编辑器文档基本是空的（审计 §1-4）。

## 3. 读者模型：只读这一个文件的人

- 一个**新克隆**里、只打开这一个文件的人，必须能在**不打开第二个文件**的前提下看懂这句注释。
- **代号必须就地展开**：`册` / `相N` / `Task N` / `B11` / `D5` / `R19` / `K1` 这类内部编号，首次出现时写成 `别名(= 路径)`，例如
  `A 册(= docs/superpowers/plans/2026-09-18-team-3v3-a-server-rules.md)定死的契约：…`。
- **禁止**只指向 `.superpowers/`：那目录 gitignore、不入库（实测 12 行这么写）。要么把不变量直接写出来，要么指向仓库里**确实存在**的文档。
- 反面实例（审计 §2.9b）：`B2 甲案` 在全仓 **0 命中**；`相③` / `相⑤` 的定义在**已被删掉**的探针文件头里。

## 4. 只写"不变量 / 为什么 / 边界"，过程进 commit message

- 注释里**不写**：谁在哪个批次做的、评审发现了什么、上一版错在哪、本批改了哪些文件。那些属于 commit message 与 `docs/superpowers/` 的 spec/plan。
- **为什么**：过程叙述**永远在长**，而且比代码先过期 —— 审计里"守卫幻觉"（§2.2）与"追加式订正"（§2.4）全是这么攒出来的。全仓注释里有 **580 行带日期戳**、"订正" 40 处、"原文" 18 处。
- **改写示例**：

```gdscript
# 反例
# ★★ 2026-10-08(closeout 批 Task 4):原写法有缺陷,详见报告 §发现A;订正只作追加、原句保留在上。
# 正例
# 必须走 apply_mag():未入树时它写 pending_mag,由 _ready 消费;直接写 mag_ammo 会在未入树窗口里失效。
```

## 5. 单点注释超过 5 行 ⇒ 先问"这是不是过程"

- 一个声明 / 一个分支之上的连续注释超过 **5 行**时，逐行问：这些是**不变量**还是**过程与实测记录**？
  - 过程 ⇒ 搬进 `docs/eng/<域>.md`，原处只留**一行指针**。
  - 不变量 ⇒ 留下，但压到 5 行内：**先写结论，再写为什么**。
- **为什么是 5 行**：注释与代码同文件，改代码的人一定会看到它；超过 5 行就意味着"这段解释比它解释的代码还长"。审计实测最长的几处：**79 行**注释解释 `const EXPECTED_SCRIPTS := 163`、**40 行**解释 `const TOP_OFFSET := 128.0`、**60 行**解释一句赋值。
- 实测数据（值得留住的那部分）**不要删**，搬走 —— 它通常正是 `docs/eng/` 缺的那一块。

## 6. 被推翻的结论直接删，不保留"原句在上"

- 同一段注释里同时存在"已被推翻的旧结论"和"现行结论"时，读者**无法分辨**哪句算数。历史在 `git log` 里。
- 本条**反转**一条旧的仓内习惯（`scenes/player/player.gd` 曾写"订正只作**追加**、原句保留在上"）。审计里那道 40 行注释包含**它自己两个已被推翻的版本**，就是这条习惯的产物。

## 7. 引用守卫的注释必须写清"它还是不是守卫"

- 写成"有守卫：`X` 会钉住"之前，先确认 `X` **存在**；被删掉的守卫要写成 **"零守卫（`X` 已删·YYYY-MM-DD）"**。
- **为什么**：审计 §2.2 —— 全仓有多处注释承诺"改漏了会红"，而那个守卫已在 2026-10-09 的测试面削减里删掉。最刺眼的一处原话是"改漏了它**响亮地红**，不是静默"，而它守的是一个**零守卫**的重复真相源。
- 守卫被删时，**注释与守卫同批改**；跨文件引用（例如 `ui/hud/pvp_hud.tscn` 指向 `ui/hud/status_banner.gd` 的某一段）也要一起改，否则就是新的死指针。

## 8. 注释额度:>100 行的 `.gd` ≤ 15%（2026-10-13 仓主裁定）

**口径（可复算）**：`整行注释行 ÷ 非空行（= 代码行 + 整行注释行）≤ 15%`。空行不计；`.gd` 之外的文件不受此限。
当时全仓 113 个 >100 行的文件里 **103 个超标**，合计需压掉约 **6694 行**注释。

### 8.1 五步配方（每个文件照做）

1. **先分三类**，逐条问"删了会不会有人再踩同一个坑"：
   - **必须活下来**（压到一行、保留结论）：① 防回归的一句话不变量（"别再把这四行加回来"）；② 反直觉的陷阱与引擎行为（"未入树时 `parent_range` 是 `Rect2()`"）；③ 单一真相源指针（"权威在 X"）。
   - **搬走**：成套的实测读数与推导 → `docs/eng/<域>.md`，原处只留一行指针。
   - **直接删**：批次 / `Task N` / 日期 / 评审 / "上一版错在哪" / 重复事实 / 能从代码一行读出的。
2. **不许动代码**：只改整行注释；行尾注释可以删短，但**不许碰字符串字面量里的 `#`**。
3. **不许重排声明**：注释删完后代码语句必须逐字节同一（见 8.2 的验证）。
4. **Markdown 一律去掉**（`**`、反引号成句），黑话按 §3 展开或删。
5. **压到 ≤15% 就停**：不要顺手把上层逻辑也重写。

### 8.2 验证（两条，缺一条不算完）

```bash
# ① 语句逐字节相同（剥整行注释 + 行尾注释后与 HEAD 比对；字符串内的 # 不算注释）
python /tmp/cy_code.py <file>...      # 输出 IDENTICAL 才算过
# ② 额度
python /tmp/cy_ratio.py <file|dir>    # 目标行不再出现 "<<< 超标"
```

★ **样板**：`core/net/pvp_session.gd`（147 行 / 90 行注释 → 43 非空 / **6 行注释 = 14%**，语句逐字节相同）。
★ **已实测的增量**：`ui/hud/status_banner.gd` 150→91、`tests/probe/allscript_probe.gd` 154→77、`tools/room_sweep_lint.gd` 838→785（这三处只做注释，代码零变化）。

### 8.3 与 §5「单点 ≤5 行」的关系

§5 是**质量**规则（别把注释写成小作文），§8 是**额度**规则（总量上限）。两者冲突时：先满足 §8 的额度，再用 §5 的方式组织剩下的注释 —— 即**留最关键的几条、每条一行**。

## 附录 A：怎么量（复算命令）

```bash
# Markdown 标记密度（**加粗** + 反引号）
git ls-files '*.gd' | xargs grep -hE '^[[:space:]]*#' | grep -cE '\*\*|`'

# 注释占非空行比例
git ls-files '*.gd' | while read -r f; do
  awk 'BEGIN{c=0;k=0} {s=$0; sub(/^[ \t]+/,"",s); if(s=="")next; if(s ~ /^#/){c++;next} k++} END{print c, k}' "$f"
done | awk '{c+=$1;k+=$2} END{printf "注释 %d / 代码 %d (%.0f%%)\n", c, k, 100*c/(c+k)}'

# 不可解的引用（gitignore 目录 / 全仓 0 命中）
git ls-files '*.gd' | xargs grep -nE '^[[:space:]]*#.*\.superpowers'

# 单点注释块长度（连续 # 后紧跟声明）
git ls-files '*.gd' | while read -r f; do
  awk -v F="$f" '/^[[:space:]]*(const|var|@export) /{ if(run>=15) printf "%4d 行 -> %s:%d\n", run, F, NR; run=0; next } /^[[:space:]]*#/{ run++; next } { run=0 }' "$f"
done | sort -rn

# 结构性检查（命名 / 文档路径 / .tscn 命名 / EOL）
python tools/check_naming.py
```
