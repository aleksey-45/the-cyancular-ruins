# 本地预测域与只读交互代理

2026-10-27。综合此前的游戏技术报告、引擎文档、公开实现与 Minecraft 调研后，本项目改为：**本地完整预测，远端只提供有界的运动代理；按实际读取结果判断本地历史是否失效。**

## 方案选择

| 资料中的路径 | 适用条件 | 本项目的选择 |
|---|---|---|
| GGPO / Backroll、MK / Injustice 的确定性整体重放 | 小规模、强耦合、完整可恢复且足够廉价的模拟 | 保留检查点、首个失效 tick 和纯模拟原则；不把八名玩家的完整玩法都放进客户端重放 |
| Rocket League 的共享物理预测 | 对车、球等相互作用进行连续物理预测 | 保留明确的碰撞时间与阶段；本项目角色按矩形阻挡，没有必要因此重演远端背包和账户 |
| Source、Epic CMC、Minecraft 基岩版的本地预测与权威校正 | 服务端完整裁决，客户端保障自己的操作响应 | 采用本地预测域；外部运动影响按权威 tick/阶段进入本地历史 |
| LoL 的局部状态预测与确认；Minecraft 的方块/物品确认 | 子系统可独立确认、撤销，不必重跑其他系统 | 保留账户轻量检查、地形增量历史、表现去重与确认覆盖 |
| Roblox 设计、netfox mutations、Chaos resimulation islands、PADS 选择性回滚 | 需要保留广泛对象预测，且愿意承担依赖传播与撤销成本 | 本轮不建设通用因果图；只记录本地实际读取的阻挡与弹丸接触结果，包含空查询 |
| Quantum prediction culling、Fusion forecast 与重模拟取舍 | 按预测预算和精确度选择哪些对象需要重算 | 远端几何采用有界估计；不把这种近似称为完整确定性物理 |

完整出处和证据限制见[选择性重放调研](selective_replay_research.md)、[LoL / CS:GO 调研](lol_cs_prediction_boundaries.md)、[Minecraft 调研](minecraft_prediction_boundaries.md)、[战斗预测资料](combat_prediction_research.md)及[行业技术阅读](netcode_industry_reading.md)。Source SDK 不等于 CS:GO 完整源码，Roblox 专利也不证明每种变体都已部署。

选择依据是本项目的实际耦合：角色间是轴向矩形阻挡，客户端不负责最终裁决他人的伤害、死亡、收入或开火。旧设计把这些状态一起预测，扩大了 STATE、远端输入和事件能使历史失效的范围，也让一次本地重放反复执行七名对手的完整角色和武器逻辑。

## 新的状态归属

| 数据 | 处理方式 |
|---|---|
| 本地移动、控制锁、武器、弹药、开火序号与后坐力 | 保存完整历史，使用共享 `ActorStep` 预测和后缀重放 |
| 本地 HP、击退、倒地、姿态与动作许可 | 已知攻击仍预测；权威 HIT 按原 tick、来源和阶段修复；可撤销错误死亡 |
| 本地时间账户 | 本地推进消耗和回复；新收入先检查加速/回溯依赖，行为不变则只修复账户 |
| 远端角色 | STATE 驱动的只读碰撞/弹丸查询代理；显示继续走独立播放缓冲 |
| 远端 HP、武器、背包、账户 | 权威状态播放，不在本地重放中执行；远端输入提示不拥有本地历史 |
| 已知弹丸、引信、光束与爆炸 | 保留有界逻辑推进和权威确认，只有本地角色承受预测伤害；远端接触仍能决定弹丸结束/引信 |
| 预测地形 | 保留按子格记录的增量历史、局部写入和确认；不复制整张地图 |
| 音画、击杀、命中确认和 UI | 沿用首次预测/服务器确认的去重路径，不随重放重复播放 |

`PredictionRollback._states` 中的角色状态和输入游标仅保存本地角色。远端不会再保存一份完整武器/账户回滚检查点，也不会执行 `ActorStep.step()`。

## 运动代理的边界

[PlayerReplica](../../scenes/player/player_replica.gd) 保存有界的权威运动快照，并为每个锚点惰性生成运动轨迹。轨迹延续权威快照中的持续方向、按住状态、负重倍率与既有运动模式，使用共享 `ActorStep.simulate_motion(..., motion_only=true)` 处理重力、制动、攀爬、游泳、落地、击退衰减与地形阻挡。它不产生新的输入边沿，不调用远端武器、伤害、氧气或账户逻辑，也不模拟代理之间的相互推动。

轨迹按锚点缓存，本地重放反复读取同一 tick 时只采样；同 tick 同内容的锚点更新也不清空轨迹。几何版本变化后对照实际变化区域与已查询区域，只废弃相交轨迹；原生运动查询缓存继续保守按全局版本清理。边界、同数据对照和分块实体复用见[地形与轨迹热点](terrain_replay_hotspots.md)。这个局部运动估计仍然会漏掉尚未到达的新输入、伤害与角色交互，不能称为权威未来或完整世界物理。

逻辑代理的 `MOTION_HORIZON=32` 与本地最大恢复窗口对齐，是可覆盖跨度与工作量上限；只生成实际查询到的部分，不是固定延迟、额外重放数量或精度保证。超过上限后保持受地形约束的终点、输出零速度，并暴露 `proxy_stale`、`proxy_age` 和实际 `proxy_sample_tick`。显示层的 `SnapshotBuffer.MAX_EXTRAPOLATION=6` 保持独立。

旧版直接复用了显示层 6 tick / 100 ms 的线性外推上限，且不处理重力或地形。这一耦合已在本轮移除。[Valve 2001 年报告](https://www.gamedevs.org/uploads/latency-compensation-in-client-server-protocols.pdf)中的 100 ms 是历史显示方案的先例，不是本项目硬阻挡代理的数值推荐。最新实现与验证见[运动轨迹与整帧记录](motion_frame_trace_validation.md)。

回溯角色优先采样服务器提供的 `rewind_path`，不自行消耗账户。已知复活边界在对应服务器 tick 关闭旧阻挡。世界接缝仍使用环形坐标与最近副本。

本地移动前，编号小于本地角色的代理采样本 tick，编号较大的采样前一 tick，对应服务端顺序移动阶段；弹丸阶段统一采样本 tick。复活移除边界独立于编号顺序。

## 按读取结果选择失效后缀

STATE 到达后仍须通过事件屏障与地图版本检查，再验证同 tick 的本地完整状态。远端背包或 HP 数值不同不再直接使本地锚点失败。

后续历史逐 tick 复核：

1. 从本地 ACK 重建本地输入调度，比较实际有效命令；序号不同不等于行为不同。
2. 用新的权威运动代理复核本地轴向裁剪与起身重叠查询，比较实际返回结果。
3. 复核弹丸点/线段接触，包含原先没有碰到人的路径；固定本地当时的候选结果，只重新查询远端候选及排序。
4. 检查弹丸射手的回溯暂停状态，即使没有接触也不能漏掉运动模式变化。
5. 本地账户仍先轻量检查加速倍率和回溯许可；新权威事件限定失效范围。

远端普通弹丸结束时，若历史中没有该攻击对本地造成的预测命中，只修正弹丸生命周期；若已预测命中本地则仍检查撤销。榴弹的引信/地形依赖、本地弹丸的开火数量限制继续保守处理。

远端普通弹丸的迟到出生也先检查影响。新身份在本地历史窗口内、没有待应用 HIT、射手未回溯，且整个可能扫掠范围没有地形变化时，只推进这枚弹丸。接触候选使用原 tick 记录的位置；只要可能接触本地就交回正常后缀重放。成功后补齐弹丸历史锚点、远端接触查询和射手模式依赖，后续 STATE 与其他事件仍可校验这些结果。重复出生不重置已追赶的弹丸，STATE 已覆盖的出生仍只更新元数据。相关检查和固定数据对照见[出生事件与重放优化](spawn_replay_validation.md)。

首个结果不同的 tick 才使后缀失效；之前的历史可保留。新代理进入原先空的移动或弹道查询时，也能发现依赖变化。这里记录的是具体查询的输入与返回值，不是“曾经碰撞过的对象集合”，更不是完整世界因果图。

近距离交互产生的误预测由权威本地状态或上述依赖检查修复。预测结果与服务器保持一致之前，本地碰撞仍可能采用近似代理；不能承诺它与整体确定性模拟有相同精度。

## 保留的保守恢复

本轮**没有**把所有 STATE 和事件差异都变成精确的局部因果检查：

- 弹丸锚点仍比较整份已知弹丸运动状态；不一致时可以重放本地角色及弹丸。
- 地形历史不匹配或历史不足时，仍恢复权威锚点；未为全部射线、LOS 和地形运动查询建设依赖图。
- 榴弹引信、爆点和部分结束事件仍可能保守地使本地历史失效。
- 本地 epoch、历史容量、控制阶段和权威死亡边界仍有效。

区别在于这些恢复不再重演另外七名玩家的完整玩法。不能把本轮改动描述为“任何无关事件都绝不会重放”或“所有模拟已脱离 Godot 节点”。

## 实际验证

全脚本加载 **242/242**。逻辑/场景回归 **66/69**；原有的精英掉落退出崩溃、预瞄探针访问空节点、设置页旧文案断言仍失败。六项基础网络检查及弹丸迟到专项合计 **7/7** 通过，迟到专项覆盖 **23 个场景**。最后的弹丸结束影响检查另复核本地预测域、历史复用、权威角色/六种武器和迟到专项，四项通过。没有将旧的整组输入预测断言继续作为新职责的要求，也没有删去本地受击与迟到恢复断言。

共运行两场八人 Beta 大乱斗。均采用 GNS、官方 EasyTier 本机 UDP 中继、禁用 P2P，包含断线重连，未启用 profiler、包轨迹或外部采样器。Godot stdout 经持续排空的 PIPE 写入文件；RenderWatch 在游戏与副本更新后观察。首场在服务端攀爬覆盖断言失败：第 8 个角色攀爬距离为 0。该角色在攀爬窗口中仍保持约 60 帧，但输入 ACK 和 STATE 一度停止推进，原本的攀爬动作未被服务端执行；尚未定位消息停顿的具体环节，不把这一点归因于预测 CPU。首场记录完整保留，未记作通过。

首场日志还暴露了远端普通弹丸无本地影响却触发重放的入口，修复并通过专项后运行最终场；没有放宽服务端攀爬断言。最终场 runner 通过，八人均完成移动、跳跃、攀爬、射击和伤害覆盖，自然结算后返回原房间。

帧间隔最大值仅取采样区间完全位于正式战斗内的每秒摘要，覆盖各进程约 88.4–89.5 秒；>50 ms 日志按整个正式战斗时间过滤。普通校正的阈值与重置排除口径单独统计，不能拿死亡/复活和 Beta 回溯的原始大位移冒充普通校正。没有发生 >50 ms 日志也不等于所有帧都在 16.667 ms 内。

作为历史参照，10 月 26 日事件影响检查后的八人场记录了客户端最大 231.236 ms、650 条 >50 ms 日志、6,229 次远端输入重放，以及 4 条 ≥32 px 的普通校正日志。新场卡顿与远端输入重放记录减少，但 ≥32 px 校正记录为 9 条。两场的实际到包时序、交互和输入反馈不同，不能视作固定事件序列的严格 A/B，不能据此承诺性能倍数或证明所有校正都来自代理近似。

本轮证据位于工作区 `work/prediction_scope_20261027/`：`regression.json` 保留首轮回归，`verification.json` 汇总修正夹具后结果，`checks/` 保存各专项输出；`match_8_relay/` 保留首场失败，`match_8_relay_final/` 为最终通过场，`analysis.json` 与 `match_8_relay_final.analysis.json` 分别保存统计及原始记录定位。各场 manifest 保存待测源码哈希，禁止混合两场结果。

## 31.764 ms 与代理时域的复核

本节保留本轮修改前对既有最终场的复核，以下“当前实现”和固定 6 tick 均指当时版本。没有为本节重跑八人对局。最新实现与实测单列于[运动轨迹与整帧记录](motion_frame_trace_validation.md)。另对同一原生进程管理入口做了五次隔离的 EasyTier CLI `--version` 启动测量，不把它当成原峰值的重现。

### 帧间隔尚未完成归因

峰值属于 `client5`，日志 `client-20261027T013627-34288.log:2327`。记录时间为台北时间 2026-10-27 01:37:02.171，统计窗口为 01:37:01.171–01:37:02.171。该摘要包含 60 帧，最大帧间隔 31.764 ms。现实现只对 >50 ms 帧间隔逐帧记录，摘要没有保存最大值的具体发生时间，不能准确定位峰值那一帧。

该窗口没有 `client_slow_tick`、`client_slow_present` 或 `transport_slow_dispatch`；它们分别在对应回调墙钟耗时超过 16.667 ms 时记录。因此没有证据把该峰值归因于某次超过 16.667 ms 的单独重放/对局回调，但多个物理 tick、其他回调、引擎工作和等待时间仍可能使整帧超预算。

摘要中的 `physics_ms=7.717`、`process_ms=1.622` 来自采样时的引擎监视器，不是最大间隔那帧的配套分解，不能与 31.764 ms 做减法。相应窗口的单条日志记录最大 0.124 ms，后台 flush 最大 0.004 ms，也不支持“某次日志同步写盘卡了 31 ms”的判断。

同窗口有一次 `tunnel_peers`。代码每五秒在主线程调用原生 `CreateProcessW` 启动 CLI，随后才异步轮询。隔离测量五次启动为 2.084–2.326 ms，poll 最大 0.050 ms：这是预算内真实存在的附加工作，但没有测到原峰值，不能据此直接认定它造成 31.764 ms。后续需要以低开销整帧记录关联帧编号、累计物理/表现/收包/CLI 阶段与墙钟间隔，而不是继续凭一秒摘要调整调度。

### 6 tick 不能被解释成碰撞精度保证

[Epic CMC](https://dev.epicgames.com/documentation/en-us/unreal-engine/understanding-networked-movement-in-the-character-movement-component-for-unreal-engine)的远端 `SimulateMovement` 虽然简化，仍处理运动模式、落地与速度。[Fusion Forecast](https://doc.photonengine.com/fusion/v2/manual/physics/physics-forecast)将外推作为校正目标，保留本地物理与障碍约束，并提供可配置的最大外推时间和重力模式；其实现不能简化为把线性外推位置直接当作碰撞体真值。[Gaffer 的实测讨论](https://gafferongames.com/post/snapshot_interpolation/)也明确展示忽略地板与碰撞响应的外推会出错。

本项目省略代理重力时，以 `gravity0=1600` 计算，100 ms 自由落体的连续近似误差就约为 8 px；地形接触、转向和新击退会产生更不连续的误差。普通移动在 100 ms 内可走 70 px，默认三倍加速时可走 210 px，停在外推终点后仍当作请求 tick 的几何使用，需要明确标记其时效与可信范围。

本地初始化/重定位目标为 `ceil(RTT_ms × 60 / 1000) + 2` tick，稳定时还受实际状态年龄与时钟反馈影响。仅按该目标计算：

| RTT 计算例 | 请求的预测跨度 | 固定 6 tick 截断后少覆盖 |
|---|---:|---:|
| 100 ms | 8 tick | 2 tick / 33.3 ms |
| 150 ms | 11 tick | 5 tick / 83.3 ms |
| 200 ms | 14 tick | 8 tick / 133.3 ms |

这不是新网络实测。最终本机中继场的 720 个客户端秒级样本中，`floor(clock)-own_tick` 全部为 1–6 tick；秒级统计不能排除帧内短暂超限，但该场没有验证稳定高 RTT 下经常需要超过 6 tick 的情况。

因此，合理的后续方向是继续保留本地预测域，让运动代理使用按运动模式和地形约束生成的轻量轨迹缓存，本地重放只采样该轨迹；根据需要覆盖的预测跨度与误差预算单独制定逻辑代理策略。显示外推上限、逻辑预测跨度和超出可信范围的降级处理需要分开，不能只把常量 6 改成另一个固定值。
