# GNS 验证记录

2026-10-22，Windows x64、Godot 4.7.1、GameNetworkingSockets v1.6.1，官方 EasyTier v2.7.0。使用工作区中的正式 NetBus、RoomSession、AuthorityWorld 与 PvpMatchClient。源码和原生 DLL 哈希、回归结果、排除窗口与原始报告位置记录于 [测量数据](gns_measurements.json)。

## 传输与真实对局

- 网络探针 6/6：INPUT、STATE、700 KiB 随机地图基线、分块重组、关闭后重连；分别验证 Zstd 与原始字节。权威探针覆盖全部武器、AI、Beta 和两种回合计分。
- 2、6、8 人大乱斗均正常结算并返回原房间；6 人使用 80±15 ms RTT、8 人使用 150±25 ms RTT，均注入 5% 丢包和 token 重连。8 人额外覆盖双向 750 ms 积压与 250 ms 断流。
- 官方 EasyTier UDP 直连及八人强制公网中继均完成对局和重连。公网测试使用三个 UDP 候选节点并轮换客户端顺序，八端到房主的路由均为 relay(2)，直接邻居使用 UDP，原生日志有内容。
- 六人团队脚本在 90 秒内未达到两局获胜，按超时失败记录；该结果不能作为完整团队对局通过。
- 统一 Windows 游戏 EXE 完成客户端、注册表、无头服务端端口 0 冒烟，以及包内 EXE 作为服务端的真实双人对局和重连。
- 生命周期 6/6、视觉 8/8、Python 链路与计量 9/9、全部 229 个 GDScript 加载通过；单元与场景 61/62，失败项为已登记的 elite_drop_probe 退出访问冲突。

≤50 ms 首轮八端窗口因本机卡顿全部排除；复测八端窗口均有效，表中采用复测。≤500 ms 排除五端，500–1000 ms 排除七端，原因均为客户端卡顿。后两档的比例只描述剩余样本，不能代表整场，也不包含被排除窗口中的全部卡顿。

停止输入后，六档全部客户端的位置误差均小于 0.004 px。极弱网仍有明显播放断供和输入延续预算耗尽；当前预测未来窗口为 32 tick。

计量窗口内的 UDP 转发器记录包含 GNS 头、加密开销、确认和重传；发送速率汇总另加 IPv4/UDP 28 字节头。GNS 日志中的速率估计不作为精确累计字节数。

## Zstd 流量对照

同一固定输入、种子、八人真实大乱斗与 ≤50 ms 波动档，分别运行 Zstd 和无压缩。下表为双向 UDP 包体实测字节，包含 GNS 头、加密、确认和重传，不含 IP/UDP 头。

| 阶段 | 无压缩 | Zstd | 本轮字节差 |
|---|---:|---:|---:|
| 首轮基线阶段 | 59,960 | 6,389 | 减少 89.34% |
| 12 秒对战窗口 | 1,944,638 | 1,713,699 | 减少 11.88% |

基线阶段从服务端首次 BASELINE 记录至最后一名玩家 READY，包含期间控制消息和已开始的快照。两轮为独立真实对局，消息时序及实际事件量可能不同。

无压缩组的服务端和客户端存在超过 50 ms 卡顿，八端窗口均被网络断供统计排除；Zstd 组八端均有效，断供为 0。本轮字节差不能当作完全相同消息序列的纯压缩比，也不能据此比较两组网络卡顿或 CPU。未独立计量压缩 CPU 时间。

## 角色接触与地形碰撞

角色的 `platform_floor_layers` 设为地形层 1，玩家碰撞层仍由对战模式配置。`authority_probe` 覆盖两名角色接触、其中一名倒地后改变位置并复活的行为：另一名角色的位置和速度保持不变。Godot 的平台跟随由碰撞层和接触方向决定，默认范围包含全部层，见 [CharacterBody2D 属性说明](https://docs.godotengine.org/en/stable/classes/class_characterbody2d.html#class-characterbody2d-property-platform-floor-layers)。

无网络的八人真实权威世界复现中，第 2305 tick 角色 1 复活到 `(224, 1824)` 并恢复直立；第 2306 tick，角色 5 缓存的脚下接触仍指向角色 1，碰撞法线为 `(-0.6665, -0.7455)`。物理引擎从角色 1 的变换差得到速度，角色 5 随后出现 `(62086.21, -20035.67)` px/s 的速度。完整现场保存在 `.test_logs/physics_trace.output.log`。采用地形平台层配置后，同一无网络脚本完成 7200 tick，八名角色的速度峰值均低于 3166 px/s。

独立双角色回归的对照结果：全部平台层配置产生 831.44 px 位移和 49886.23 px/s 速度；地形平台层配置的位移与速度均为 0。该用例保留角色之间的实际碰撞。

随后运行两场 120 秒八人 Beta 公网中继对局，均包含一次 token 重连、40 次 Beta 回溯，并自然结算。第二场在测试服务端增加了异常角色现场保存，正式游戏代码相同。

校正统计排除控制阶段切换与 Beta 回溯，仍包含服务端受击、爆炸击退和碰撞差异。第一场服务端与客户端均有超过 50 ms 的卡顿，正式网络窗口全部排除。第二场八端窗口均有效，共 480 客户端秒；网络播放断供累计 6.250 秒，占 1.302%，最长 0.320 秒。原始窗口、逐端结果和源码 SHA-256 记录在各场 `analysis.json` 中。

**平台速度继承的触发已修复，严重校正尚未全部解决。** 两场均保留了角色停在地形附近而速度持续累积的样本。第二场保存的角色 5 在 `(5.567913, 1827.441)`，接触来自地形分块，法线为 `(-0.780578, -0.625058)` 与 `(0.902966, -0.429713)`；均未达到地面判定角度。单独加载该地形与角色状态、关闭网络后，角色仍卡在缺口中，纵向速度随重力继续累加。角色 4 的另一份现场记录了弹性地形附近的负向速度累积。这些现象保留为物理碰撞问题继续排查。

本次回归：网络 6/6、视觉 8/8、Python 链路与计量 9/9、单元与场景 61/62；失败项为已登记的 `elite_drop_probe` 退出访问冲突。两场及离线探针的进程均已回收。
