# 预测校正与卡顿排查记录

2026-10-23，Windows x64、Godot 4.7.1、GNS、官方 EasyTier UDP。以下是无头真实对局的模拟、网络及表现逻辑记录，不衡量 GPU 帧率。修改前与修改后分别保存源码 SHA-256，完整数据在 `.test_logs/prediction_stall_validation.json`。

## 成因与实现

### 复活后的旧尸体阻挡

第一轮日志中的角色 4 / tick 7266（136.71 px）、角色 6 / tick 6104（170.43 px）及 tick 9680（171.09 px），均无新增击退。前后快照显示附近阻挡角色的 epoch 已变更并在远处复活，而客户端此前仍沿旧尸体预测阻挡；加速移动放大了该时间差。

`MatchRules` 使用绝对 `respawn_tick` 安排死亡后 120 tick 的复活。服务端在该 tick 的所有角色移动之后执行复活；STATE 同步时刻，预测从下一 tick 起结束旧尸体阻挡。此字段采用既有差量编码，变化时写入 4 字节；未变化时省略。新权威状态提供复活角色的位置。行为探针覆盖对手编号在本地之前和之后两种顺序，逐 tick 与实际阻挡移动对照。

### 旋转碰撞体与手动重放的位姿

角色 7 / tick 10122 的 221.13 px 校正发生在已知爆炸击退期间，不能以“存在击退”解释。提取其前一快照，在相同高度的简化平地恢复全部角色并重放 8 tick：仅改变碰撞掩码的调用历史，运动学查询可得到约 `(1947.894, 2275.494)` 与 `(1812.236, 2418.637)` 两条终点。

Godot 的[原生位姿实现](https://github.com/godotengine/godot/blob/master/modules/godot_physics_2d/godot_body_2d.cpp)将运动学位姿存入下一物理步的 `new_transform`；[问题 76256](https://github.com/godotengine/godot/issues/76256)记录了同帧强制更新的限制。当前手动模拟调用 `Player.enable_manual_simulation`，使用即时位姿的原生静态查询体，每个共享 tick 提交变换，再通过 `move_and_slide` / `move_and_collide` 求移动和接触。

同一诊断现场在当前代码中，两种查询历史的全部 8 tick 状态逐字段相同，终点均为 `(1780.256, 2442.424)`。这验证了该查询历史依赖的消除；简化平地不包含现场破坏后的完整地图，不能当作原对局的逐帧重演。原始捕获及对照保存在 `contact_10122.json`、`death_query_mode_final.json` 和对应日志。

倒地旋转会清除接地状态。单人重新开始与服务端复活共用 `Player.reset_motion`，重置运动、击退、攀爬、游泳、跳跃、冲刺及姿态锁。权威探针验证恢复后的原生查询位姿在同 tick 生效。

## 本次唯一实战验证

目录：`.test_logs/network/gns_manual_motion_verify_relay_8/`。60 秒 Beta 大乱斗，8 个独立客户端，轮换三条公网 UDP 中继候选、禁用 P2P，包含主动断线重连。总进程运行 67.875 秒，真实对战 60.031 秒。该次源码对应 `gns_manual_motion_source_sha256.json`，共核对 25 个文件。

5 次大幅校正都位于首次收到新爆炸冲量的状态：前一权威击退为零或接近零，本次新增约 1524–2243 px/s 的击退，随后重放 4–6 tick。257 次本地受击事件中，仅这 5 次对应大幅校正，同次命中没有重复的大幅校正记录。这属于本次看到的权威冲量同步现象，不能将它记作网络抖动或网络卡顿，也不能据此承诺所有碰撞都已正确。

此前三次复活阻挡和已知冲量反复校正未在这一轮复现。此轮是一次定向验证，网络时序与对局过程不同，不计算相对于旧对局的改善百分比，不宣称所有校正归零。
