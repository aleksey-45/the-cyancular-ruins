# 校正与卡顿归因验证

本文保留 2026-10-23 的历史定位记录；大幅校正问题现已修复，当前状态见[联机改造实测记录](netcode_test_results.md)。

当时确认存在本地实现问题，不能把校正和卡顿统一归因于公网波动。该阶段修复减少重复碰撞体提交，并在基线恢复前读取新连接 RTT。最终八人强制中继场没有战斗内 ≥32 px 校正，但仍有三次卡顿。另一次带插桩的固定 RTT 对照仍出现四次战斗内大校正；离线重放也确认存在本地运动计算开销，问题在当时尚未全部关闭。

## 已确认的实现问题

### 重放中的重复物理提交

角色步进、状态恢复和阻挡体锚定会反复提交相同姿态、旋转和位置。Godot 的 [`CollisionPolygon2D::set_disabled`](https://github.com/godotengine/godot/blob/4.7/scene/2d/physics/collision_polygon_2d.cpp) 会请求重绘并调用物理接口，调用方只在姿态变化时切换形状。角色记录已应用的碰撞姿态；阻挡体记录姿态和旋转，只在位置改变时写入位置，锚定结束仍立即刷新待提交变换。

无网络的交错对照，在同一进程内交替运行两种阻挡体提交方式，每种 50 次、每次八角色重放六 tick。中位耗时为 5.735 / 4.793 ms，P95 为 6.422 / 5.394 ms，两种方式重复重放的位置差均为 0 px。它证明重复提交存在成本，不是整场性能提升百分比，也不覆盖多人接触的全部状态。

角色、跳跃、加速和击退数值、输入余量、重放上限、校正阈值和视觉衰减时间保持当前配置。

### 重连后的 RTT 初始化

新连接的 `ping_ms` 从 0 开始，周期采样每秒更新一次。重连基线可能在第一次采样前完成，预测时钟因此以零 RTT 初始化。第一场的重连角色在 target tick 703 的输入到达时，服务端已经是 tick 706；随后该阶段七次输入状态切换的余量为 -2 或 -3 tick。这不是只靠公网抖动能够解释的初始化行为。

`NetBus` 在派发 BASELINE 前读取并记录 GNS 统计，使基线恢复使用新连接当前 RTT。最终场重连基线前读到 61 ms；这场没有负余量的输入状态切换，另有一次余量为 0。不能据不同战局的计数推导改善百分比。

预测时钟结合权威输入到达余量进行调整，参考 [DDNet 的 INPUTTIMING 处理](https://github.com/ddnet/ddnet/blob/master/src/engine/client/client.cpp)。初始化与后续反馈必须使用对应连接的实际测量。

## 区分收包与游戏线程处理

GNS 消息的 [`m_usecTimeReceived`](https://github.com/ValveSoftware/GameNetworkingSockets/blob/v1.6.1/include/steam/steamnetworkingtypes.h) 是本地收包时间。扩展将它转换到 Godot 单调时钟，在本机消息元组中传给 `NetBus`，不增加网络包字段。

当前日志同时记录：

- `state_receive_gap_max_ms`：GNS 完成接收 STATE 的间隔。
- `state_gap_max_ms`：游戏线程处理 STATE 的间隔。
- `receive_queue_max_ms`：从 GNS 收包到游戏线程派发的等待时间。
- `poll_gap_max_ms`：游戏主线程两次轮询的间隔。
- `input_arrival`：输入切换的服务端到达 tick、目标 tick、余量和四帧冗余记录。
- `client_slow_tick.rollback`：角色恢复、弹丸准备、角色重放耗时及重放 tick 数。

≥32 px 现场包含对账前未确认的输入和动作；8–31 px 现场仍按每秒最多一条记录。统计阈值与排除规则没有变化。

传输探针在本机故意暂停应用轮询 80 ms，原生时间戳测得消息已等待 52.853 / 61.127 ms，确认可以识别“已经收到但尚未处理”。收包间隔仍包含 GNS 工作线程及发送端调度，不能直接称为纯公网延迟。跨进程关联使用服务端 tick、epoch、输入序号和 UTC 日志时间；本地排队使用单调时钟，不依赖设备时钟同步。

## 八人公开中继实测

两场均为八个独立客户端、Beta 大乱斗、24 秒实际战斗、一次 token 重连，最后三秒停止输入。分别冻结 145 个源码及夹具文件并记录 GNS 二进制 SHA256。第一场验证碰撞提交与诊断，发现重连时钟问题；第二场验证该处修复后的最终源码。每次测试对应具体改动，没有重复网络矩阵。

| 运行目录后缀 | 战斗内 ≥32 px | 全流程 ≥32 px | 战斗内 >50 ms 卡顿 | 战斗内处理阶段卡顿 |
|---|---:|---:|---:|---:|
| `replay_cost_relay_8` | 0 | 1，开局时钟重置 | 0 | 65 |
| `replay_clock_relay_8`，最终源码 | 0 | 8，开局时钟重置 | 3 | 57 |

两场全部进出房间、自然结算和重连断言通过，八端最终误差均为 0 px，武器不一致采样为 0。每场 43 个目标路由采样均为 `relay(2)`，98 个邻居协议采样均为 UDP。GNS 采样发送排队及可靠待发字节最大为 0，发送错误、缺基线和过期计数为 0。不同战局和公网条件不构成严格配对性能实验。

最终场 RTT 中位数 55 ms、P95 66 ms、最大 68 ms。完全位于战斗区间的采样中，客户端 GNS 收包间隔最大 68.549 ms，游戏线程处理间隔最大 67 ms，收包后等待最大 32.555 ms，主线程轮询间隔最大 48.881 ms。整场没有超过 100 ms 的 STATE 间隔记录。这些最大值可能来自不同消息，不可直接相减拆分同一个包的延迟。

最终场 81 次弹丸命中中，79 次在 HIT 到达前预测到相同 tick；5 次爆炸全部提前预测。5 次激光命中均未在 HIT 到达前预测到相同 tick。未获知的远端瞬发攻击仍存在信息边界。

## 卡顿的具体现场

最终场三次卡顿集中在 `06:04:26.196–06:04:26.198 UTC`：

| 客户端 | 帧间隔 | 重放耗时 | 重放 tick | 可见弹丸数 |
|---|---:|---:|---:|---:|
| client0 | 56.839 ms | 39.492 ms | 6 | 0 |
| client4 | 54.839 ms | 40.310 ms | 6 | 0 |
| client7 | 59.052 ms | 43.529 ms | 5 | 0 |

这三次恢复同一个权威 tick 1310，主要时间在角色运动、接触与阻挡体重放；角色状态恢复不足 0.06 ms，弹丸准备不足 0.05 ms。没有超长历史追赶或爆炸计算。重放循环没有等待网络，不能把这些耗时解释为丢包重传等待。

三个进程在几乎同一墙钟时刻结束处理卡顿，仍需要区分主机抢占、物理查询开销和共享资源竞争。这一场缺少线程 CPU 与调度轨迹，不能把 43.529 ms 全部当成实际 CPU 运算。后续离线定位确认原生运动调用有明显开销，但不是这三个历史现场的精确调度轨迹。

该场最终仍有 47 次客户端 tick 超预算，另有服务端和派发阶段超预算，共 57 次处理阶段卡顿。这些是阶段计数，不是独立帧间隔卡顿数。该场不能作为无非网络卡顿的依据。

## 固定 RTT 对照与离线定位

`gns_fixed_rtt_thread_profile_8` 使用同一份运行源码、本机真实八人对局、60 ms 注入 RTT、零注入抖动和零注入丢包。开启服务端轨迹记录，同时在外部每约 2 ms 读取九个 Godot 主线程的 CPU 时间和执行周期。它是一场定位用对照；轨迹复制、采样器和本机转发线程均增加开销，不能把它的卡顿数与无插桩的公网场作性能优劣比较。

这场有四次战斗内 ≥32 px 校正、46 个战斗内 >50 ms 帧间隔。流程、重连和最终收敛检查通过，八端最终误差均为 0 px。GNS 实测 RTT 中位数 62 ms、P95 69 ms、最大 80 ms；固定的是注入传播时延，应用调度及传输处理仍会变化。因此，这场证明公网波动不是上述现象的必要条件，不能称为端到端毫无波动的网络。

| 角色 / 权威 tick | 校正 | 现场 |
|---|---:|---|
| 4 / 446 | 36.000 px | 梯子处持续输入切换，一帧下行位移差 |
| 5 / 1002 | 199.352 px | 权威首次确认致命攻击和倒地，碰撞姿态与存活时的预测不同 |
| 7 / 1424 | 67.724 px | 回溯退出后的跳跃及角色接触，未锁定逐 tick 分歧路径 |
| 8 / 1330 | 33.411 px | 加速阶段，接近一帧高速位移差，仍需核对输入执行时间 |

这些是现场分类，不把所有输入或接触差异等同于已经确认的同一种 bug。致命攻击的倒地状态由服务端结算，统一击退预测不等于已经预测死亡。尚未到达的对手输入在固定 RTT 下也存在未知区间。

进一步取该场角色 3、权威 tick 1320、地形版本 557 的实际状态，在单进程中恢复地形、角色和时间账户，连续外推八角色八 tick，重复 100 次。该夹具使用当前持续输入外推，用于定位耗时，不是完整重演原现场的所有未确认动作。没有网络连接，插桩中位耗时 24.309 ms、P95 28.485 ms、最大 29.673 ms；重复重放的终点最大差为 0.027 px。

100 次累计角色步进耗时 2433.987 ms，其中 `move_and_slide` 累计 1248.833 ms。原生运动调用包括物理形状更新、碰撞恢复和滑动求解；Godot 的 [`body_test_motion`](https://github.com/godotengine/godot/blob/4.7/modules/godot_physics_2d/godot_physics_server_2d.cpp) 会先更新待处理形状，再执行运动查询。当前数据尚不能进一步拆分这些原生步骤的比例。单进程离线复现说明这部分成本属于本地模拟，不能用公网丢包或重传解释。

线程采样中，一次八 tick 重放耗时 29.161 ms，估算执行约 8630 万线程周期，确实包含大量本地执行工作。Windows 线程 CPU 时间在此环境呈现约 15.625 ms 的量化，采样边界也经过插值，不能作为精确的逐帧 CPU 毫秒数。一般场景的八进程离线重放最高为 13.376 ms；它没有覆盖破坏后的同一地形和运动状态，不能代替上述实际状态定位。

剩余性能问题集中在完整角色运动与接触重放。当前源码仍执行完整预测，不通过降低击退、跳过历史 tick 或修改统计阈值消除记录。

## 之前五次大校正

`gns_unified_impact_verified_relay_8` 中，三次约 34 px 的加速校正接近一帧高速移动距离：2061.537 px/s ÷ 60 = 34.359 px。部分现场尚未确认客户端已预测的加速输入，存在一帧执行差；旧日志没有原生收包时间，不能将这帧差具体归因于公网或发送、轮询调度。

另两次为加速 178.906 px 和跳跃 60.444 px，附近角色同时改变输入；没有对应的新命中，属于移动与接触预测分歧的排查范围。旧现场没有逐 tick 接触法线，不能断言已经锁定具体碰撞路径。对手尚未到达的输入即使在恒定 RTT 下也会产生预测不确定性；共享模拟需要相同输入和完整状态，见 [Gaffer 的网络物理说明](https://gafferongames.com/post/networked_physics_2004/)。这两次不能作为“已经证明由网络波动导致”的样本。

本轮两场没有重现战斗内 ≥32 px 校正，不能据此关闭所有接触预测问题。
