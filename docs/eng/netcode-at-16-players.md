# 16 人规模下的联机：命中补偿 / 带宽与分片预算 / 渲染插值

> 设计上限 16 人；现行上限 `ROYALE_MAX_PLAYERS := 16`（`server/lobby/lobby_rooms.gd`）。

## 1. 带宽与分片预算

载荷按 `core/net/net_codec.gd` 的 schema 折算（trail 2 点、装枪 + 1 件背包，世界与本人包；**每包全量自包含**，v7 起 DELTA 编解码已删）。**2026-10-30 起所有人数的下行都是 60Hz**（用户指定），下表按 60Hz 重算：

| 量 | 值 |
|---|---|
| 世界包（每包全量） | `8 + N × 25` B/包（trail 2 点；N=16 ⇒ **408 B**；空 trail = 280 B），60Hz，扇出到 N 个 peer |
| 本人包 | 全量 **99 B**，每 tick 一包（≈5.9 KB/s/role） |
| 服务器上行（N=16） | 世界 `408 × 16 × 60 ≈ 392 KB/s` + 本人 `16 × 5.9 KB/s ≈ 95 KB/s` ⇒ **≈487 KB/s**（≈3.9 Mbit/s；trail 2 点/多人回溯时；常态 ≈364 KB/s） |
| 单端下行（N=16） | `(408 + 99) × 60 ≈ 30 KB/s` |

- 服务器上行仍是 O(N²)：世界包载荷 ∝ N 且每个 peer 收一份；N=16 下世界包占上行约 84%。
- 现状没有兴趣管理 / PVS：世界包含全部玩家（含自己那份）。
- 合同：**世界包必须恒 1 片**。`unreliable` = `UNSEQUENCED | UNRELIABLE_FRAGMENT` ⇒ 丢一片 = 整帧丢。
- 最坏（16 人各 4 点 trail）：`8 + 16 × 33 = 536 B` ⇒ 1 片（`TRAIL_WIRE_MAX := 4`，MTU 预算 1400 B）；v6 同形是 792 B。
- 改世界字段 / `TRAIL_WIRE_MAX` 前跑 `tests/probe/snapshot_size_probe.tscn`（判词 `SNAPSHOT SIZE PROBE: ALL-OK`，5 条断言）。
- 历史：2026-10-24 bool 打包把世界条目 51→48 B、本人包 102→94 B；2026-10-26 P1 定点化把世界条目 48→33 B、输入包 46→42 B；2026-11-01 输入上行改 60Hz 单记录 ⇒ 输入包 **28 B/包（1.68 KB/s/客户端）**；2026-10-30 v7 把 trail 定点化 ⇒ 世界条目 33→**25 B**、最坏包 792→**536 B**；P1.5 增量/差分曾把稳态世界包降到 ≈28%，但 2026-10-28 因乱序/丢包下 RTT 级冻结而**整体放弃、回退全量**，v7 把差分代码一起删除。

## 2. 命中补偿：已落地（2026-10-26，时间域解耦）

- 伤害全走服务器模拟的实体子弹：`server/match/match_combat.gd::_adjudicate_bullets()` 用子弹上一位置→当前位置的线段与玩家受击面（`Player.hurt_rect()`，经 `core/sim/hit_shape.gd`）判命中。
- ★ **命中盒按射手观看时刻回放**：`core/sim/hit_lag_history.gd` 每 tick 存 `role → {位置, 相对受击面}`（24 tick ≈400ms 环）；`MatchCombat._replay_hurt_rect()` 用 `want = clamp(st − PLAYOUT_TICKS, _srv_tick − MAX_REWIND_TICKS, _srv_tick)` 取那一帧的受击面（`st` = 射手客户端最近应用的世界快照 tick，走输入包字段；`cfg` 常量单一来源 = `core/net/lag_comp.gd`：`PLAYOUT_TICKS = 2`、`MAX_REWIND_TICKS = 8`）。普通弹与榴弹直击同一条路径；无历史/非网络射手回退现时受击面。
- `beam_fired` 只 `_rpc_all` 广播视觉，不裁决伤害；没有 hitscan 路径（激光伤害也是服务器实体扫掠）。
- 客户端看到的对手位置是 playout 后的历史位置（比权威晚 ≈33ms，`PLAYOUT_TICKS = 2`）—— 命中回放补偿的正是这一段。**爆炸 AoE 不回放**（现时位置，见 registered-debt §十五）。

## 3. 远端副本：playout 缓冲插值

> playout 机制(缓冲 / 夹逼 / `SNAP_DIST` / 幽灵体 / 锚定)的权威见 [`netcode-client-interp-and-input-details.md`](netcode-client-interp-and-input-details.md);本节只留 16 人规模与代价读数。

- 16 人下每个客户端各跑 15 份历史环 + 15 个播放时钟。历史环是定长（`PlayerReplica.HISTORY_MAX = 12`），但**不是零分配**：每条快照每个副本会新建 2 个小 Dictionary（`_push_history` 的 `{tick,pos,st}` 与 `_state_from` 的外观态）；每帧每副本还要 1 次环内取样扫描 + `_in_water()` 网格查询。实测 8 人局这把客户端主循环压在 avg 16.7ms / p95 17.4~17.9ms（§5）。
- ★ 2026-10-30 全 60Hz + playout 2 的代价：16 人局服务端上行 ≈487 KB/s（trail 2 点；§1 表）；好处是样本间隔与画面滞后都只有 16.7/33ms，对手观感最接近本地玩家。

## 4. 边界

- `snapshot_size_probe` 的 N 折算表只到 N=8；16 人的每秒读数是由 schema 算术折算，不是探针产出。
- 抖动 / 丢包 / 命中缺口的真链路读数没有仪器：无丢包注入路径，无取图探针。

## 5. 多人局负载实测（2026-11-01；来源 = `tests/probe/royale_soak_probe.tscn`）

同配置（同一张 `newfactory` 图、同一机器人脚本、`--match=75 --run=105`），只改 `--clients=N`。**本机 20 逻辑核**；headless 客户端无渲染 ⇒ 下表量到的只是「网络 + 模拟 + 场景树」，**不含画面开销**；且 8 个 headless 客户端与 worker 同机跑，客户端帧读数含互相争用。worker CPU 取自进程 `TotalProcessorTime`（整局均值近似，含启动/收尾），「ms/tick」= CPU 秒 ÷ 局时长 ÷ 60。

| N | 单端下行（解码后 Dict KB/s） | 快照到达 p95 / max（ms） | 客户端帧 avg / p95 / max（ms） | worker CPU（单核） | 折算 ms/tick | C2 回滚 / 局（逐端范围） |
|---|---|---|---|---|---|---|
| 2 | 43.8~44.4 | 17.3~17.4 / 109~113 | 16.66 / 17.3~17.5 / 29~36 | ≈26%（23.9s CPU / 89.8s 局） | ≈4.4 | 7 |
| 4 | 82.2~84.3 | 17.4~18.0 / 135~1604 | 16.65~16.66 / 17.5~18.0 / 25~33 | ≈40%（单次 20s 采样窗口） | ≈6.7 | 7~117 |
| 8 | 160~165 | 17.3~17.9 / 118~176 | 16.66~16.70 / 17.4~17.9 / 52~199 | ≈53~61%（51.1s CPU / 83.6s 局） | ≈10.2 | 16~244 |

读数要点（按证据强度）：
- **快照到达 p95 在所有人数组都是 17.3~17.9ms** ⇒ 本机 worker 没有持续 tick 超时（60Hz 保持；偶发 max 一两个 100~170ms 的缺口）。
- **worker per-tick CPU 随人数近似线性上涨**：≈4.4ms@2 → ≈6.7ms@4 → ≈10.2ms@8（60Hz 预算 16.67ms/tick，8 人已花掉 1/4~2/3）。按此斜率 14~16 人会越过预算 ⇒ **云主机 vCPU 较弱 / 同机多个 worker 时，最可能先卡在服务器 tick**。这是「1v1 不卡、多人卡」最可信的产品侧解释。
- 单端下行带宽 ∝ N 但绝对值小（≈18 KB/s@8 线格式 ≈ (208B+99B)×60），**不是瓶颈**；服务器上行 ≈ 世界 208B×8×60 + 本人 99B×8×60 ≈ 147 KB/s（§1 表同口径）。
- **C2 回滚频率随「对手数 × 交火密度」上升**（2 人 ≈0.12/s、8 人 0.2~4.3/s）⇒ 多人局更容易被"拉回"是真实差异，但驱动量是对手/命中密度，不是代码分叉。
- 两跑 8 人局都出现 **t≈15.5s 的同步 >100ms 帧尖峰**（52~199ms，全部客户端同一时刻）。探针自身嫌疑最大：`soak_bot_input.PHASE_TICKS = 75` × 12 段 = **恰好 15s 一个脚本周期**，8 个 headless 客户端同相位、同机争用；**不作为产品证据**。
- `--clients=12` 在 20 核本机上跑不干净（有客户端赶不上观测窗 → 无 `ALL-OK`）⇒ 本探针的实际可用上限是 8 端/机。
