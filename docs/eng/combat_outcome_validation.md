# 完整受击预测验证

日期：2026-10-24。实测目录：`.test_logs/network/gns_combat_outcome_relay_8/`。

## 当前实现

- 服务端和预测共用 `CombatComponent.simulate_hit`，同时更新 HP、击退、无敌帧、冲刺取消、倒地碰撞与瞄准取消。倒地后的角色继续按倒地物理推进，不再生成新的射击动作或成为新的弹丸命中目标。
- `CombatPrediction` 按绝对 tick 和模拟阶段处理已知光束、弹丸与爆炸。`HIT` 携带命中后的权威 HP、朝向与击退向量，单条事件为 44 字节；本地弹丸已结束时，确认结果仍可独立重放。
- 完整 STATE 恢复角色、武器和输入基线，再重新模拟。错误的死亡预测可恢复为存活，并重放仍有效的移动与射击；战绩、掉落、地形和复活由服务端结算。
- 新 STATE、迟到的战斗事件与远端输入提示在物理帧开始统一应用。同批消息共用一次重放；已覆盖命中随 STATE 清理。音画反馈与逻辑重放分开，爆炸表现按攻击 ID 合并。
- 预测与确认共用攻击 ID、命中 tick、目标和来源。服务端确认的爆点与命中结果用于重放，同一次结果不重复施加伤害或冲量。

公开资料与证据范围见[大型游戏调研](combat_prediction_research.md)。

### 保存的 150 px 现场

角色 6 在 tick 1864 前剩余 1 HP，实际 4 点伤害应致死。保持存活的预测分支在 tick 1866 又接受了一次服务端不存在的重狙命中，产生额外强击退。

使用保存的角色状态、输入和远端提示，并在对应 tick 注入原日志两次接触向量：保持存活的受力分支复现 **150.384 px** 差异，与原保存位置相差 **0.000244 px**；完整致死状态分支与较新权威分支的端点差为 **0 px**。

这是针对该现场的因果对照，包含记录的接触向量；不是完整网络、毁后地形与弹丸几何的原样回放。

## 八人公网强制中继

一场八客户端、一个服务端的 Beta 大乱斗，实际战斗 **60.015 秒**，总运行 **67.656 秒**，包含一次 token 重连。官方 EasyTier 使用指定目录，连接三个公网 UDP 中继候选并轮换顺序，禁用 P2P。客户端无头运行。

| 最大非重置校正 | 91.869 px |

| 战斗期间 >50 ms 卡顿 | 0 |

| 完整战斗采样窗最大帧耗时 | 39.858 ms |

### 四次校正的原因

| 角色 / tick | 误差 | 核对结果 |
|---|---:|---|
| 8 / 817 | 33.275 px | 步枪开火与命中均在 tick 817；无提前命中预测，HIT 约 42 ms 后收到 |
| 8 / 877 | 32.935 px | 步枪开火与命中均在 tick 877；无提前命中预测，HIT 约 42 ms 后收到 |
| 8 / 921 | 33.276 px | 步枪开火与致死命中均在 tick 921；HIT 约 40 ms 后收到，随后恢复倒地分支 |
| 1 / 1266，INPUT 触发 | 91.869 px | 角色 4 新的左移与加速输入，从 tick 1267 起改变跨环面接触；本地已经预测到 tick 1273 |

前三次属于当前方案尚未获知的远端近距离新攻击，不能靠已知弹丸的预测提前裁决。它们不需要异常丢包或延迟尖峰才能出现，也不属于致死后再次接受假命中的缺陷。

最后一条使用保存的权威基线、输入与角色状态，对照未获知新提示和收到新提示两个分支，复现 **91.869 px** 差异；与原日志前后位置分别相差 **0 px** 和 **0.000488 px**。该实验使用原 arena 和默认时间账户，未恢复完整毁后地图；端点吻合验证了此处新输入改变预测接触的因果。

### 处理耗时与网络边界

31 次阶段卡顿集中在对局末段，相关重放为 11–20 tick，单次重放最大 21.507 ms。它们是本机预测处理超过物理预算，未按网络卡顿统计。该场没有 >50 ms 战斗卡顿，但较长预测窗口的重放成本仍有优化空间。

完全位于战斗内的采样窗口中，客户端原生 STATE 最大接收间隔为 100.949 ms，收包后队列等待最大 29.145 ms，主线程轮询间隔最大 33.335 ms。这些指标和 RTT 分别反映不同环节，不能互相代替。

本场没有独立的网络专用卡顿计量窗口，不宣称网络卡顿时间为零；无头结果也不代表八个可见窗口的 GPU 性能。

## 是否正常、是否应继续修复

预测重放本身是正常机制；可解释的预测失误仍可能产生需要改进的体验。`32 px` 是本项目的诊断分档，不是行业统一的合格线。当前站立碰撞宽度为 80 px，91.869 px 已超过一个角色宽度，不能仅因最终收敛就视为合格。

| 现象 | 判断 | 后续处理方向 |
|---|---|---|
| 三次约 33 px 的近距离受击校正 | 当前预测尚未取得新攻击信息；普通传输延迟就足以产生，未发现必须由异常网络解释的证据 | 应改善受击运动的时间安排。先区分伤害裁决 tick 与影响运动的生效 tick，评估一致调度的代价；不能承诺提前知道远端尚未传来的新开火 |
| 一次 91.869 px 的加速碰撞校正 | 新输入改变了对手未来位置和阻挡结果，保存现场已复现。已知输入下的分支对齐，不代表这种大跳变可接受 | 应作为角色交互预测问题继续处理，重点是高速双方接触及输入到达时机；保留实体阻挡意味着仍需承担未知远端操作的预测风险 |
| 31 次处理阶段超过 16.667 ms | 是本机 CPU 预算超支。较长的重放窗口增加计算量，网络延迟可能放大负载，但不能把实际计算耗时记为网络卡顿 | 应定位八角色重放、碰撞查询及重复工作的耗时，保持模拟结果一致地优化。没有 >50 ms 卡顿不等于没有性能问题 |

公开资料支持这一分法：

- Riot 的 [VALORANT 网络设计](https://www.riotgames.com/en/news/peeking-valorants-netcode)把合理网络下避免模拟分歧、不可避免时降低影响列为目标。它没有提供适用于本项目的像素阈值。
- Valve 的 [CS2 2024-08-14 更新](https://store.steampowered.com/news/posts/?appids=730&enddate=1724364740&feed=steam_community_announcements)通过略延后受击减速减少被击中时的瞬移，同时明确代价是受击后短暂保持全速。这说明修复可能涉及权威效果的时序，而不只是客户端画面插值；该资料讨论的是减速，不能直接证明适用于本项目全部击退与死亡规则。
- Psyonix 的 [Rocket League 网络演讲](https://media.gdcvault.com/gdc2018/presentations/Cone_Jared_It_Is_Rocket.pdf)第 176 页说明其他车辆的运动更难预测，重放校正有计算成本。它说明问题的普遍性，不构成接受本项目 91.869 px 跳变的依据。
- Epic 的 [Networked Physics Overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/networked-physics-overview)说明重放所需历史会消耗 CPU 和内存，较高延迟与速度会降低交互质量。当前 Godot 实现的实际热点仍须按自身测量判断。

当前结论：旧的致死后假命中属于已定位的逻辑缺陷；本次剩余四条是已解释的交互预测分歧，仍有改进价值。不能宣称所有剩余问题均由网络波动造成。优先处理可测量的重放成本与接近一个角色宽度的碰撞跳变，再评估受击运动时序。
