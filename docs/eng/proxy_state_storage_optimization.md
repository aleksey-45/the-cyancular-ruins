# 代理轨迹与快照复制优化

2026-10-28。承接[14.949 ms 客户端物理回调分析](server_fanout_optimization.md#14949-ms-物理回调成本复核)。本轮处理代理状态序列化、STATE 重复复制和历史元数据构造；没有改变预测窗口、权威优先级、影响审核或接纳调度。

## 实施

### 连续原生代理轨迹

`NativeMotionTrack` 为每份权威锚点保存 `std::vector<ActorMotionState>`，按现有 `MOTION_HORIZON` 预留容量。首次接纳解析网络字典；生成轨迹和恢复样本直接使用原生成员。批量应用同时设置运动、碰撞姿态、只读权威 HP/氧气、锁定与过期停止状态。

运动字段由 `motion_fields.inc` 统一列出。原来的 `capture_motion_state` / `restore_motion_state` 与原生轨迹共用该字段定义，避免两份状态清单发生遗漏。替换了旧的 `extend_motion_samples` 字典轨迹接口。

`PlayerReplica` 仍负责锚点选择、区域失效审核和已知回溯路径；通常请求最新锚点，因此改为从尾部查找。服务端按角色顺序移动前后的两个代理采样阶段保持原语义。Godot 仍管理物理节点、形状和即时物理查询。

计数拆分为 `proxy_motion_initializations` 与 `proxy_geometry_invalidations`：新 STATE 首次建轨迹不再被记录为已有几何缓存失效。旧日志仍按旧语义解释。

### 解码历史的所有权与按需复制

旧路径先深拷贝整个基线 world，重建字段增量，再深拷贝 frame 保存历史。改为：

1. 内部历史的记录只读；新的 world 只复制一层索引。
2. players、pickups、projectiles 的变化区块先复制其索引表；修改的实体记录由原解码器重建，不改旧记录。
3. 没变的 own、time 和实体记录在内部历史间共享；time 变化时只复制其索引和变化账户。
4. 保存已拥有的内部 frame，最后对外深拷贝一次。调用方仍获得完整可修改快照，与全部旧基线和其他解码结果隔离。

没有删除外部快照隔离，也没有修改协议字节布局、ACK、丢包基线、控制阶段或事件屏障。当前仍保留一次对外完整深拷贝，以及字段解码所需的局部复制。

### 历史的低频元数据

`NativePredictionHistory` 在远端配置相同时复用配置；逐 tick 采集时检测回溯模式、碰撞层和对象有效性。模式、复活 tick、碰撞层或成员变化才构建新的元数据表；旧表及其中的模式数组设置为只读。更新采用替换容器，不能 clear/修改已经发布给旧检查点的容器。

角色位置、接触、弹丸、本地账户和输入游标仍逐 tick 保存。对象使用实例 ID 检查存活，角色销毁不会成为强引用或留在新检查点中。

## 已完成的固定数据比较

产物位于工作区 `work/proxy_motion_storage_20261027/`。其中 `before/` 保存本轮开始的源码和 DLL；`comparison_sources.json` 标识参与比较的代理脚本和库；`performance_summary.json` 保留原始 us。

该轮比较只覆盖上面的代理轨迹存储修改，发生在解码复制与历史元数据修改之前，不能作为最终三项修改的综合收益。

两个负载：

- 从已有八人对局提取的角色状态出发，按固定审核/重放阶段执行 140 次代理采样，实际生成 42 步。每一阶段的运动字段、姿态、HP、氧气、倒地/回溯、碰撞框、层、查询 tick、过期状态与修改前严格一致。这是固定请求模式，未复现原峰值帧的全部消息和地形时序。

A/B/B/A，每个进程预热 3 次，测量 30 次；每侧各 60 个样本。Release 原生扩展、FrameTrace 关闭、持续排空 stdout PIPE。计时不含逐阶段结果比较，也不含 setup 和清理。下表为墙钟时间，us 除以 1000 后展示为 ms：

| 140 次代理采样 / 42 步生成 | 2.8385 | 2.1370 | 4.248 | 2.958 |

### 最大循环区间：没有重放

`client1` frame 3166，UTC 18:07:01.900594（本地 02:07:01.900594）结束：

- 59.119 ms = 普通节点 1.333 ms + 物理节点 27.587 ms + 外层 span 覆盖外 30.199 ms。
- 物理回调中只有一轮权威接纳，前缀完整复用，重放为 0，正常推进 1 tick。
- 正常预测区间 13.455 ms，其中该步 `prediction_step` 为 13.116 ms；单次 `proxy_sample` 为 10.326 ms，其余采样远小于它。
- 整帧已计量观察器成本 0.166 ms，不是全部测量开销的上限。

因此这一次最大循环间隔不能解释为重复重放。30.199 ms 覆盖外区间也不能直接当 CPU 时间或全部当睡眠。单次代理采样的墙钟尖峰缺少原生调用内的线程 CPU 数据，不能断定都在积分或分配。

### 最大物理回调：重放本身只占 3.412 ms

`client2` frame 2273，UTC 18:06:47.084122（本地 02:06:47.084122）结束：

- 单次物理回调 29.625 ms，整段循环 43.069 ms。
- 收包/预处理/派发 1.900 ms；权威批次外层 20.576 ms；正常预测外层 6.786 ms；其他节点和边界 0.363 ms。以上互不重叠，总计 29.625 ms。
- 权威应用内部 7.905 ms，包含两步重放 1.638 + 1.774 = 3.412 ms。
- `authority_apply` 结束后到权威外层结束另有 12.652 ms；权威事件打点之后仍有 12.592 ms。这里包含函数返回、状态清理和未细分代码，不能归给已计时的重放步骤。
- 正常预测进入实际步骤前 4.693 ms，实际一步 2.064 ms，步骤后 0.029 ms。
- 49 次代理采样合计 1.932 ms、历史保存 0.590 ms，地形碰撞分块重建为 0。这些子区间不能再加到外层耗时上。

本场还有三个客户端出现 23 tick 的事件后缀重放，其对应物理回调约 12.270～14.963 ms，循环间隔约 18.797～20.846 ms，并非两个最大尖峰。它们说明不能只按重放 tick 数推断耗时；本场没有进一步判定这些事件重放是否必要。

### 并发与记录影响的证据边界

最大循环区间附近，其他多个进程也有不同阶段的墙钟升高，例如 `client7` 循环 43.680 ms、`client6` 循环 31.725 ms，服务端循环 28.714 ms。最大物理回调附近，`client3` 的单份 STATE 解码为 9.908 ms，`client5` 为 6.659 ms。这是同时间附近的相关现象，不能单凭时间接近认定其原因相同。

`client4` 另有三条 GNS 性能告警，分别报告持锁 7.9、7.5、6.4 ms；告警文字提到线程饥饿可能性。其发生时间与上述两个峰值不相同，不能用来直接解释两个峰值，也不是网络 RTT 波动的证明。

`client6` 的 FrameTrace 后台记录线程有一次写盘批次墙钟耗时 823.446 ms。其累计最大值首次在 frame 2628 观察到，前一帧待写队列为 48 条；主线程仍继续产生帧，观察到更新的帧间隔为 27.745 ms，丢记录为 0。不能把后台写盘时间称为主线程停顿，但也不能排除记录线程、文件系统和整机并发对测量的间接影响。服务端 GameLog 队列峰值 140 条，最终各进程采样待写量均降至 2～3 条，没有观察到持续增长。

本次仅测试及读取现有日志，没有继续修改调度或追加测试。尚需区分的成本集中在权威应用尾部、正常预测进入步骤前，以及个别采样/解码的墙钟尖峰；当前证据不足以把它们全部归为模拟计算、日志、锁竞争或 OS 抢占中的任何一项。

## 59.119 ms 的引擎阶段复核

用户质疑 59.119 ms 后继续分析同一份记录，没有重跑。原始 `start_us=55510079`、`end_us=55569198`，帧号连续为 3166→3167；并非多帧求和。GameLog 独立的普通回调间隔也记录了 59.164 ms，支持该墙钟间隔确实发生，而非 FrameTrace 汇总加错。

| 相对于 frame 3166 起点 | 区间 | 墙钟 ms |
|---|---|---:|
| 0～1.333 ms | 普通节点回调 | 1.333 |
| 1.333～13.878 ms | 上一轮节点回调之后至下一轮 physics_frame 打点，含帧尾、限帧等待及下一物理阶段准备 | 12.545 |
| 13.878～41.465 ms | 节点物理回调，含网络、权威审核和正常预测 | 27.587 |
| 41.465～59.119 ms | 节点物理回调之后至 process_frame 打点 | 17.654 |

关键修正：`physics_nodes` 不是整个 Godot 物理阶段，不能把它后面的时间笼统归为限帧等待。按本机引擎版本 `a13da4feb` 的 [SceneTree::physics_process](https://github.com/godotengine/godot/blob/a13da4feb/scene/main/scene_tree.cpp#L596)，节点回调之后还会执行组调用与消息队列、物理定时器/补间、变换通知、删除队列和 idle callbacks。[Main::iteration](https://github.com/godotengine/godot/blob/a13da4feb/main/main.cpp#L4632) 随后继续导航、消息队列、PhysicsServer2D/3D 的 end_sync 与 step、iteration_end，之后才进入普通 process_frame；常规帧率等待在整个循环的后面。

从节点物理起点到下一 process_frame 打点为 **45.241 ms**。随后同一个客户端的每秒 performance 记录给出引擎物理阶段窗口最大值 **45.243 ms**，两者高度吻合。该 monitor 是窗口最大值，并非带同一 frame ID 的逐帧计时，因此这是强对应证据，不把 2 μs 差额解释成某个具体函数成本。

另一条 frame 3469 也印证此盲区：循环 55.126 ms、节点物理 12.269 ms、节点之后 33.565 ms，两者合计 45.834 ms；随后引擎 monitor 的物理峰值为 45.838 ms。两次均无重放。不能以节点物理回调小于 30 ms 推断整个引擎物理阶段也小于 30 ms。

对单个物理回调的帧进行全场对照，client1 的节点后区间中位数仅 **0.247 ms**、P99 **1.264 ms**，5,396 个样本中超过 5 ms 的有 8 个。因此 17.654/33.565 ms 是离群尖峰，不是正常固定的额外等待。各客户端对照见工作区 `tail_gap_analysis.json`。

27.587 ms 节点区间本身可无重叠拆成：网络收包/预处理/派发 3.493 ms、权威接纳 9.609 ms、正常预测 13.455 ms、其余节点/边界 1.030 ms。权威完整复用，重放为 0。正常一步的本地角色为 0.487 ms、弹丸阶段为 0.334 ms、历史为 0.343 ms；异常主要表现在单次代理采样 10.326 ms，以及审核中的未细分间隙。

按 `_sample_proxies` 的稳定角色顺序和当前本地 role=2 推断，该 10.326 ms 样本是正常步进移动前的 role=8 查询，目标 tick=3083，与权威审核最后恢复的代理 tick 相同。它应复用已经存在的运动样本，而非新增积分；即使代理正在播放已知回溯路径，也不需要调用普通运动核生成该 tick。日志没有逐调用的角色与缓存分支标记，所以保留为根据代码顺序的推断，不能把 10.326 ms 标成已测得的原生积分成本。

源码继续缩小了候选范围：Godot 2D [stepper](https://github.com/godotengine/godot/blob/4.7-stable/modules/godot_physics_2d/godot_step_2d.cpp#L224) 在约束准备和求解阶段会向 WorkerThreadPool 提交任务并等待；物理节点后的工作也包括变换、删除和延迟消息处理。因此“物理阶段墙钟很大”仍可能包含线程等待/被抢占，不能直接等同于碰撞计算 CPU 时间。九个 Godot 进程及各自隧道、网络与记录线程的并发，和多进程在不同阶段同时出现尖峰，是应检查线程等待的理由，并非已确认的根因。

已计量 FrameTrace 观察器在该帧为 0.166 ms；GameLog 相应窗口的入队最大值为 0.188 ms。它们不足以解释 17.654 ms，但也不覆盖后台竞争和全部记录工具成本。后台写盘 823.446 ms 与 GNS 持锁告警发生在不同时间，不能直接拿来解释这一帧。

结论已经比“可能是等待”具体：存在约 45 ms 的引擎物理阶段墙钟尖峰；此前只测节点回调，遗漏了引擎物理尾部。尚未确定延迟队列、变换/对象清理、PhysicsServer 步进及其工作线程等待各占多少。后续需要覆盖这些边界并配合线程 CPU/等待记录，不能再仅靠回滚 tick 数或继续修改网络重放调度来归因。

### 10.326 ms 样本为什么值得优先检查

根据 `_sample_proxies()` 的角色排序，本地 role=2，对手顺序应为 1、3、4、5、6、7、8。审核最后已按 tick 3083 采样全部代理；随后正常推进至 tick 3084，移动前 role>2 的对手仍读取 tick 3083。因此第 7 次调用按代码顺序应为 role=8 再次读取已有的 3083 样本，而非生成新运动步骤。记录没有逐调用的 role、tick、命中分支，所以仍将此保留为代码推断。

普通缓存路径只需从最多 32 个锚点中倒序选取、读取原生样本数量、比较轨迹及采样索引，并更新查询元数据。相同采样索引和数据时不再执行 `motion.apply()`；`NativeMotionTrack::size()` 只读连续数组长度。`_ghost` 的碰撞层设置器直接写原生成员，`_forecast` 为顶层节点，不需要沿父节点层级计算全局位置。该路径没有显式等待网络、睡眠或玩法重放。因此不能把 10.326 ms 直接解释为 C++ 运动积分、反射的稳定成本或网络 RTT。

### 已缩小范围，尚未证明具体等待源

目前更应调查调用途中的偶发执行延迟：线程未获运行时间、原生内部同步或分配/回收等。附近其他进程在表现、代理采样或广播等不同阶段也有墙钟升高，是并发影响的线索，不是同一原因的证明。九个 Godot 进程及其工作线程、隧道和记录线程是候选竞争来源，不能仅凭进程数量认定 CPU 已饱和。

记录工具仍在调查范围内：此帧 FrameTrace 已计量开销为 0.166 ms，GameLog 相应窗口的入队最大值为 0.188 ms；前者只计量部分内部操作，不覆盖全部调用边界，也不覆盖后台记录引发的间接竞争。代理缓存路径没有直接调用 `GameLog.record()`，但有 FrameTrace 打点。现有数字不足以认定日志导致尖峰，也不足以排除测量影响。
