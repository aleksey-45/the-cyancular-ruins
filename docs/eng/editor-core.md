# 编辑器格式核心层（`level_editor/core/`）

> 本文件接收从 `level_editor/core/` 那 12 个分片注释里**搬出来**的推导、实测读数与完整契约
> （按 [`comment-style.md`](comment-style.md) §8：注释超额时，过程与推导进域文档，原处只留一行指针）。
> ★ 文档会过期 —— **任何冲突以源码为准**，读之前先 `grep` 复核。返回索引：[`CLAUDE.md`](../../CLAUDE.md)。

## 1. 分片与加载顺序

- 12 片按**文件名字典序**加载，`NN_` 前缀就是顺序。**顺序的真相源是 `level_editor/editor.html` 的 `<script src>` 列表** ——
  node 侧的 `level_editor/loader.js` 从同一个地方读，不另抄一份。
- `level_editor/worker.js` 的 `importScripts` 列表必须与页面加载的 core 分片**逐项相同**：只错这一处时页面照常，
  **只有编解码在浏览器里死**，node 侧一条断言都看不到（`parts_check.js` 守这条）。
- 分片在**一个共享作用域**里求值（经典 `<script>` 共享同一个顶层词法环境），所以分片之间能直接引用彼此的顶层声明；
  代价是**顶层名不许重名** —— 重名即静默覆盖，`var` / `function` 那条连错误都不报。
- ★ **core/ 是纯逻辑**：不引用任何 DOM API，必须能被 node 直接 `new Function(src)()` 求值（`smoke.js` 就是这么跑的）。
- 末片恒为 `99_exports.js`：公开 API 表只在它里面，改它等于改公开接口。

## 3. `MAX_BODY_SIZE = 64MB` 是怎么来的

**它堵的是 deflate 炸弹**：deflate 的单流最大压缩比约 **1032:1** ⇒ 几十 KB 的恶意／损坏文件就能解出 **GB 级**内存。
它**完全不碰头部字段**（magic / 版本 / 尺寸 / CRC 全合法），所以 `decodeBody` 里那条「按 body 实际余量反推格数上界」
的检查对它**天然无效** —— 那条管的是「头部声称的尺寸大于 body 装得下的量」，炸弹是反过来的：**声明的 body 很小、解出来极大**。
故必须拿「头部声明的解压后大小」单独设一道闸，且判在**任何解压动作之前**（判在解压之后等于拒是拒了、内存已经先分配出去了）。

**64MB 是怎么算出来的 —— 合法文件最坏就多大**：上限尺寸 400×300 格 = 1600×1200 子格，即 `n = 1,920,000`；四层全在、且全都取到最坏编码：

| 段 | 最坏字节数 | 约 |
|---|---|---|
| 背景层（颜色） | `1 + 4n` = 7,680,001 | 7.68MB |
| 三个纹理层各 | `1 + 2 + 4×65535 + 1 + 2n` = 4,102,144 | 4.10MB ×3 ≈ 12.31MB |
| meta | `2 + 65535`（u16 长度字段的上限） | 0.07MB |
| **合计** | **20,051,970** | **≈ 19.1MiB** |

取 64MB（67,108,864）= 上表的 **≈3.3 倍**：对**任何**合法文件都不可能误拒，对炸弹则是一道明确的硬闸。
这条余量本身有断言钉住（`smoke.js`：`MAX_BODY_SIZE > 20MB`），有人把常量调小到会误拒合法大图时会直接红。

★ **这个常量今天用在两道闸上，两道都不可省**（只留一道就会漏掉半个炸弹面）：

1. `decodeMap` 里比对「头部声明的 `body_size`」—— 挡**声明侧**的炸弹（头部就写着 2GB）；
2. `inflateBytes` 的 `maxBytes` —— 挡「谎报声明 + 真炸弹」（声明很小、解出来极大），它是作用在**实际输出**上的那一道。

## 4. 为什么上界必须作用在**实际输出**上

- **不能只靠文件头里的 `body_size`**：那个字段**本身也是攻击者可控的**。把它谎报成一个能通过闸门的小值（比如 4096）、
  而 deflate 流里塞真炸弹，则「判在解压之前」那道闸完全挡不住 —— `new Response(stream).arrayBuffer()`
  会**先把整份解压结果分配出来**，判在后面的长度比对处等于拒是拒了、内存已经花掉了。
- **量级**：DEFLATE 单流最大压缩比 ≈ 1032:1 ⇒ 64KB 的 `.cyrm` 能解出 ≈64MB、1MB 的能解出 ≈1GB
  （`arrayBuffer` 的峰值还约等于输出的 2 倍）。**结果无界、输入有界。**
- **上界传的是 `bodySize` 而<u>不是</u> `MAX_BODY_SIZE`**：合法文件的解压结果**恒等于** `body_size`
  （`decodeMap` 里那句长度比对就是它），所以 `bodySize` 是**精确**上界、不会误拒任何合法文件；
  而 `MAX_BODY_SIZE` 只是「任何合法文件都不可能超过」的松值。拿松值当这道闸，「谎报 body_size + 真炸弹」
  要靠**真解压出 64MB** 才被拒（拒是拒了，那 64MB 已经花掉了）；换成 `bodySize` 后大约 **4KB** 的解压结果 + 一个 chunk 就能拒。
  安全边界不该比它需要的宽 **16000 倍**。

## 5. `inflateBytes` 的 `cancel` 为什么是 fire-and-forget

- 旧写法 `return reader.cancel().then(throw, throw)` 把「抛不抛得出来」押在 `cancel()` **会不会 settle** 上 ——
  它若不 settle（实现差异／流已进错误态），这段代码就不是抛错，而是**这条路永远不 settle**。
- **实测**：旧形态配一个永不 settle 的 `cancel`，会让 node 在**跑到一半时静默退出、退出码 0、
  连 `结果:` 行都不打**（未决 promise + 事件循环空转）。只看退出码的话，那是完美的假绿。
- **结论**：取消只是「别继续解压」的礼貌动作，不该挂在安全路径上 —— 所以是**先抛再 cancel**，
  且 `cancel().catch(function () {})` 只做善后。

## 6. `decodeMap` 对外保证什么、不保证什么

「解码一份来路不明的 `.cyrm` 能得到什么」此前在代码里没有答案，只有一串散在各处的 `throw`。
写在这里，免得下游（渲染端／迁移端）误以为拿到的是一份"已校验过"的数据。

**保证**（不满足就 reject，绝不静默返回一张残缺的图）：

1. 头部合理性：长度 ≥ 20、magic === `"CYRM"`、version === 4、`compression ∈ {0,1}`；
2. 尺寸合理：`sub_cols` / `sub_rows` > 0 且都是 `SUB_PER_CELL` 的倍数；
3. 解压闸门：头部声明的 `body_size ≤ MAX_BODY_SIZE`（判在解压之前），且解压的**实际输出**不超过 `body_size`；
4. body 长度精确：解压后字节数 === 头部声明的 `body_size`；
5. CRC 相符：算得的 CRC32 与头部字段逐位相等（CRC 只覆盖 body，**不覆盖头部**）；
6. body 全消费：解完四层后剩余字节必须是 0（尾部多余字节 = 文件坏了）；
7. 索引与调色板边界：调色板非空、`index_width ∈ {1,2}`、每个索引都 `< palette_count`；
8. 每层分配前的粗筛：头部尺寸反推出的格数不得超过该层剩余字节能装下的量。

**不保证**（下游要自己判，今天靠 `validateMap` / 渲染端）：

- 调色板 `[0]` 是空气（规格把它列为**编码端**义务，解码端不代偿）；
- 描述符的纹理位 ≤ 22、或纹理 0 与整体 0 一致（「0 ≡ 空气」这条不变量在解码侧**不**成立，见 §8）；
- 尺寸在上限内（`MAX_CELLS_W/H` 是**编辑器**的输入钳制，不是格式的边界条件，见 §11）；
- 出生点／敌人坐标在地图内、或落在非实心格里；
- `sub_cols` / `sub_rows` 与 body 里实际排布的子格数一致（那由第 ⑧ 条粗筛兜底，不是精确校验）。

## 7. 调色板与索引

- ★ **索引 0 恒为空气**：即使本层一个空气格都没有，也要占住第 0 位，这样「空图 = 调色板 `[0]` + 全 0 索引流」
  是一条**无条件成立**的不变量。解码端对空调色板是**硬拒**（`decodeTexLayer` 的 '调色板为空'），所以第 0 位不能省。
- **u16 上界的推导**：`palette_count` 是 u16，能表达的最大值就是 65535；而判上界那一刻的 `p` 是**加入该项之前**的
  `pal.length` ⇒ 加入后 `pal.length === p + 1`，故合法条件是 `p + 1 ≤ 65535` 即 **`p ≤ 65534`**。
  写成 `p > 65535` 会放行**恰好 65536 项**的调色板：紧接着的 `w.u16(65536)` 按位截断成 0，
  产出的是「本文件自己的解码器当场拒绝（调色板为空）」的 `.cyrm` —— 即「导出后再也导不回来」那一类缺陷的逐字翻版。
- 错误信息里的数字必须与实际限值一致（**65535 = u16 上限**，不是 `p` 的上限）。

## 8. descriptor 位域与 `isAir` 的适用域

位域（规格 §2.3）：

```
descriptor (u32)
  bit  0- 2   hue          0-7
  bit  3- 5   brightness   0-7
  bit  6- 8   saturation   0-7
  bit  9-11   alpha        0-7
  bit 12-23   texture      1-4095   (0 = 空气)
  bit 24-31   保留，固定 0
```

★ **三列的中性档不在同一行**：hue / brightness / saturation 的中性在**档 4**，alpha 的中性在**档 7**
（`neutralDesc` 拼的是 `(4, 4, 4, 7)`）。档位含义表与像素数学定义见规格 §2.3。

**`isAir(d)` 的适用域**（这条决定了它能不能被下游用）：

- `isAir(d)` 判的是**整体等于 `DESC_AIR`（0）**，只对**本编码器产出的**数据可靠：`packDesc()` 保证空气恒为 0，
  `decodeTexLayer` 又原样回读自己写进去的调色板项，所以"自己导出、自己导入"这条闭环里 `isAir` 是对的。
- 读**外来**文件时唯一的空气判据是 **`texOf(d) === 0`**（按纹理位域取值）。一个「辅码非 0 而纹理为 0」的畸形描述符
  （如 `0x000007FF`）会让 `isAir(d) === false` 与 `texOf(d) === 0` 得出**相反**结论，而 `decodeMap` /
  `decodeTexLayer` 当前**不**归一化来路不明的描述符（它是原样穿过编解码的）。
- 两种收口方式（在 `decodeTexLayer` 里加一行归一化 / 取消导出 `isAir` 并声明 `texOf(d) === 0` 是唯一判据）
  **都要动公开接口**，属接口决定 —— **尚未选**，留给控制器 / 计划 2 定。

## 9. v3 文本 / 旧字母格式

- ★ **`packed = texture*16 + shape` 是 v3 的编码**，与 v4 的 descriptor 毫无关系。故一律走
  `_v3Pack` / `_v3TexOf` / `_v3ShapeOf`，绝不与 `packDesc` / `texOf` 混用。
- **版本标记行的唯一谓词**：`isV3Text` 与 `parseV3Text` 两处都必须走 `isV3MarkerLine`。
  规格 §3.6 的规范写法是 `# cyrm-v3`，实现比字面**稍宽**（容许 `#cyrm-v3` 这种无空格写法、也容许行尾还跟着别的字，
  如 `# cyrm-v3 (demo)`）。宽严本身不是重点，**重点是两处必须同宽**。此前两处各写一份且不等价
  （跳过用 `/^#\s*cyrm-v\d+\s*$/`、识别用 `indexOf('# cyrm-v3') === 0`），于是两种输入一头一尾各错一半：

  | 输入 | 旧后果 |
  |---|---|
  | `#cyrm-v3` | 被跳过、却**不被识别为 v3** ⇒ 网格掉进旧字母格式（报错／错位） |
  | `# cyrm-v3 (demo)` | 被识别为 v3、却**不被跳过** ⇒ 标记行落进 comments，污染往返 |

- **旧字母格式的宽高必须都是 ≥2 的偶数**（它靠 2×2 折叠成 1 格）。此前直接交给 `Math.floor(h/2)` / `Math.floor(w/2)`，
  后果有两档：单行输入会抛**裸 TypeError**（读 `undefined.length`）；宽 3 × 高 4 会返回 1×2 格、
  **一句话不说地永久丢掉两整列**。而按规格 §3.6 迁移是**单向**的（迁移后不再导出文本），吃掉的东西找不回来。
- **旧 2×2 字母网格 → 1 格 packed**：纹理取组内首个非零，形状 = 2×2 掩码；逻辑与游戏侧 `MapFormat.convert_old_grid` 逐字对应。
  旧字母表只认 `0-9` 与 `A`（大小写均可），与游戏侧 `_tile_char_to_value` 一致。
- **meta 文本形状**（规格 §3.2）：就是那几行 `# ...` 注释，deflate 压得掉，而且游戏侧 `MapFormat.parse_spawn_metadata()`
  零改动就能继续用。输出顺序：先注释，再出生点（`player` / `player2` / `player3`…），最后敌人。
- **解析失败的行降级成注释而不是丢掉**（含坐标不是整数、坐标个数不够）—— 本模块的绑定约束是
  「编辑器不许静默吃掉用户写的东西」。整数判定必须是**整数字面量**（`/^[+-]?\d+$/`）而不是 `isFinite`：
  `parseInt('3.5')===3` / `parseInt('7abc')===7` / `parseInt('1e3')===1` 全都不是 NaN，只判 `isFinite`
  会把 `# player 3.5 4` 静默改写成 `# player 3 4`，原文被吃掉。
- **v3 → v4 迁移**（规格 §3.6）：旧掩码 bit `(qy*2+qx)` 为 1 → 新网格的 4 个子格 `X∈[2qx,2qx+1], Y∈[2qy,2qy+1]`
  填同一纹理；spawn 坐标同步 ÷2。配合 §10 的取角映射，这保证迁移后**视觉逐像素不变**：旧的那块 32px 区域
  由 4 个 16px 子格拼回，每个取到的正是原来那 8px 象限放大 2×。前 / 后 / 背景三层留空 —— v3 里没有它们。

## 10. 取角映射（`subcellRender`）

子格全局坐标 `(X, Y)` → 目标矩形（世界像素）+ 源矩形（贴图块内偏移）；调用方按 `(texture-1)` 定位贴图块，再加这里的 `src` 偏移。

- `dst: [x, y, w, h]` 世界像素，**恒为 16×16**；
- `src: [x, y, w, h]` 贴图块内偏移，**恒为 8×8**；
- ★ 象限由子格在 64px 格内的位置决定（`X % 4` / `Y % 4`），**不是存在数据里的字段** —— 每个子格要能独立推出自己该画哪一块。

★★ **调用方约束：`X` / `Y` 必须非负，调用方自己 `posmod`**。JS 的 `%` 保留被除数的符号，`X = -1` 会得到 `qx = -1`
⇒ `src[0] = -8` —— 落在贴图块外；而本函数**不做**任何归一化（也不该做：归一化是"负坐标该绕到哪一格"的**环面语义**，
属于调用方的世界模型，不是本函数的事）。负坐标请先用 `posmod(X, subCols)` 之类绕进 `[0, subCols)` 再调；
本函数不抛错、只会安静地给出**错误的源矩形**。

## 11. 尺寸上限与校验

- `MAX_CELLS_W = 400` / `MAX_CELLS_H = 300`（规格 §4.3 闸 1）。**为什么要有硬上限**：旧编辑器的
  `clampMin(v, min, def)` 第三参是"非数字时的默认值"而不是上限，输 99999 就会去分配一张巨图、卡死浏览器。
- 用户输入一律**钳制**而不是报错回滚（输 99999 变成 400）；缺省 `125×75`。
- ★ `MAX_CELLS_W/H` 是**编辑器**的输入钳制，**不是格式的边界条件** —— 格式只要求 `subCols` / `subRows` 是 4 的倍数。
- **导出前校验只报告、不阻止导出**（规格 §4.7）：`errors` = 真正非法，导出去就是坏文件；`warnings` = 能导出，
  但游戏里大概不按你预期跑。`encodeMap` **只拒 `errors`** —— 拿 `warnings` 拦导出就是把"只报告"变成"阻止"，
  编辑器不该替用户做决定。
- `encodeMap` 必须先跑一遍 `validateMap`：`decodeMap` 在尺寸／图层长度上是**严格**的（非 4 倍数、图层长度不符一律拒收），
  而 `encodeMap` 若不校验，一张 `subCols` 非 4 倍数的图能编码成功、产出的文件却连本编辑器自己都读不回来
  —— 又一个「导出后再也导不回来」。

## 12. 头部前向兼容（有意为之，别加校验）

`reserved` 字节与 `layer_flags` 的 bit4-7 一律**读掉不判**：今天写侧恒写 0（`encodeMap` 里 `w.u8(0)`、
`layerFlags` 只看 bit0-3），读侧刻意只认低 4 位。这是**有意的前向兼容** —— 将来若在头部扩字段
（多出的图层／新增元信息），老编辑器读新文件时降级成"忽略"而不是当场拒收。
故**不要**加 `reserved === 0` 或 `flags & 0xF0 === 0` 的校验：实测 `reserved = 0xAB`、`layer_flags = 0xFF`
的头部今天都能正常解码，那是有意为之。

★ **闸门顺序**：`decodeMap` 必须**先判头部声明的解压后大小、再碰 payload** —— 解压是把攻击者给的字节变成内存的
**那一步**，判在它后面就等于没判。★ **零守卫**（2026-10-15 订正）：`smoke.js` 里那组"读源码比位置"的断言
（闸门必须早于 `inflateBytes(payload…)` 的调用点）已按 D6 删掉 ⇒ 把闸门挪到解压之后**不会变红**；
行为侧剩下的只有"头部声明的 `body_size` 超限必须拒"（期望子串 `64MB`），它**钉不住位置**。
