## 代码因果链

1. `AuthorityWorld._physics_process` 立即执行 `Player.execute_actions`。
2. `WeaponBase._spawn_projectiles` 按弹丸实例化场景，逐项设置属性并挂到服务端场景树。
3. `AuthorityWorld.add_projectile` 立即广播出生；`RoomSession._broadcast` 按接收者逐次调用 `NetBus.send_event`。
4. `send_event` 每次重新 `encode_event`、添加传输头并发送。相同事件向八名接收者发送时，公共载荷编码也做八遍。
5. 每次发送另写一条 `net_event`。`GameLog.record` 在调用线程中构造时间、JSON 字符串并持锁入队；后台线程负责写盘。后台写盘没有移走主线程 JSON 成本。
6. 接触结算中，每次命中又执行 `combat_impact`、`combat` 和逐接收者 HIT 发送/日志。

因此该类峰值的主要已证实问题是射击后的节点管理、事件扇出与主线程日志；正常角色模拟核不是这个样本的主要热点。节点实例化的独立成本尚未单独计量，不能用 `execute_actions` 的完整时间代替。原始 18.107 ms 中各函数的线程 CPU 时间也没有采样证据。

下一步应优先评估公共事件一次编码后扇出、按有序批次发送、聚合同类传输诊断，以及批量弹丸装配。BASELINE 会修改每个连接的 codec 状态，不能把所有事件都不加区分地共享编码。保持命中顺序、可靠事件语义及每个连接状态是前提；本轮调查只新增计量，没有修改协议、伤害或执行顺序。

## 13.7 ms 空档与画面停顿的含义

测试 runner 明确给服务端传 `--max-fps 60`。Godot [主循环源码](https://github.com/godotengine/godot/blob/4.7-stable/main/main.cpp) 先执行物理，再执行普通 process，最后调用限帧等待；[OS::add_frame_delay](https://github.com/godotengine/godot/blob/4.7-stable/core/os/os.cpp) 根据目标节拍与当前时间决定 sleep。

原始记录从上一轮 `process_frame` 起算：13.694 ms 后进入下一轮物理回调，18.107 ms 后退出，再过 0.351 ms 到下一个 `process_frame`，合计 32.152 ms。前一个物理回调只有 2.783 ms，限帧等待解释了空档的主要部分；未在引擎内直接计量 sleep，不能把全部空档精确归为主动等待。

物理任务已经在下一轮主循环执行，没有证据表明被提前插进上一轮。这个顺序正常；计时边界跨过了主循环边界。32.152 ms 表示两次 process 信号之间的间隔，18.107 ms 表示物理节点回调区间。

该服务端间隔不代表玩家画面停顿同样久。客户端独立预测与呈现，同一时间八个无头客户端的主循环间隔最大约 21.2 ms。本场没有真实屏幕呈现记录，不能据此判定玩家看到或没看到一次 30 ms 的画面停顿；实际呈现间隔需要有画面的客户端数据。
