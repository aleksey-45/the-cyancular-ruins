# 大乱斗模式压力与长时间稳定性测试报告 (2026-09-12)

本文档记录针对 PvP 大乱斗模式开展的长时间稳定性测试（Soak Testing）与系统压力测试结果。测试重点评估长时间运行下的进程稳定性（是否存在崩溃、内存泄漏或逻辑死锁）、帧耗时波动分布以及随并发人数增长的网络带宽瓶颈。

---

## 一、 测试目标与测试边界

### 1. 测试目标
- **长时间运行稳定性**：验证高频对战与实体交互下，服务端与客户端是否存在原生崩溃（Segmentation Fault）、引擎异常或断线死锁。
- **高负载性能表现**：测量多客户端并发场景下的主循环帧间隔（Frame Time）、快照到达抖动以及瞬时卡顿（Stall）发生频率。
- **网络负载与扩展性评估**：分析状态同步带宽随玩家人数增加的增长曲线，识别潜在的网络吞吐瓶颈。

### 2. 测试方法与编排机制
- **测试套件**：基于 `tests/royale_soak_probe.tscn` 与 `tests/royale_soak_probe.sh` 构建自动化测试编排器。
- **全流程驱动**：编排器作为宿主拉起独立的专用工作进程（Worker Server）及多个无头（Headless）客户端实例，真实执行完整生命周期：
  $$\text{连接大厅} \longrightarrow \text{创建/加入房间} \longrightarrow \text{连接对局 Worker} \longrightarrow \text{角色认领} \longrightarrow \text{加载 royale\_game 场景} \longrightarrow \text{对战交互} \longrightarrow \text{结算退出}$$
- **自动化测试 Bot 行为仿真**：客户端注入 `tests/soak_bot_input.gd` 模拟机器人，除遍历基础移动、跳跃、下蹲、攀爬、潜水、切枪开火外，增加了**朝向最近敌对目标索敌与交火**逻辑，确保产生真实的受击、阵亡、复活、击杀广播与伤害结算。
- **中途离场场景覆盖**：配置指定客户端在对局进行至 45% 时主动触发按键退出（ESC 返回主菜单），验证中途离场下的场景切换安全性及服务端对断开连接的处理逻辑。

### 3. 测试边界与限制说明
1. **渲染层开销隔离**：测试使用无头模式（Dummy Renderer）运行，测得的数据反映网络通信、物理模拟、场景树节点调度与 UI 逻辑耗时，未包含真实 GPU 渲染与 Shader 呈现管线开销。
2. **Worker 进程输出管道**：通过 `OS.create_process` 拉起的独立 Worker 服务端，其标准输出独立重定向，性能探针主要通过客户端接收快照的连续性及结算事件反推服务端健康状态。
3. **环境破坏覆盖度**：测试采用的标准 PvP 地图 `maps/factory1v1.cyrm` 中可破坏砖块数量极少，场景破坏（`tile_destroyed`）引发的动态碰撞体重建开销主要由专属探针 `tests/tile_destroy_probe.gd` 独立覆盖。

## 二、 实测性能数据与分析

### 1. 客户端帧耗时分布（`Engine.max_fps = 60`，基准标称 16.67ms）

| 轮次 | 客户端数 / 配置说明 | 平均帧耗时 (avg) | 95分位数 (p95) | 最大单帧耗时 (max) | >33ms 帧数占比 | >100ms 帧数 |
|---|---|---|---|---|---|---|
| A | 4 客户端 | 16.66 ms | 17.0 ms | 40~45 ms | 2~13 帧 / 端 | 0 |
| A | 6 客户端（优化前基线） | 16.71 ms | 17.5 ms | 79~81 ms | 116~121 帧 / 端 | 0 |
| B | 6 客户端（对照：禁用排行榜重建） | 16.66 ms | 30.4~30.6 ms | 37~48 ms | 37~52 帧 / 端 | 0 |
| C | 6 客户端（同配置复现测试） | 18.05 ms | 31.2~31.8 ms | 178~256 ms | 163~181 帧 / 端 | 58~64 帧 / 端 |

#### 离散度与主机并发环境噪声分析
对比 A 轮与 C 轮（相同配置的两次独立执行）：
- 虽然平均帧时间均接近 16.7ms（维持 60 FPS 满帧基线），但最大单帧耗时从 80ms 上升至 256ms，`>100ms` 的严重卡顿从 0 次激增至约 60 次。
- A 轮的最坏帧出现于对局中段（t ≈ 53.7s），而 C 轮的最坏帧集中在场景初始化与地图加载阶段（t ≈ 4.5~5.5s）。
- **分析结论**：在本地单台宿主机上同时并发运行 7 个 Godot 实例（1 个大厅编排进程 + 1 个 Worker 服务端 + 6 个客户端）时，操作系统进程调度与 CPU 资源竞争产生了显著的背景噪声。单次观察到的偶发帧耗时峰值不能直接等同于单一代码逻辑的确定性开销，性能评估需结合纯逻辑微基准测试（Micro-benchmarks）进行隔离分析。

## 三、 快照网络带宽与传输瓶颈

实测测得每个角色在单一物理快照中的状态载荷恒定约为 **0.96 KB**：

| 对局人数 (N) | 单客户端下行吞吐 | 单快照数据包体积 | 服务端总上行带宽要求 |
|---|---|---|---|
| 4 人局 | 230 KB/s (1.8 Mbps) | 3.83 KB | 920 KB/s (7.4 Mbps) |
| 6 人局 | 345 KB/s (2.8 Mbps) | 5.75 KB | 2.07 MB/s (16.6 Mbps) |
| **8 人局** | **460 KB/s (3.7 Mbps)** | **7.70 KB** | **3.68 MB/s (约 29.4 Mbps)** |

### 扩展性架构瓶颈分析
1. **$O(N^2)$ 广播开销**：在 `MatchHost._broadcast_snapshot` 中，服务端每帧将包含全部 $N$ 个玩家完整物理状态的全量数据包，向所有 $N$ 个客户端分别下发一次。服务端总上行带宽随玩家数量呈平方级增长（$\text{Bandwidth} \propto 57.5 \times N^2 \text{ KB/s}$）。当扩展至 8 人局时，服务端稳态持续上行带宽需求高达近 30 Mbps，超出普通网络环境的承载上限。
2. **超出 MTU 分片与不可靠包丢包放大**：ENet 默认网络最大传输单元（MTU）通常约为 1400 字节。当快照体积达到 3.8KB~7.7KB 时，底层必须将数据包切分为 3~6 个分片传输。由于快照采用不可靠通道（Unreliable），**任意单个分片丢失均会导致整帧快照无法重组并被完全丢弃**，在公网丢包环境下将显著放大客户端拉扯与画面冻结现象。

## 四、 排行榜全量重建开销微基准测试

针对 A 轮测试中观察到的每 1 秒出现一次约 44~80ms 帧耗时波动的现象，通过微基准探针 `tests/royale_hud_cost_probe.tscn` 对 `RoyaleHud._on_round_state` 进行纯逻辑耗时隔离测量：

| 结算排行榜行数 | 中位耗时 | 95分位数 | 最大单帧耗时 |
|---|---|---|---|
| 4 行 | 2.63 ms | 3.38 ms | 4.17 ms |
| 6 行 | 3.78 ms | 4.23 ms | 4.79 ms |
| 8 行 | 4.68 ms | 5.15 ms | 5.18 ms |

- **开销分析**：优化前，`RoyaleHud` 在接收到每秒一次的 `round_state` 状态广播时，将所有既有行节点调用 `queue_free()` 销毁，随后重新实例化 $N$ 个 `Label` 节点并强制触发 `get_combined_minimum_size()` 布局计算。虽然该操作在 6 人局下产生的直接同步耗时仅为 3.8ms，不足以完全解释 80ms 的外部复合卡顿，但频繁的节点创建、销毁与 UI 重排构成了不必要的性能开销。

## 五、 稳定性监控与缺陷治理

在全部测试轮次中，系统稳定性表现良好：
- **原生崩溃率**：**0 次**。未出现任何进程闪退、段错误或未捕获的 C++ 引擎异常。
- **脚本异常**：日志分析结果显示脚本级错误（`SCRIPT ERROR` / `Parse Error`）为 **0 次**。
- **进程生命周期收尾**：所有并发客户端与工作进程均完整运行至 `MATCH_OVER` 状态，正常完成结果持久化并以退出码 0 退出。
- **动态切场景安全性**：在中途触发 ESC 退出的客户端测试中，通过 `Level0.safe_change_scene` 返回主菜单安全平稳，服务端成功捕获玩家离场并向剩余玩家广播 `round_state.left` 事件，其余对局玩家继续正常游戏至比赛结束。

### 已落地的 4 项缺陷修复

#### 1. RoyaleHud 排行榜节点池化复用
- **问题**：`scenes/royale_hud.gd` 每次收到回合状态广播时，均对 UI 节点执行全量销毁与重建，导致单帧产生 3.8ms 的主线程同步停顿。
- **优化**：改为**节点池化复用**机制。在玩家数量未发生变化时，仅更新既有 `Label` 的文本与数值属性；仅在检测到玩家增减时才执行节点的动态增删，并移除了每秒重复调用的全局最小尺寸刷新。
- **成效**：同步耗时显著下降至 **0.33ms (4人) / 0.41ms (6人) / 0.46ms (8人)**，降幅超过 88%。

#### 2. 大乱斗结算阶段场景切换定时器竞争与暂停菜单残留
- **问题**：`scenes/royale_game.gd` 在比赛结束（`MATCH_OVER`）后启动 6 秒定时器切回主菜单，但定时器回调缺少节点在场校验（`is_inside_tree`），且未销毁既有的暂停菜单实例。若玩家在此 6 秒窗口内通过暂停菜单手动返回主菜单，定时器到期后将触发二次场景切换，产生多余的菜单实例。
- **优化**：对齐 1v1 模式的防御规范。在触发 `MATCH_OVER` 时立即释放暂停菜单（`queue_free`），并在定时器回调首行补充 `if not is_inside_tree(): return` 安全守卫。

#### 3. 服务端子弹跟踪集合内存单调累积
- **问题**：`server/match_host.gd` 中的 `_seen_bullets` 字典用于记录已广播过的子弹实例 ID。原逻辑仅在换局重置世界时清空，而大乱斗模式为单回合连续战斗，导致整场比赛发射的子弹 ID 持续在内存中累积。
- **优化**：在每物理帧子弹命中裁决阶段（`_adjudicate_bullets`），收集当前物理空间中实际存活的子弹 ID 集合，并在帧末进行全局原子替换，及时淘汰已销毁子弹的跟踪记录。

#### 4. 大厅广播窗口期 ENet 通道发包告警
- **问题**：日志中偶发 `Unable to send packet on channel 0, max channels: 0` 引擎底层告警。根因在于 `server/room_manager.gd` 中的 `_flush_royale_state` 采用了延迟调用机制（`call_deferred` 并在下一帧发送），在排队到实际执行期间，房间可能已正式开局且客户端已转连并断开大厅连接，导致向已失效的 Peer 发送 RPC。
- **优化**：在真正执行数据发送前再次增加 `in_match` 状态与 Peer 在线校验，对于已进入战斗的房间跳过无意义的等待室广播。

### 3. 后续规划
1. **实机渲染基准测试**：在真实硬件终端上执行带 UI 与特效渲染的完整对局，针对 Shader 与粒子系统建立真实 GPU 帧耗时基线。
2. **状态同步协议演进**：针对 6 人及以上的大乱斗场景，推进快照增量同步（Delta Snapshots）与感兴趣区域（AOI）过滤，降低服务端广播带宽，消除超 MTU 分片带来的丢包隐患。
3. **输入时钟自适应同步**：引入严格的输入序号校验机制，结合网络往返延迟（RTT）动态平滑客户端输入上报节奏。
