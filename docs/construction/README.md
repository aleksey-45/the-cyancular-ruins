# docs/construction —— AI 施工产物

> **★ 这里不是真相源。**
> 本目录放 AI 生成的 **review / spec / plan**（代码审查报告、规格方案、计划与任务拆解）。
> **任何结论都必须先"提升"到 `docs/systems/`、`docs/netcode/`、`docs/workflow/` 才算生效** ——
> 写在这里的结论不作数，只作过程记录。改代码前别把它当契约读。

## 为什么会有这个目录（以及它为什么危险）

2026-10 本仓曾把「入库的 spec 与 plan」放在 `docs/superpowers/`，后来整体删除并立下
「本仓不设归档目录：历史看 `git log`，一次性审计 / 旧计划不入库」。删它的原因是过程文档会**腐烂**：
结论过期、引用失效，却还占着"文档"的名分被人当现行契约读。

`construction/` 是有意识地恢复这类产物，因此必须配机制约束，否则就是同一个坑再走一遍。

## 三条硬规则

| # | 规则 | 不遵守的后果 |
|---|---|---|
| 1 | 文件名 `YYYY-MM-DD-<slug>.md`（例：`2026-11-17-params-tres-review.md`） | **工具判红**（`check_naming.py` 规则 G）—— 日期让陈旧一眼可见，并保证排序 |
| 2 | 第一行（`#` 标题之后的首行非空行）必须是状态横幅：<br>`> 日期: 2026-11-17 · 状态: 进行中` | **工具判红**（规则 G）。状态取 `进行中` / `已完结` / `已废弃` / `已提升 → docs/<域>/<文件>.md` |
| 3 | 结论已并入真相源后，把状态改成 `已提升 → <路径>`（或 `已废弃`） | 不提就会有人照着旧结论改代码 |

## 子目录

| 目录 | 装什么 |
|---|---|
| [`review/`](review) | 代码审查报告（按提交 / 按子系统） |
| [`spec/`](spec) | 规格与方案（迁移方案、接口设计、取舍分析） |
| [`plan/`](plan) | 计划与任务拆解（分期、验收标准、写作用域） |

## 与链接守卫的关系

本目录**不纳入** `check_naming.py` 的"路径必须存在"检查（规则 C）：三个月前的 review 引用的文件
可能早已删除或改名，那是**记录**而不是错误 —— 与 `docs/` 顶层历史文档同款理由。
代价是这里的路径没有机械守卫；要查只能手工扫。**这也是规则 1 / 2 存在的意义**：
靠"日期 + 状态"让读者一眼判断该不该信它，而不是靠路径正确性。
